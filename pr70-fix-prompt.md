## 2. Review Findings to Address

### 2a. CRITICAL (P1) — `_populateGatewayDeviceLive()` only updates network cards

**Reported by:** Both Codex (P1) and Copilot
**File:** `dashboard/dashboard.js` (and mirrored to `dashboard/dashboard.html`)

**Problem:** `_populateGatewayDeviceLive()` only updates DOM fields when `cat === 'network'`.
Environmental and other cards rendered by `renderGatewayDevices()` never receive temperature/humidity
values from `/api/aggregator/live` and remain in a perpetual "waiting" state.

**Fix:** Expand `_populateGatewayDeviceLive()` to handle all device categories. For environmental
sensors, map the live payload fields (`temp`, `hum`, `batt`) to the corresponding DOM elements
using the same pattern as `handleState()` / SSE updates but driven by the aggregator live JSON.

**Note:** This is a functional bug that affects the main per-gateway view. Must be fixed.

### 2b. IMPORTANT (P2) — Per-gateway tab not refreshed on poll

**Reported by:** Codex (P2)
**File:** `dashboard/dashboard.js` (and mirrored to `dashboard/dashboard.html`)

**Problem:** In `pollAggregatorLive()`, only the `all` and `settings` tabs trigger re-renders.
When a specific gateway tab is active, no refresh path runs — per-gateway device data becomes stale.

**Fix:** Add an `else` branch in `pollAggregatorLive()` that calls a lightweight update function
for the active gateway tab:

```js
// Inside pollAggregatorLive(), after the settings check:
else {
  // Refresh the active per-gateway view
  var gw = data.gateways.find(function(g) { return g.id === gwId; });
  if (gw) _populateGatewayDeviceLive(gwId, gw);
}
```

### 2c. IMPORTANT — Local device cards stuck in "waiting" state in aggregator mode

**Reported by:** Copilot (2 comments on same issue)
**File:** `dashboard/dashboard.js` (and mirrored to `dashboard/dashboard.html`)

**Problem:** In aggregator mode, the boot path builds local device cards (e.g., `wan_ping`) but
never starts the normal live update mechanisms (SSE/polling and `/api/v2/live` polling). Local
cards render but remain permanently in the "waiting" state.

**Fix (choose one):**
- **Option A (recommended for this step):** Do NOT render local device cards in aggregator mode.
  Add a comment explaining why. The aggregator's own sensors are secondary to the gateway view.
- **Option B:** Start the satellite live update mechanisms (`connectSSE()`, `pollV2Live()`) in the
  aggregator boot path after `initAggregatorDashboard()`.

### 2d. IMPORTANT — Namespaced IDs break manifest lookups and history URLs

**Reported by:** Copilot (2 comments with code suggestions)
**File:** `dashboard/dashboard.js` (and mirrored to `dashboard/dashboard.html`)

**Problem:** Per-gateway sensors get namespaced IDs (`"gwId.deviceId"`), but downstream code
assumes `sensor.id` matches `manifest.sensors[].id`. This breaks:
- `buildNetworkCard()` manifest lookups
- `fetchDeviceHistory()` URL construction (fallback URLs point to non-existent endpoints)

**Fix:** Preserve the original device ID alongside the namespaced DOM ID:
```js
cfg._gwId = gwId;
cfg._deviceId = s.id;        // original manifest ID
cfg._namespacedId = nsId;     // DOM-safe namespaced ID
```
Then update `buildNetworkCard()` and `fetchDeviceHistory()` to use `cfg._deviceId` when present.

### 2e. SECURITY — HTML injection via innerHTML with gateway data

**Reported by:** Copilot (3 comments on different locations)
**Files:** `dashboard/dashboard.js`, `dashboard/dashboard.html`

**Problem:** `gw.name`, `gw.id`, `gw.base_url` are interpolated directly into HTML via string
concatenation + `innerHTML`/`insertAdjacentHTML`. Malformed values could inject markup.

**Fix:** Use the existing `escAttr()` function for attribute values, and add a text-escaping
function for text content. Or switch to DOM APIs (`createElement` + `textContent`).

**Note:** In this embedded context (ESP32 serving its own dashboard), the risk is low since
gateway data comes from the device's own config. However, it's good practice to fix. If this
would significantly delay the PR, document it as a TODO for v7.5.5.4.

### 2f. SECURITY — JSON injection in firmware gateways response

**Reported by:** Copilot
**File:** `dashboard/sensor_history_multi.h`

**Problem:** `sat.base_url` is concatenated directly into a quoted JSON string in the gateways
response builder. If `base_url` contains a quote or backslash, this produces invalid JSON.

**Fix:** JSON-escape `base_url` before appending, or validate at config load time that URLs
contain only safe characters.

### 2g. PERFORMANCE — `out.reserve()` undersized for manifest payload

**Reported by:** Copilot
**File:** `dashboard/sensor_history_multi.h`

**Problem:** Including full cached manifest JSON in the gateways response increases size by
several KB per satellite, but `out.reserve()` is still tuned for the pre-manifest payload.
This forces `std::string` to grow/reallocate on the embedded heap.

**Fix:** Calculate reserve size based on expected manifest length:
```cpp
size_t reserve_size = 512; // base
for (int i = 0; i < MAX_SATELLITES; i++) {
  reserve_size += 256 + strlen(satellite_caches[i].manifest_json);
}
out.reserve(reserve_size);
```
