# v7.6.10.2 — Operator Flash & Measure Procedure

_Phase VX Step 2. Operator-driven — not an agent prompt._
_Purpose: Flash each new board with full project firmware, collect measurements._
_Prerequisite: PR #201 (v7.6.10.1) merged. Config backup files present for all boards._

---

## Why This Document Exists

The sprint prompt (`phaseVX-board-onboarding-sprint-prompt.md`) listed "provision.sh target"
as a v7.6.10.2 deliverable, but the v7.6.10.1 handoff prohibited provision.sh changes.
This document resolves that gap by providing a manual provisioning procedure that works
without new provision.sh targets.

The manual procedure uses the same config files and pipeline that provision.sh would use.
Adding formal provision.sh targets for these boards is deferred to Phase 7, when the boards
get permanent sensor assignments and roles.

## Procedure: Flash One New Board

Repeat for each of the 3 boards. Example below uses the S3 SuperMini — substitute the
correct hostname for other boards.

### Step 1: Switch to the board's config

```bash
# Clean any active non-default config
bash scripts/provision.sh satellite

# Remove the C3 default gateway.json (provision.sh satellite leaves it absent)
rm -f config/gateway.json

# Copy this board's gateway and sensors configs into active position
cp config/gateway-sat-s3-4m-173.json.bak config/gateway.json
cp config/sensors-sat-s3-4m-173.json.bak config/sensors.json
```

### Step 2: Regenerate firmware for this board

```bash
python3 scripts/render_sensor_config.py --write
```

This generates `firmware/esp32-s3-supermini-4m-gw.yaml` (or similar — check the output).
The generated YAML uses the board profile, partition table, and sensor configs.

### Step 3: Run the full pipeline

```bash
bash scripts/assemble-sensor-history.sh --write
bash scripts/bundle-dashboard.sh --write
python3 scripts/render_sensor_config.py --write
node tests/fixtures/generate-fixtures.js
python3 scripts/render_sensor_config.py --write
bash scripts/build-dashboard.sh --write
bash scripts/minify-dashboard.sh
bash scripts/generate-header.sh
python3 scripts/render_sensor_config.py --check
```

Or use the pipeline shorthand if available.

### Step 4: Compile and flash

```bash
# Find the generated YAML name from Step 2 output
esphome compile firmware/<generated-yaml-name>.yaml

# Flash via OTA (if board already has a network-capable firmware):
esphome run firmware/<generated-yaml-name>.yaml --device=192.168.120.173

# Or via USB serial:
esphome run firmware/<generated-yaml-name>.yaml --device=/dev/ttyACM1
```

### Step 5: Wait 2 minutes, collect measurements

```bash
curl -s -u ESPadmin:ESPpass100 http://192.168.120.173/api/status/full | jq '{
  version, httpd_stack_watermark_bytes, free_heap, min_free_heap,
  free_heap_internal, free_heap_total, uptime_seconds
}'
```

### Step 6: Run stress test

```bash
# S3 SuperMini has 2MB PSRAM — try concurrent=4 first, then 8 if stable
bash scripts/stress-test-httpd-stack.sh 192.168.120.173

# C5 has 8MB PSRAM — can use 8
bash scripts/stress-test-httpd-stack.sh 192.168.120.180 --concurrent=8

# C6 has no PSRAM — use default 4
bash scripts/stress-test-httpd-stack.sh 192.168.120.184
```

### Step 7: Record results

Fill in the corresponding rows in `Docs/board-measurement-log-v7.6.10.md`.

### Step 8: Restore CI-safe config

```bash
bash scripts/provision.sh satellite
bash scripts/preflight.sh
```

⚠️ **CRITICAL**: Always run `provision.sh satellite` before pushing any commits.
The generated YAML for the new board and the active gateway.json are NOT CI-safe.

## Notes

- The sensors.json for all new boards is identical to the C3/WROOM sensor list (same
  physical location, same BLE beacons). If a board can't reach a specific beacon due to
  antenna differences, it will still compile and run — the sensor will just show "never seen".

- If `render_sensor_config.py` doesn't recognize the board_id in the gateway.json,
  check that the board profile exists at `firmware/boards/<board_id>.yaml` and that
  the `board_id` field matches exactly.

- The generated YAML filename follows the pattern: `firmware/<esphome_name>-gw.yaml`
  where `esphome_name` comes from the gateway.json.
