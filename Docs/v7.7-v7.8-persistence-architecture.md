## 1. Problem Statement

### 1.1 The cascade that exposed the design flaw

In March 2026, the project added a network ping probe device to the manifest (v7.5.4.0, Phase 4). This was supposed to be a low-risk additive change — the ping device uses RAM-only history with no flash persistence. What followed was a three-bug cascade:

**BUG-045:** The Python generator aliased `NUM_SENSORS = NUM_DEVICES`. Because `NUM_SENSORS` is a compile-time constant that dimensions the `SegmentSnapshot` struct (which contains `temp[NUM_SENSORS][4]` and `hum[NUM_SENSORS][4]`), changing it from 3 to 4 made the struct 68 bytes larger. Every existing NVS segment blob was now the wrong byte size for the new firmware.

**BUG-046:** The `HistoryMeta` blob stored `num_sensors = 3` in NVS. The corrected firmware expected `num_sensors = 3` (after the BUG-045 fix), but the meta validation failed because the stale blob still said `num_sensors = 4` from a brief window when the buggy firmware ran. The fix code reset the meta in RAM but never persisted the correction back to NVS, creating an infinite reset loop on every boot.

**BUG-048:** Even after the meta migration was fixed, the actual segment data blobs written during the `NUM_SENSORS = 4` period were physically 298 bytes, while the corrected firmware allocated a 230-byte read buffer. `nvs_get_blob()` returned `ESP_ERR_NVS_INVALID_LENGTH` — the data was irrecoverably lost without a cross-schema deserializer.

**The fundamental problem:** A compile-time constant (`NUM_SENSORS`) is embedded in a persisted data structure's physical layout. Changing the constant — even when the intent is to add a completely unrelated device — destroys all existing data.

### 1.2 Why this matters for the roadmap

The v7.5–v7.6 architecture plan envisions a sensor ecosystem:

- ThermoPro temperature/humidity sensors
- Network ping probes
- Weather stations (temp, humidity, wind speed, rainfall, UV)
- Leak detectors (binary state)
- Soil moisture sensors (single analog)
- Ultrasound distance sensors
- Host/computer health monitors (CPU, RAM, disk, swap)

Every sensor type has a different metric shape. Weather stations have 4-6 metrics; leak sensors have 1; host monitors have 4. Under the current persistence model, adding any of these requires changing `NUM_SENSORS` or creating a parallel persistence system — and changing `NUM_SENSORS` destroys all existing history.

The architecture plan's Section 10.2 correctly deferred non-environmental persistence to RAM-only. But this means operational metrics (ping latency trends, weather history, leak event logs) are lost on every reboot. As the project moves toward production deployments, that limitation becomes unacceptable for several use cases — weather stations need multi-day history for trend analysis, leak sensors need event persistence for audit trails, and even ping probe history is useful for ISP reliability tracking.

### 1.3 What this document covers

This architecture defines a **per-device persistence engine** that replaces the current monolithic `SegmentSnapshot` model. The key properties:

- Adding or removing a device never touches another device's NVS data
- Each device's metric count is encoded in the blob header, not in a compile-time constant
- Retention is budgeted per device from the manifest, not uniform
- Per-device delete, import, and export
- One-time automatic migration from v7.x format
- Backward-compatible rollback to v7.x firmware
- Extensible to larger flash platforms (ESP32-S3, ESP32-WROVER) with no structural changes

## 2. Current System Assessment

### 2.1 What works

The current persistence engine is not broken — it has been reliable for its designed scope (3 fixed ThermoPro sensors). Its strengths:

**Deterministic sizing.** `sizeof(SegmentSnapshot)` is a compile-time constant. `nvs_get_blob()` always knows the exact buffer size. No runtime allocation for persist or restore.

**Ring buffer simplicity.** 1080 slots (45 days × 24 hours), circular write, oldest-drops-off. The write cursor (`next_slot`) and valid count (`valid_segments`) fully describe the state.

**Reliable boot restore.** The restore loop reads the newest N segments into RAM in chronological order. The yield-every-4-blobs pattern (BUG-043) prevents HTTP task starvation. The dashboard has history immediately after boot.

**Working import/export.** CSV export produces human-readable data. Multi-sensor import does a clean wipe-and-replace. Single-sensor merge does read-modify-write with epoch→slot indexing.

### 2.2 What doesn't work

**Monolithic blob.** All sensors' data lives in one struct. The struct size changes when sensor count changes. This is the root of BUG-045/046/048.

**Fixed metric shape.** Only `temp` and `hum` are persisted. No mechanism for additional metrics. The persistence layer is ThermoPro-specific while the rest of the architecture (SensorEntity, CARD_RENDERERS, manifest v2) is already generalized.

**Uniform retention.** All sensors share the same 1080-slot ring buffer. No way to give environmental sensors more retention than operational metrics.

**All-or-nothing delete.** The `/api/delete-data` endpoint erases the entire history partition. No way to delete one device's data while preserving others. This is an operational gap — if a sensor is replaced, its old data should be removable without destroying other sensors' history.

**All-or-nothing import.** The multi-sensor import does a full partition wipe. Single-sensor merge works per-sensor but reads through all segments. No per-device import that only touches one device's NVS keys.

### 2.3 The core struct

```cpp
struct SegmentSnapshot {                          // v7.x current
  SegmentSnapshotHeader header;                   // 26 bytes
  uint16_t temp_counts[NUM_SENSORS] = {};         // 2 × NUM_SENSORS
  uint16_t hum_counts[NUM_SENSORS] = {};          // 2 × NUM_SENSORS
  HistEntry temp[NUM_SENSORS][PERSIST_POINTS_PER_SEGMENT] = {};  // 8 × NUM_SENSORS × 4
  HistEntry hum[NUM_SENSORS][PERSIST_POINTS_PER_SEGMENT] = {};   // 8 × NUM_SENSORS × 4
};
// NUM_SENSORS=3: sizeof = 230 bytes
// NUM_SENSORS=4: sizeof = 298 bytes  ← 68 bytes larger, ALL blobs incompatible
```

The problem is visible: `NUM_SENSORS` appears in four array dimensions. Changing it changes the struct's physical byte layout.

## 3. Requirements

### 3.1 Functional requirements

**R1. Accommodate different types and numbers of devices/sensors.** The persistence format must work for any mix of environmental, network, weather, leak, soil, distance, and host health devices. Adding a weather station to a system with 3 ThermoPros must not require any format migration for the existing ThermoPro data.

**R2. Support device-specific metric shapes.** Each device class has different metrics. ThermoPro: temp + humidity. Weather station: temp + humidity + wind speed + rainfall. Ping: latency + success rate. Host: CPU + RAM + disk + swap. The persistence format must handle 1-6 metrics per device without wasting excessive space on devices with fewer metrics.

**R3. Add/remove devices without destroying existing data.** This is the critical requirement that the current system violates. The user must be able to add a ping probe, remove a broken sensor, or swap a ThermoPro without any impact on other devices' persisted history.

**R4. Per-device data deletion.** Delete one device's history while preserving all other devices' data. Needed when replacing a sensor, cleaning up test data, or removing a device from the system.

**R5. Per-device and all-device import/export.** Export a single device's history as CSV. Import data for one device without touching other devices. Also support full-system export/import (all devices in one file).

### 3.2 Non-functional requirements

**R6. Zero dynamic allocation in persist/restore paths.** ESP32-C3 heap fragmentation risk. All buffers must be stack-allocated with compile-time known sizes.

**R7. Boot restore within 10 seconds.** Users expect the dashboard to have history shortly after boot. The current system restores 24 segments in ~2 seconds. The new system with 5-7 devices must stay under 10 seconds.

**R8. Backward-compatible rollback.** If a user flashes v7.7 firmware, discovers a problem, and rolls back to v7.5 firmware, their original v7.x history data must still be accessible. The migration must not delete old-format blobs.

**R9. No partition table change required for basic operation.** The current 512 KB history partition must work for the common case (3 ThermoPros + 1-2 additional devices). Larger partitions are optional for deployments with many devices or longer retention.

**R10. Platform extensibility.** The design must work on ESP32-C3 (512 KB history, ~320 KB RAM), ESP32-S3 (up to 4 MB flash for history, ~512 KB RAM), and Raspberry Pi (unlimited). The struct layouts and algorithms must be the same; only the partition size and budget calculations change.

## 4. Design Principles

### 4.1 Per-device isolation

Each device's history segments are stored under device-specific NVS keys. Adding device B never reads, writes, or validates any of device A's keys. Removing device B deletes only its keys.

**WHY:** This is the direct solution to BUG-045/046/048. The root cause was coupling all devices into one struct. Per-device isolation eliminates that coupling entirely. A weather station addition cannot change a ThermoPro segment's byte layout because they are in completely separate NVS entries.

### 4.2 Self-describing blobs

Every segment blob carries its metric count in the header. The restore path validates the blob against its own declared metric count, not against a compile-time constant.

**WHY:** This is what makes firmware updates safe. If a firmware update adds a metric to a device (e.g., weather station gains UV index), the old blobs say `metric_count = 4` and the new firmware expects 5. The restore path loads metrics 0-3 from the old blob and leaves metric 4 (UV) empty. The blob's self-description drives the restore, not external assumptions.

### 4.3 Manifest-driven retention

The v2 manifest declares each device's persistence backend (`flash` or `ram_only`) and priority tier (`high`, `normal`, `low`). The firmware calculates per-device slot counts at boot based on partition size and priority shares.

**WHY:** Different sensor types have different retention value. 45 days of temperature history is highly valuable for energy auditing. 45 days of ping latency has diminishing value past ~14 days. The budget system lets users control the trade-off through the manifest rather than accepting uniform retention.

### 4.4 Fixed maximum metric count per blob

Segment blobs use a compile-time maximum: `MAX_PERSIST_METRICS = 6`. Devices with fewer metrics use a subset; unused slots are zeroed. The blob size is constant for all devices within a firmware build.

**WHY:** `nvs_get_blob()` requires the caller to provide the exact expected size. If blob sizes varied per device, the restore path would need to query blob size first (extra NVS read per blob) or use dynamic allocation. Constant size means a single stack-allocated buffer works for every device. The maximum of 6 covers the widest planned sensor (weather station with 5-6 metrics).

**WHY 6 and not 4 or 8:** 4 would exclude weather stations. 8 adds 64 bytes per blob (2 more metric slots × 4 data points × 8 bytes) across potentially thousands of blobs — a meaningful flash cost. 6 fits every planned device type with ≤2 unused slots for the narrowest (1-metric leak sensors).

### 4.5 Preservation over optimization

The migration from v7.x preserves old-format blobs in NVS. The delete operation marks keys for overwrite rather than explicit erasure where possible. Import validates before writing.

**WHY:** Data loss is the most severe failure mode for a history system. Every design decision should err toward keeping data accessible, even at the cost of flash utilization or restore speed.

## 5. Storage Model: Per-Device Segments

### 5.1 DeviceHistoryMeta

One blob per persistent device, storing the device's ring buffer state:

```cpp
static constexpr uint32_t DEV_HIST_MAGIC = 0x44485632UL;  // "DHV2"
static constexpr uint16_t DEV_HIST_VERSION = 1;

struct DeviceHistoryMeta {
  uint32_t magic = DEV_HIST_MAGIC;            // format identifier
  uint16_t version = DEV_HIST_VERSION;        // schema version for future migration
  uint16_t metric_count;                      // how many metrics this device persists
  uint16_t points_per_segment;                // data points per hourly segment (typically 4)
  uint16_t max_slots;                         // retention capacity (budget-calculated at boot)
  uint16_t valid_segments;                    // how many slots contain valid data
  uint16_t next_slot;                         // ring buffer write cursor
  uint16_t last_written_slot = 0xFFFF;        // most recently written slot (dedup/debug)
  uint32_t last_persist_epoch;                // epoch of most recent persist (dedup guard)
  char     device_id[16];                     // null-terminated device ID string
};
// sizeof = 36 bytes
```

**WHY `device_id` in the meta:** The meta must be self-identifying. During restore, the firmware matches the stored `device_id` against the current manifest to verify the meta belongs to the right device. This catches hash collisions (however unlikely) and detects misconfigured manifests.

**WHY `max_slots` stored in meta:** The budget calculation runs at boot and may produce different results if the manifest changes (device added/removed). Storing the previously calculated `max_slots` lets the restore path compare against the new calculation and resize the ring buffer gracefully.

### 5.2 DeviceSegment

One blob per device per hour:

```cpp
static constexpr int MAX_PERSIST_METRICS = 6;
static constexpr int PERSIST_POINTS_PER_SEGMENT = 4;  // 15-min intervals for 1 hour

struct DeviceSegmentHeader {
  uint32_t magic = DEV_HIST_MAGIC;
  uint16_t version = DEV_HIST_VERSION;
  uint16_t metric_count;                      // populated metric count in this blob
  uint16_t points_per_segment;
  uint32_t saved_at_epoch;                    // when this segment was written
  uint32_t first_epoch;                       // earliest data point epoch
  uint32_t last_epoch;                        // latest data point epoch
};
// sizeof = 22 bytes

struct DeviceSegment {
  DeviceSegmentHeader header;                 // 22 bytes
  uint16_t counts[MAX_PERSIST_METRICS] = {};  // 12 bytes (valid point count per metric)
  HistEntry data[MAX_PERSIST_METRICS][PERSIST_POINTS_PER_SEGMENT] = {};  // 192 bytes
};
// sizeof = 226 bytes (constant regardless of actual metric count)
```

**Size comparison:**

| Configuration | v7.x SegmentSnapshot | v8.x DeviceSegment |
|---|---|---|
| Struct size | 230 bytes (NUM_SENSORS=3) | 226 bytes |
| Metrics stored | 2 × 3 sensors = 6 | up to 6 per device |
| Devices per blob | ALL (monolithic) | ONE (isolated) |
| Total blobs for 3 ThermoPro, 45 days | 1,080 | 3 × 1,080 = 3,240 |
| Adding a device changes struct size? | YES (fatal) | NO |

**Data layout within a blob:** Metric positions are ordinal — metric 0 is the first persistent metric in the manifest, metric 1 is the second, and so on. The metric identity (what metric 0 "means") is resolved by matching the device ID against the manifest. The blob itself carries no metric key strings.

**WHY positional indexing:** Metric key strings like `"temp_c"` are 6-8 bytes each. Storing them in every hourly blob for every device wastes ~50-100 bytes per blob × thousands of blobs = 50-100 KB. The manifest already maps device+position→key. Positional indexing keeps blobs compact.

## 6. NVS Key Scheme

### 6.1 Constraints

ESP-IDF NVS keys are limited to **15 characters**. The key must encode:
- Which device the data belongs to
- Whether it's a meta blob or a segment blob
- For segments: which slot number

Device IDs can be up to 15 characters (e.g., `first_floor`, `wan_ping`). They cannot be used directly in NVS keys because the key must also include a prefix and slot number.

### 6.2 Hash-based keys

Use a 32-bit FNV-1a hash of the device ID, rendered as 8 hex characters:

```cpp
static uint32_t device_id_hash_(const char *id) {
  uint32_t h = 0x811c9dc5;
  for (const char *p = id; *p; p++) {
    h ^= (uint8_t)*p;
    h *= 0x01000193;
  }
  return h;
}
```

### 6.3 Key format

```
dm_{8hex}          → DeviceHistoryMeta     (3 + 8 = 11 chars)
ds_{8hex}_{3dec}   → DeviceSegment         (3 + 8 + 1 + 3 = 15 chars)
v7_migrated        → uint8_t flag          (11 chars)
```

**Examples:**
```
"office"     → hash 0xa3f7b2c1 → dm_a3f7b2c1, ds_a3f7b2c1_000 .. ds_a3f7b2c1_554
"wan_ping"   → hash 0x8e12d4f0 → dm_8e12d4f0, ds_8e12d4f0_000 .. ds_8e12d4f0_199
"first_floor"→ hash 0x5c9d1e3a → dm_5c9d1e3a, ds_5c9d1e3a_000 .. ds_5c9d1e3a_554
```

**Slot suffix:** 3 decimal digits, zero-padded. Max 999 slots per device (999 hours = 41.6 days). For the ESP32-C3's 512 KB partition, no device will exceed ~690 slots (28.8 days). The 999-slot limit leaves headroom for larger partitions on ESP32-S3.

**WHY hashing instead of truncated IDs:** `first_floor` is 11 characters. With a `ds_` prefix and `_000` suffix, the key would be `ds_first_floor_000` = 19 characters — exceeds the 15-char limit. Hashing to 8 hex characters is the only way to fit all components.

**Collision risk:** FNV-1a 32-bit has 2^32 = 4.3 billion possible values. For 20 devices, the birthday paradox gives collision probability ~(20²) / (2 × 2^32) ≈ 5 × 10⁻⁸. Effectively zero. The `DeviceHistoryMeta` also stores the full `device_id` string, so collisions are detected at restore time.

### 6.4 Key enumeration

NVS does not support prefix-based key listing. To enumerate a device's segment keys, the firmware computes the hash and iterates `ds_{hash}_000` through `ds_{hash}_{max_slots-1}` using `nvs_get_blob()` with `ESP_ERR_NVS_NOT_FOUND` as the stop condition.

**WHY this is acceptable:** The firmware knows each device's `max_slots` from the budget calculation. The restore loop reads exactly `min(valid_segments, RAM_SEGMENTS)` blobs — it never scans all possible keys.

## 7. Retention Budgeting

### 7.1 Budget calculation

At boot, the firmware calculates each persistent device's maximum slot count:

```
partition_bytes = esp_partition_find_first(history)->size
usable_bytes = partition_bytes × 0.85            // NVS page overhead, alignment waste
per_slot_cost = sizeof(DeviceSegment) + 48        // blob + NVS entry overhead ≈ 274 bytes
per_meta_cost = sizeof(DeviceHistoryMeta) + 48    // ≈ 84 bytes

persistent_devices = [d for d in manifest.devices if d.persist.backend == "flash"]
meta_total = len(persistent_devices) × per_meta_cost
segment_budget = usable_bytes - meta_total
```

### 7.2 Priority tiers

The manifest assigns each persistent device a `persist_priority`:

| Priority | Intended use | Default budget share |
|---|---|---|
| `high` | Long-term trending (environmental, weather) | 70% |
| `normal` | Moderate retention (soil, leak, distance) | 20% |
| `low` | Operational (ping, host health) | 10% |

Within each tier, budget is divided equally among devices in that tier:

```
per_device_slots[d] = tier_budget / (tier_device_count × per_slot_cost)
```

If a tier has no devices, its share is redistributed proportionally to other tiers.

### 7.3 Budget scenarios

**Scenario A: Current deployment (3 ThermoPro + 1 Ping, 512 KB partition)**

| Device | Priority | Slots | Days |
|---|---|---|---|
| Office, First Floor, Outside | high (85%) | 460 each | 19.2 |
| WAN Ping | low (15%) | 243 | 10.1 |

**Scenario B: Full deployment (3 ThermoPro + 1 Weather + 1 Ping + 2 Leak, 512 KB)**

| Device | Priority | Slots | Days |
|---|---|---|---|
| ThermoPro × 3, Weather × 1 | high (70%) | 284 each | 11.8 |
| Leak × 2 | normal (20%) | 162 each | 6.8 |
| WAN Ping | low (10%) | 162 | 6.8 |

**Scenario C: Full deployment with 640 KB partition**

| Device | Priority | Slots | Days |
|---|---|---|---|
| ThermoPro × 3, Weather × 1 | high (70%) | 355 each | 14.8 |
| Leak × 2 | normal (20%) | 203 each | 8.5 |
| WAN Ping | low (10%) | 203 | 8.5 |

### 7.4 Budget change handling

When the manifest changes (device added or removed), the budget recalculates at next boot. If a device's `max_slots` decreases:

- Existing segments beyond the new `max_slots` become unreachable
- They are naturally overwritten as the ring buffer wraps
- No explicit deletion needed — the ring buffer simply stops referencing them
- `valid_segments` is capped to `min(old_valid, new_max_slots)` and persisted

If a device's `max_slots` increases (device removed, freeing budget):

- The ring buffer naturally grows as new segments fill the expanded range
- No migration needed — just let `valid_segments` grow up to the new maximum

## 8. Manifest-Driven Persistence Configuration

### 8.1 Device-level persist block

The v2 manifest gains a `persist` block per device:

```json
{
  "id": "office",
  "name": "Office",
  "category": "environmental",
  "adapter": "thermopro_ble",
  "persist": {
    "backend": "flash",
    "priority": "high"
  },
  "measurements": [
    { "key": "temp_c",       "history": true,  "persist": true },
    { "key": "humidity_pct", "history": true,  "persist": true },
    { "key": "battery_pct",  "history": false, "persist": false },
    { "key": "rssi_dbm",     "history": false, "persist": false }
  ]
}
```

### 8.2 Per-measurement persist flag

Each measurement with `"persist": true` occupies one slot in the `DeviceSegment.data[]` array, at the ordinal position of that metric among all persisted metrics for the device.

**Rules:**
- `persist.backend = "flash"` → device gets NVS segment storage
- `persist.backend = "ram_only"` → device uses HistoryBuffer only (24h, lost on reboot)
- `persist: true` on a measurement requires `history: true` (can't persist without RAM history)
- Maximum 6 measurements with `persist: true` per device (`MAX_PERSIST_METRICS`)
- Measurements with `persist: false` still get RAM history if `history: true`
- A device with `persist.backend = "ram_only"` ignores per-measurement `persist` flags

### 8.3 Default behavior

If the manifest omits the `persist` block for a device:
- `environmental` category → defaults to `{ "backend": "flash", "priority": "high" }`
- `network` category → defaults to `{ "backend": "flash", "priority": "low" }`
- `system` category → defaults to `{ "backend": "ram_only" }`

This ensures backward compatibility — existing manifests without explicit persist blocks get sensible defaults.

### 8.4 Generator changes

The Python generator reads persist configuration and produces:
- `PERSIST_DEVICE_COUNT` — number of flash-persistent devices
- `PERSIST_DEVICE_IDS[]` — array of device IDs for persistent devices
- `PERSIST_METRIC_COUNTS[]` — per-device persistent metric count
- `PERSIST_PRIORITIES[]` — per-device priority tier enum

**WHY generate constants:** The firmware must know at compile time which devices persist and how many metrics each has. This avoids runtime JSON parsing and keeps the persist path free of dynamic allocation.

## 9. Boot Restore Flow

```
restore_all_devices():
  1. Initialize history NVS partition
  2. Check v7_migrated flag
     - If not set and old hist_meta exists → run v7 migration (Section 13)
     - Set v7_migrated = 1 after successful migration
  3. Calculate retention budget (Section 7)
  4. For each device in manifest where persist.backend == "flash":
     a. Compute NVS key hash for device ID
     b. Open NVS read-only
     c. Load DeviceHistoryMeta from dm_{hash}
     d. Validate: magic, version, device_id match current manifest
     e. If meta.metric_count != device's current persistent metric count:
        - Log metric count change
        - Will restore what we can (positional matching)
     f. If meta.max_slots != new budget max_slots:
        - Recalibrate (cap valid_segments if budget shrank)
        - Flag needs_persist
     g. Restore segments:
        - restore_count = min(valid_segments, RAM_SEGMENTS)
        - Start from newest segments working backward
        - For each segment: load blob, extract metrics 0..min(blob.metric_count,
          current_metric_count), push into HistoryBuffer
        - Yield every 4 segments (BUG-043 pattern)
     h. Close NVS read-only
     i. If needs_persist: open NVS read-write, save corrected meta, close
  5. Mark restore complete (g_history_restored_from_nvs = true)
```

### 9.1 Metric mismatch during restore

When a firmware update changes a device's persistent metric count:

**Adding a metric (e.g., weather station gains UV index, metric count 4→5):**
- Old blobs have `metric_count = 4` in their header
- Restore loads metrics 0-3 from the blob into HistoryBuffer slots 0-3
- Metric 4 (UV) has no historical data — HistoryBuffer starts empty
- DeviceHistoryMeta updated with `metric_count = 5`
- New segments written with 5 metrics going forward

**Removing a metric (e.g., device drops battery reporting, 4→3):**
- Old blobs have `metric_count = 4`
- Restore loads metrics 0-2, ignores metric 3 in the blob
- DeviceHistoryMeta updated with `metric_count = 3`

**Reordering metrics is NOT supported.** If the manifest reorders persistent metrics, the positional mapping breaks — old metric 0 data gets loaded into new metric 0's buffer, which may be a different measurement. The generator must validate that persistent metric ordering is append-only and emit an error if reordering is detected.

## 10. Persist Flow

```
persist_all_devices():
  For each device where persist.backend == "flash":
    1. Build DeviceSegment from device's HistoryBuffer ring buffers:
       - Export latest PERSIST_POINTS_PER_SEGMENT entries per persistent metric
       - Set header.metric_count, first_epoch, last_epoch
    2. Open NVS read-write for this device
    3. Load DeviceHistoryMeta
    4. Dedup: skip if meta.last_persist_epoch == segment.header.last_epoch
    5. Write segment to ds_{hash}_{next_slot}
    6. Update meta: advance next_slot, increment valid_segments (cap at max_slots),
       set last_persist_epoch
    7. Save meta
    8. Close NVS
    9. Yield between devices (BUG-043 pattern)
```

**Persist frequency:** Every hour, matching the current system. An ESPHome `interval:` lambda fires `persist_all_devices()` at the top of each hour.

**Error handling per device:** If one device's persist fails (NVS full, write error), log the error and continue to the next device. Don't fail the entire persist cycle because of one device.

## 11. Per-Device Delete

### 11.1 API endpoint

```
DELETE /api/v2/history/{device_id}
```

Response: `{ "ok": true, "device_id": "office", "deleted_segments": 442, "deleted_meta": true }`

### 11.2 Implementation

1. Compute NVS key hash for the target device ID
2. Open NVS read-write
3. Load DeviceHistoryMeta → get `valid_segments` and slot range
4. Delete all segment keys: `nvs_erase_key(ds_{hash}_{slot})` for each slot 0..max_slots-1
5. Delete meta key: `nvs_erase_key(dm_{hash})`
6. Commit: `nvs_commit()`
7. Close NVS
8. Clear the device's in-memory HistoryBuffer ring buffers

**WHY erase all slots, not just valid ones:** Over time, the ring buffer may have wrapped, leaving orphaned blobs at slots beyond the current valid window. A clean delete removes everything associated with the device.

### 11.3 Existing "delete all" endpoint

The existing `/api/delete-data` endpoint continues to work — it erases the entire history NVS partition, clearing all devices' data. The new per-device delete is additive.

## 12. Import/Export v2

### 12.1 Per-device CSV export

Each device exports a separate CSV. The format generalizes the current temp/hum format:

```csv
# device_id: office
# device_name: Office
# category: environmental
# metrics: temp_c,humidity_pct
# metric_units: °C,%
# exported_at: 2026-03-19T23:15:00Z
epoch,temp_c,humidity_pct
1710264000,23.4,45.2
1710264900,23.5,44.8
1710265800,,45.1
```

The `# ` comment headers carry device identity and metric metadata. The data rows have epoch + one column per persistent metric. Empty cells represent missing readings.

**Backward compatibility:** For environmental devices with temp+hum, this format is a superset of the current export. Existing export parsing tools that expect `epoch,value\n` format work with single-metric exports unchanged.

### 12.2 Multi-device bundle export

The "Export All" button produces a single CSV with device sections separated by headers:

```csv
# device_id: office
# metrics: temp_c,humidity_pct
epoch,temp_c,humidity_pct
1710264000,23.4,45.2
...

# device_id: wan_ping
# metrics: ping_ms,success_pct
epoch,ping_ms,success_pct
1710264000,12.3,100
...
```

### 12.3 Per-device import (merge)

Import data for one device without touching other devices:

```
POST /api/v2/import/{device_id}
```

The import reads the target device's existing segments, builds an epoch→slot index, overlays the imported data, and writes back modified segments. Only the target device's NVS keys are touched.

**WHY this is safe now:** In the per-device model, the merge only needs to index and modify one device's segments. There's no risk of the "segment index build failed" error that occurred in v7.x when the entire partition's segments were incompatible.

### 12.4 Multi-device import (replace)

Import data for all devices:

```
POST /api/import/all
```

This follows the existing wipe-and-replace pattern: clear the history partition, parse the multi-device CSV, write segments for each device.

### 12.5 Multi-device import (merge)

A new option that merges imported data into existing history per-device without wiping:

```
POST /api/v2/import/merge
```

For each device section in the uploaded CSV, perform a per-device merge. Devices not present in the CSV are untouched. This is the safest import option for partial data recovery.

## 13. Migration Path from v7.x

### 13.1 Detection

At boot, the firmware checks for the `v7_migrated` flag in NVS:
- If the flag exists and is 1: skip migration, proceed to v8 restore
- If the flag doesn't exist: check for old `hist_meta` key
  - If `hist_meta` exists: old v7.x data present, run migration
  - If neither exists: fresh install, no migration needed

### 13.2 Migration algorithm

```
migrate_v7_to_v8():
  1. Open history NVS read-only
  2. Load old HistoryMeta (v7 format) → get valid_segments, next_slot
  3. If valid_segments == 0: set v7_migrated=1, return (nothing to migrate)
  4. For each environmental device i in [0, NUM_ENV_SENSORS):
     a. Create DeviceHistoryMeta for devices[i].id
     b. Set metric_count=2 (temp, hum)
  5. Close NVS read-only

  6. Open NVS read-write
  7. For n = 0 to valid_segments-1:
     a. Compute old slot index
     b. Read old SegmentSnapshot (v7 format) from seg_{slot}
     c. For each environmental device i:
        - Extract temp[i][*] and hum[i][*] from old snapshot
        - Build new DeviceSegment for devices[i]:
          header.metric_count = 2
          data[0][*] = temp values, counts[0] = temp_count
          data[1][*] = hum values, counts[1] = hum_count
          header.first_epoch, last_epoch from data
        - Write to ds_{hash}_{slot} for device i
     d. Yield every 4 iterations (BUG-043)
  8. Write DeviceHistoryMeta for each device
  9. Set v7_migrated = 1
  10. Commit
  11. Close NVS

  DO NOT delete old seg_* or hist_meta keys (rollback safety)
```

### 13.3 Migration time estimate

1080 segments × 3 devices = 3240 new blob writes + 1080 old blob reads = 4320 NVS operations. At ~2ms per operation with periodic yields: ~9 seconds. Acceptable for a one-time boot event. The dashboard shows "Migrating history data..." during this period.

### 13.4 Rollback safety

After migration, the old `hist_meta` and `seg_NNN` keys remain in NVS. If the user rolls back to v7.x firmware:
- v7.x ignores `dm_*`, `ds_*`, and `v7_migrated` keys (unknown keys are harmless in NVS)
- v7.x reads `hist_meta` and `seg_NNN` — everything works as before

The old keys are only deleted when the user explicitly calls `/api/delete-data` (which erases the entire partition) or when the NVS partition fills up and ESP-IDF garbage-collects unused pages.

### 13.5 Migration space

During migration, both old and new blobs coexist. Space required:
- Old blobs: 1080 × 230 bytes = ~243 KB (already present)
- New blobs: 3 devices × 1080 × 226 bytes = ~713 KB (being written)
- Total: ~956 KB

This exceeds the 512 KB partition. **The migration must be selective:**

Option A: Migrate only the most recent `RAM_SEGMENTS` (24 segments = 24 hours) per device. This fits in the partition and matches what the user sees in the dashboard after boot.

Option B: Migrate based on available space. Calculate how many old segments can be converted before the partition fills, migrate that many (newest first), set `valid_segments` accordingly.

**Recommendation:** Option A. The user's most recent 24 hours are preserved. If they need older data, they should CSV-export before upgrading. This is the safest approach — the migration cannot fail due to space exhaustion.

## 14. Partition Layout Options

### 14.1 Current layout

```csv
ota_0,      app,  ota_0,    0x10000,  0x1B0000,    # 1728 KB
ota_1,      app,  ota_1,    ,         0x1B0000,    # 1728 KB
history,    data, nvs,      ,         0x80000,     # 512 KB
coredump,   data, coredump, ,         0x10000,     # 64 KB
```

### 14.2 Option: 640 KB history (recommended)

```csv
ota_0,      app,  ota_0,    0x10000,  0x1A0000,    # 1664 KB (was 1728)
ota_1,      app,  ota_1,    ,         0x1A0000,    # 1664 KB
history,    data, nvs,      ,         0xA0000,     # 640 KB (was 512)
coredump,   data, coredump, ,         0x10000,     # 64 KB
```

**Trade-off:** Each OTA slot shrinks by 64 KB. Current firmware binary is ~1550 KB; the new slot is 1664 KB, leaving **114 KB headroom** for firmware growth. This is comfortable.

### 14.3 Option: 768 KB history (aggressive)

```csv
ota_0,      app,  ota_0,    0x10000,  0x190000,    # 1600 KB
ota_1,      app,  ota_1,    ,         0x190000,    # 1600 KB
history,    data, nvs,      ,         0xC0000,     # 768 KB
coredump,   data, coredump, ,         0x10000,     # 64 KB
```

**Trade-off:** Only 50 KB OTA headroom. Viable after dashboard minification and unused component removal.

### 14.4 Partition change is optional

The v7.7 implementation must work with the existing 512 KB partition. Partition resizing is an optional optimization for users who want longer retention with many devices. Partition changes require a **full reflash** (not OTA) because the partition table is separate from the application firmware.

### 14.5 Platform comparison

| Platform | Flash | Recommended history partition | Typical retention (3T+1P) |
|---|---|---|---|
| ESP32-C3 SuperMini | 4 MB | 512–640 KB | 19–24 days |
| ESP32-S3 (8 MB flash) | 8 MB | 2 MB | ~60 days |
| ESP32-S3 (16 MB flash) | 16 MB | 4 MB | ~120 days |
| Raspberry Pi (SD card) | Unlimited | 100 MB+ file-based | Years |

The per-device segment model works identically on all platforms. Only the budget calculation changes (more partition space → more slots per device).

## 15. Memory Budget

### 15.1 RAM: HistoryBuffer instances

Each metric with `history: true` gets a `HistoryBuffer` (96 entries × 8 bytes = 768 bytes):

| Configuration | Buffers | RAM |
|---|---|---|
| 3 ThermoPro (2 metrics each, 2 metadata) | 6 history | 4.5 KB |
| + 1 Weather station (4 metrics) | 10 | 7.5 KB |
| + 1 Ping (2 metrics) | 12 | 9.0 KB |
| + 1 Host (4 metrics, RAM-only) | 16 | 12.0 KB |
| + 2 Leak (1 metric each) | 18 | 13.5 KB |

13.5 KB for 18 history buffers. That is ~4.2% of the ESP32-C3's 320 KB. Comfortable.

### 15.2 Stack: persist/restore buffers

`sizeof(DeviceSegment)` = 226 bytes. One is stack-allocated during each persist and restore operation. Negligible.

### 15.3 Heap: migration buffer

The v7→v8 migration needs to read a `SegmentSnapshot` (230 bytes) and write up to 3 `DeviceSegment` blobs (226 bytes each). Both can be stack-allocated in the migration function. Zero heap allocation.

## 17. Platform Extensibility

### 17.1 What stays the same across platforms

- `DeviceHistoryMeta` and `DeviceSegment` struct definitions
- NVS key scheme (hash-based)
- Persist and restore algorithms
- Manifest-driven configuration
- Import/export CSV format
- Per-device delete API

### 17.2 What changes per platform

| Aspect | ESP32-C3 | ESP32-S3 | Raspberry Pi |
|---|---|---|---|
| History partition size | 512–640 KB NVS | 2–4 MB NVS | File-based (unlimited) |
| Budget calculation input | Partition size | Partition size | Config-specified max size |
| MAX_PERSIST_METRICS | 6 | 6 (or 8) | 8+ |
| PERSIST_POINTS_PER_SEGMENT | 4 | 4 | 4 (or configurable) |
| Concurrent persist | Sequential | Potentially parallel | Parallel |
| Storage backend | ESP-IDF NVS | ESP-IDF NVS | SQLite or flat files |

### 17.3 Scaling to ESP32-S3

The ESP32-S3 with 8 MB flash can dedicate 2 MB to history. The budget calculation produces larger `max_slots` per device:

```
Scenario: 3 ThermoPro + 1 Weather + 1 Ping (2 MB history)
  ThermoPro (high): 2100 slots each = 87.5 days
  Weather (high): 2100 slots = 87.5 days
  Ping (low): 735 slots = 30.6 days
```

The code is identical — only the partition size input changes.

### 17.4 Scaling to Raspberry Pi

On a Pi, NVS is replaced by file-based storage (SQLite or flat JSON files per device). The `DeviceSegment` struct can still be used as the in-memory format, with a storage adapter that reads/writes files instead of NVS blobs. The API, manifest, and import/export formats remain identical.

## 18. What Not to Do

### Do not use variable-length blobs

`nvs_get_blob()` requires the caller to know the expected size. Variable-length blobs require either a size-query call first (doubling NVS reads) or dynamic allocation. Constant `sizeof(DeviceSegment)` eliminates both.

### Do not store metric keys in every segment blob

The metric identity is resolved through the manifest and meta. Storing key strings in every hourly blob wastes 50-100 KB across the partition.

### Do not attempt cross-schema blob deserialization for old data

If a device's metric count changes, don't try to reinterpret old blobs with a different metric layout. Load what matches by position, ignore the rest. Old blobs cycle out naturally as the ring buffer wraps.

### Do not dynamically resize NVS blobs based on metric count

This was explicitly identified as risky in the v7.5-v7.6 architecture plan (Section 14): "Coupling manifest edits to mandatory history wipe + migrate + restore is a poor user experience and a data loss vector." The fixed `MAX_PERSIST_METRICS` avoids this entirely.

### Do not delete old v7.x blobs during migration

They are the rollback safety net. Delete them only when the user explicitly erases history or when NVS garbage collection reclaims them.

### Do not make the persist path depend on WiFi or network state

The persist engine writes to local NVS only. If WiFi is down, persistence still works. Network-dependent storage (cloud upload) is a separate concern for future phases.

### Do not reorder persistent metrics in the manifest

Positional indexing means metric 0 is always metric 0 in the blob. Reordering causes silent data corruption (old metric 0 data loaded into new metric 1's buffer). The generator must validate append-only ordering.
