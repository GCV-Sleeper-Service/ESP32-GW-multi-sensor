# v7.3.x Build and Regression Test Checklist

This checklist is designed for **step-by-step development** of the ESP32 Multi-Sensor BLE Gateway dashboard/firmware codebase.

It is split into:
- tests I would run on **every step/build**,
- tests I would run on **release candidates**,
- tests I would **defer to the user**,
- and **cross-file consistency checks** specifically meant to catch include/version drift such as:
  - `sensor_history_multi-*.h` still including `dashboard-v7.2.5.h`
  - YAML also including `dashboard-v7.3.1-phase0.h`

---

## How to use this checklist

- Mark an item only when it was actually verified.
- Treat any unchecked **blocker** item as a build stop.
- Run the "Cross-file consistency" section **before** flashing.
- Run the "ESP-served verification" section **after** flashing.

---

## 1) Build blockers — run on every change

### 1.1 Syntax and generation
- [ ] **Dashboard HTML parses cleanly.**  
  Explanation: catches malformed tags, broken `<script>` blocks, accidental truncation, or invalid inline markup before header generation.

- [ ] **Dashboard JavaScript loads without startup errors.**  
  Explanation: catches immediate runtime failures such as missing braces, undefined globals at boot, or broken function declarations.

- [ ] **Header generation completes successfully.**  
  Explanation: confirms the HTML-to-header packaging step still works and the embedded dashboard artifact can actually be produced.

- [ ] **Generated dashboard header is refreshed after the latest HTML change.**  
  Explanation: catches the common mistake where HTML was edited but the `.h` file still contains an older embedded payload.

### 1.2 Cross-file consistency and include/version drift
- [ ] **YAML include list matches the intended dashboard version.**  
  Explanation: catches cases where ESPHome still includes an old dashboard/header file after a rename or phase bump.

- [ ] **No header file hard-includes a different dashboard generation than the YAML includes.**  
  Explanation: catches failures like: `sensor_history_multi-*.h` still including `dashboard-v7.2.5.h` while YAML includes `dashboard-v7.3.1-phase0.h`.

- [ ] **All transitive includes resolve to a single dashboard version family.**  
  Explanation: catches mixed include trees such as one path pulling `v7.2.5` and another pulling `v7.3.x`, which can cause duplicate definitions, wrong symbols, or stale embedded content.

- [ ] **No obsolete dashboard/header files remain referenced anywhere in YAML, shell scripts, or C/C++ headers.**  
  Explanation: catches stale references left in comments, copy-pasted include blocks, helper headers, or generator scripts.

- [ ] **Generator script target filename matches the dashboard version currently under development.**  
  Explanation: catches cases where the script still regenerates an older `.h` filename than the one firmware expects.

- [ ] **Embedded asset source-of-truth is explicit.**  
  Explanation: confirms whether `.html` is authoritative and `.js` is review-only, so the team does not edit the wrong file and create silent drift.

- [ ] **Version strings are aligned across HTML, JS comments, header banner/comments, changelog, and documentation.**  
  Explanation: catches misleading “looks like v7.3.1 but still says v7.2.5 somewhere” situations that make debugging much harder.

- [ ] **Only one active dashboard header is intended to be compiled into firmware.**  
  Explanation: catches accidental coexistence of multiple dashboard payloads, duplicate route handlers, or build ambiguity around which embedded page is actually served.

### 1.3 Compile/build integrity
- [ ] **ESPHome build succeeds with no missing include errors.**  
  Explanation: catches broken include paths, renamed files not reflected in YAML, and missing generated assets.

- [ ] **ESPHome build succeeds with no duplicate symbol / multiple definition errors.**  
  Explanation: catches cases where two dashboard versions or duplicated route handlers are compiled together.

- [ ] **Partition CSV, includes, and code assumptions are mutually consistent.**  
  Explanation: catches mismatches between declared storage layout and code/docs that assume a different partition arrangement.

- [ ] **No new compiler warnings appear in modified areas.**  
  Explanation: warnings are often the first sign of version drift, incorrect function signatures, or dead code after refactors.

## 2) Local dashboard smoke tests — run on every UI change

- [ ] **Dashboard opens from local file mode with configured fallback host.**  
  Explanation: confirms the HTML can still be tested without flashing and that the fallback-host workflow remains usable.

- [ ] **App namespace initializes correctly.**  
  Explanation: confirms `App.Config`, `App.State`, `App.Util`, `App.API`, `App.Transport`, `App.Render`, `App.Charts`, `App.Boot`, and `App.Features` exist.

- [ ] **No “connecting forever” regression on startup.**  
  Explanation: this is a historically high-risk failure mode and should be treated as a build stopper.

- [ ] **Hosted/SSE selection logic still behaves as expected.**  
  Explanation: confirms empty host = same-origin hosted mode and HTTP fallback still chooses SSE.

- [ ] **HTTPS fallback still chooses polling.**  
  Explanation: confirms Cloudflare / HTTPS access paths do not silently break by trying to use the wrong transport mode.

- [ ] **Manifest load succeeds when `/sensors.json` is available.**  
  Explanation: confirms sensor definitions still come from the live manifest when available.

- [ ] **Fallback sensor metadata still works when manifest is unavailable.**  
  Explanation: prevents total dashboard failure when the manifest endpoint is missing or temporarily unavailable.

- [ ] **Core sections render even before live data arrives.**  
  Explanation: confirms placeholder UI and layout still render instead of blanking the page.

## 3) Plugin and modularity safety tests

- [ ] **A plugin can register without breaking core boot.**  
  Explanation: confirms the plugin bus is usable and not coupled too tightly to boot order.

- [ ] **A plugin throwing in `onBoot` does not blank the UI.**  
  Explanation: validates the intended non-fatal isolation behavior.

- [ ] **A plugin throwing in `onManifest` does not stop manifest handling.**  
  Explanation: confirms one feature cannot break sensor discovery.

- [ ] **A plugin throwing in `onStateUpdate` does not stop incoming live updates.**  
  Explanation: confirms runtime updates stay robust even if one extension misbehaves.

- [ ] **A plugin throwing in `onThemeChange` does not break theme switching globally.**  
  Explanation: important because theme-related bugs already affected chart readability.

- [ ] **A plugin throwing in `onRangeChange` does not break history range switching.**  
  Explanation: confirms one history-related feature cannot take down chart navigation.

- [ ] **A plugin throwing in `onChartsReady` does not block chart initialization for the rest of the dashboard.**  
  Explanation: validates the safety claim behind the plugin architecture.

---

## 4) Theme and rendering tests

- [ ] **Light mode is readable on first load.**  
  Explanation: catches theme initialization bugs where chart colors or text are set only for dark mode.

- [ ] **Dark mode is readable on first load.**  
  Explanation: confirms theme defaults do not leave text, borders, or charts invisible.

- [ ] **Switching light → dark updates all chart legends correctly.**  
  Explanation: catches canvas text/legend colors not being recomputed during theme changes.

- [ ] **Switching dark → light updates all chart legends correctly.**  
  Explanation: catches the inverse case and helps detect stale chart option objects.

- [ ] **Axes, tick labels, grid lines, and tooltip text remain visible after theme toggles.**  
  Explanation: this is the broader class of theme bugs that includes invisible telemetry legend cases.

- [ ] **Theme switch does not require Ctrl+F5 to correct chart rendering.**  
  Explanation: catches exactly the class of bug where runtime re-theme logic is incomplete but full reload masks it.

- [ ] **Theme preferences persist correctly if persistence is intended.**  
  Explanation: verifies localStorage-based theme behavior if used.

## 5) Sensor card and live data tests

- [ ] **All configured sensors render cards.**  
  Explanation: confirms the card builder/template logic stays aligned with manifest data.

- [ ] **Live temperature updates populate correctly.**  
  Explanation: confirms SSE/polling state events still map to the correct DOM fields and charts.

- [ ] **Live humidity updates populate correctly.**  
  Explanation: same purpose as temperature coverage for humidity-specific mapping.

- [ ] **Dew point updates when temp/humidity changes.**  
  Explanation: catches broken derived-value recomputation logic.

- [ ] **Comfort classification updates and colors remain semantically correct.**  
  Explanation: preserves the corrected cold/cool/neutral/hot color semantics.

- [ ] **RSSI updates populate correctly.**  
  Explanation: confirms signal strength mapping still works and sensor card decorations remain accurate.

- [ ] **Last-seen/staleness indicators transition correctly.**  
  Explanation: verifies warning and critical stale-state behavior still works over time.

- [ ] **Min/Max toggle still works for each sensor card.**  
  Explanation: confirms per-sensor UI state did not regress during rendering refactors.

## 6) Chart behavior tests

- [ ] **Real-time temperature chart initializes correctly.**  
  Explanation: catches chart-construction failures, missing datasets, or broken axis config.

- [ ] **Real-time humidity chart initializes correctly.**  
  Explanation: same purpose for humidity chart path.

- [ ] **Telemetry chart initializes correctly.**  
  Explanation: important because telemetry has already shown theme-specific visibility bugs.

- [ ] **Incoming data appends to real-time charts without errors.**  
  Explanation: confirms datasets accept new points and no update path is broken.

- [ ] **No-data placeholders disappear when chart data becomes available.**  
  Explanation: verifies correct transition from waiting state to active chart state.

- [ ] **Legend click show/hide behavior still works.**  
  Explanation: validates interactive Chart.js behavior after refactors.

- [ ] **History charts load retained data successfully.**  
  Explanation: confirms `/history/<sensor>/temp` and `/history/<sensor>/hum` integration still works.

- [ ] **24h / 7d / 30d / 45d buttons change visible history correctly.**  
  Explanation: catches range-filter bugs and history-store slicing errors.

- [ ] **Refresh action reloads history without requiring page reload.**  
  Explanation: verifies active re-fetch and redraw behavior.

- [ ] **History charts handle empty or partial data gracefully.**  
  Explanation: prevents blank or broken charts when some sensors have gaps.

## 7) Export tests

- [ ] **Single-sensor export still downloads successfully.**  
  Explanation: protects the existing export baseline.

- [ ] **Merged export still downloads successfully.**  
  Explanation: protects the multi-sensor export path already considered part of the stable baseline.

- [ ] **Export headers are deterministic and in the intended order.**  
  Explanation: catches schema drift that would later break import compatibility.

- [ ] **Export rows are sorted ascending by timestamp.**  
  Explanation: preserves the normalization rule introduced to handle out-of-order endpoint data.

- [ ] **Duplicate timestamps normalize with last-value-wins behavior.**  
  Explanation: protects the documented canonicalization logic needed for future import.

- [ ] **Gateway metadata columns are present when expected.**  
  Explanation: confirms `gateway_host`, `gateway_ip`, `timestamp`, and `datetime_utc` remain intact.

- [ ] **Sensor prefix / slug generation is stable.**  
  Explanation: important because export and future import must share identical schema-helper behavior.

- [ ] **Export still works when one sensor has sparse or missing data.**  
  Explanation: validates outer-join behavior and blank-cell handling in merged exports.

## 8) Import-related tests — enable once import exists

- [ ] **Browser-side schema detection accepts only supported gateway export formats.**  
  Explanation: protects against arbitrary CSV ingestion beyond intended scope.

- [ ] **Browser-side validation rejects malformed headers, wrong schema version, and oversized files.**  
  Explanation: catches bad input early for usability and safety.

- [ ] **Timestamp validation rejects impossible/far-future/badly formatted values.**  
  Explanation: prevents garbage time-series data from being written.

- [ ] **Temperature and humidity validation enforce plausible numeric bounds.**  
  Explanation: protects retained history from corrupt physical readings.

- [ ] **Duplicate rows normalize according to the chosen policy.**  
  Explanation: ensures import behavior matches documented conflict rules.

- [ ] **Validation failure does not trigger destructive erase.**  
  Explanation: this is a critical safety guarantee for replace-only import.

- [ ] **Firmware-side validation rejects malformed payloads even if browser validation was bypassed.**  
  Explanation: enforces the required second validation layer.

- [ ] **Replace-and-import succeeds end-to-end on a valid file.**  
  Explanation: confirms the happy path actually restores retained history.

- [ ] **Storage stats and retained history refresh after successful import.**  
  Explanation: confirms the UI reflects the new on-device state immediately.

## 10) ESP-served verification — run after flashing

- [ ] **The ESP-served dashboard matches the intended version when downloaded from `/dashboard-download`.**  
  Explanation: this is the authoritative check that the firmware is serving the artifact you think it is serving.

- [ ] **The ESP-served page behaves the same as the tested local artifact for core flows.**  
  Explanation: catches differences between local-file testing and actual embedded deployment.

- [ ] **The LAN-served page connects and updates correctly.**  
  Explanation: validates the main local operating path.

- [ ] **The Cloudflare-served page connects and updates correctly if that deployment path is used.**  
  Explanation: validates production-like remote access behavior.

- [ ] **Cloudflare/browser cache does not serve an older dashboard build after deployment.**  
  Explanation: catches stale-cache confusion that previously made the hosted UI appear older than local code.

- [ ] **Device-info, storage, charts, and sensor data all populate on the served page.**  
  Explanation: confirms the real embedded runtime remains healthy end-to-end.

## 11) Long-session and resilience tests

- [ ] **Dashboard remains stable during extended open session.**  
  Explanation: catches timer leaks, chart growth problems, and reconnection issues that short tests miss.

- [ ] **Network interruption causes recoverable reconnect behavior.**  
  Explanation: validates resilience for both SSE and polling paths.

- [ ] **No progressive slowdown or runaway memory behavior is observed during long session.**  
  Explanation: important for chart-heavy dashboards that append data continuously.

- [ ] **Staleness, telemetry, and chart updates remain correct after reconnect.**  
  Explanation: confirms resumed runtime still computes and renders correctly.

## 12) Tests I would defer to the user

These are not because they are unimportant; they are deferred because they depend on your real environment, operational expectations, and destructive-action approval.

- [ ] **Final UX acceptance on the real device and real network.**  
  Explanation: only the user can decide whether layout, readability, and interaction feel “right” for everyday use.

- [ ] **Final approval of Cloudflare deployment behavior in the actual production path.**  
  Explanation: cache rules, domain routing, and propagation can be environment-specific.

- [ ] **Approval to run destructive actions against real retained history.**  
  Explanation: reboot/delete/import replacement flows may be technically valid, but final consent should remain with the user.

- [ ] **Validation that real sensor behavior matches physical expectations in the environment.**  
  Explanation: only the user can confirm whether timing, signal, and readings align with the real placement and use case.

- [ ] **Acceptance of import policy for real historical data.**  
  Explanation: even if replace-only import is safe technically, only the user should approve that workflow for valuable retained history.

## 13) Similar version-drift cases this checklist is meant to catch

- [ ] **History header includes old dashboard header while YAML includes new dashboard header.**  
  Explanation: direct example of the mismatch that can fail builds or serve the wrong dashboard.

- [ ] **YAML includes new history header, but history header still references old helper/header names internally.**  
  Explanation: catches partial renames that appear correct at top level but fail deeper in the include chain.

- [ ] **Generator script writes `dashboard-v7.3.0-skeleton.h`, but YAML expects `dashboard-v7.3.1-phase0.h`.**  
  Explanation: catches phase/version naming drift between tooling and firmware config.

- [ ] **Standalone `.js` was edited, but embedded `.html` still contains old inline JS.**  
  Explanation: catches the classic “review file changed, source-of-truth file did not” mistake.

- [ ] **Version string updated in comments/docs, but actual route payload remains old.**  
  Explanation: catches false confidence from comments when the served artifact was never regenerated/flashed.

- [ ] **Two dashboard headers with similar names both remain in the repo and one stale file is still referenced.**  
  Explanation: catches accidental compilation against a legacy copy rather than the intended active file.

- [ ] **Docs/changelog mention a fix, but `/dashboard-download` proves the device still serves a pre-fix artifact.**  
  Explanation: catches deployment mismatch rather than source-code mismatch.

- [ ] **One file renamed to `v7.3.x`, but hard-coded strings, links, or route assumptions still reflect `v7.2.x`.**  
  Explanation: catches incomplete migration after phase bumps.

## 14) Recommended pass/fail policy

### Blocker — fail the step immediately
- Any include/version drift.
- Any ESPHome compile failure.
- Any startup blank-page / connecting-forever regression.
- Any mismatch between intended artifact and `/dashboard-download` after flashing.
- Any theme bug that makes charts unreadable after toggle.

### Major — do not release, but local iteration can continue
- One browser failing a non-core interaction.
- Export schema drift.
- Partial chart/history rendering problems.
- Auth modal regressions without security bypass.

### Minor — track and fix, but not necessarily step-blocking
- Cosmetic spacing/alignment issues.
- Non-critical log wording.
- Slightly inconsistent hint text.

---

## 15) Minimum quick gate for every code step

If time is limited, I would still require this minimum set before calling a step “good”:

- [ ] Header regenerates successfully.
- [ ] YAML/includes/header chain point to one dashboard version only.
- [ ] ESPHome compiles.
- [ ] Dashboard opens without console errors.
- [ ] No connecting-forever regression.
- [ ] Theme toggle works without invisible chart text.
- [ ] Sensor manifest and basic live data load.
- [ ] `/dashboard-download` matches intended version after flash.

---

## 16) Best-practice note

For this project, **build quality is not only “does ESPHome compile?”** It is also:
- does the generated embedded dashboard match the intended source,
- does the device actually serve that artifact,
- and does it still behave correctly across the known high-risk surfaces: transport/init, theme, charts, export, browser-specific inputs, and cached remote access.
