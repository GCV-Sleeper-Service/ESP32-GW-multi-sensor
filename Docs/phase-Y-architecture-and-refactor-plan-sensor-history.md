## 0. Architecture Decisions (Resolved)

These decisions were open or ambiguous in the Phase X carryover context (`Docs/phase-X-context-for-phase-Y.md` §7). They are resolved here and apply to all Phase Y steps.

| # | Decision area | Decision | Rationale |
|---|---|---|---|
| D1 | Assembly strategy | **Option B — assembled artifact.** `dashboard/sensor_history_multi.h` remains the committed, assembled output. Fragments are the hand-edited sources; a new assembly script concatenates them. | Zero generator changes, zero YAML changes, zero preflight impact, portable identity gate (SHA-256 of text). Direct analogue to Phase X `bundle-dashboard.sh`. |
| D2 | Fragment directory | **`firmware/core/`** for hand-maintained fragments. | Firmware code does not belong under `dashboard/`. Clean long-term home for Phase 7/8 extensions. |
| D3 | Generator ownership | **Generator unchanged.** `render_sensor_config.py` continues writing into `dashboard/sensor_history_multi.h` at its existing `HEADER_PATH`. Fragment `data-model.h` contains marker delimiter stubs only. | Zero generator migration risk. The assembled file is the generator's actual target. |
| D4 | Identity gate | **SHA-256 of assembled text.** `assemble-sensor-history.sh --check` compares assembled output to committed file. No build toolchain required. | Portable, deterministic, directly enforces the "structural only" rule. |
| D5 | Dispatcher strategy | **Keep `HistoryWebHandler::canHandle()` and `handleRequest()` in one contiguous class.** Do not split the class body across fragments. | Syntactically incomplete C++ fragments break IDE tooling, static analysis, and coding-agent ergonomics. One `web-handler.h` preserving class integrity is the correct boundary. |
| D6 | Aggregator two-island | **Resolved by assembly concatenation order.** Under Option B, both islands (`aggregator-runtime.h` and the aggregator endpoint cluster inside `web-handler.h`) are re-joined in the assembled file before the compiler sees the code. The two-island problem is a source-organisation concern, not a compilation concern. |
| D7 | Phase Y before Phase 7 | **Phase Y lands before Phase 7.** Phase Y fragments make the NVS persistence module independently loadable, reducing Phase 7 task context by 70%+. |
| D8 | YAML `includes:` | **Unchanged.** YAML continues to include only `dashboard/sensor_history_multi.h`. No fragment files appear in YAML. |

### 1.2 Why the Current Structure Is Expensive

Any firmware task forces a coding agent to load the full 4,325-line file (~27K–32K tokens for the file alone). Adding YAML, generator, lessons, and test context pushes a typical task to 47K–52K tokens before the agent writes a single line of code.

### 1.3 Context-Window Cost Estimate

| Task type | Current tokens | After Phase Y |
|---|---:|---:|
| Fix history-chart endpoint | ~50K | ~12K |
| Add NVS helper function | ~33K | ~8K |
| Ping adapter tuning | ~27K | ~5K |
| Aggregator poll task change | ~33K | ~9K |
| New management endpoint | ~50K | ~14K |

**Target:** every routine task fits under 15K tokens. Reduction factor: 3×–5×.

**Verification sum:** 95 + 460 + 614 + 50 + 168 + 891 + 2,006 + 41 = **4,325** ✓

### 2.4 Module Boundary Justification

Each boundary aligns with the v2 inventory §9 contiguous/scattered analysis:

| Boundary | Seam | Justification |
|----------|------|--------------|
| 1↔2 at line 96 | `TAG` definition | Starts the runtime symbol space; everything before is pure preprocessor/includes |
| 2↔3 at line 556 | `struct HistoryMeta` | Begins the NVS persistence model; everything before is runtime data model + generated topology |
| 3↔4 at line 1170 | `reboot_task_` | First deferred-task function; persistence core is complete above |
| 4↔5 at line 1220 | `#ifdef PING_DEVICE_INDEX` | Clean compile-guard boundary |
| 5↔6 at line 1388 | `#if AGGREGATOR_ENABLED` | Clean compile-guard boundary (aggregator runtime island 1) |
| 6↔7 at line 2279 | `class HistoryWebHandler` | Class declaration; everything before is top-level functions |
| 7↔8 at line 4285 | Post-class `};` | Registration function is standalone after class close |

### 2.5 Why a Single `web-handler.h` (2,006 lines)

Splitting `HistoryWebHandler` into multiple fragments (e.g., core/local/aggregator) would create syntactically incomplete C++ files — fragment N opens a class that fragment N+2 closes. This breaks IDE syntax highlighting, clangd, static analysis, and coding-agent file-scoped tooling. The 2,006-line fragment is large (~14K tokens) but represents a 52% reduction from the monolith baseline and preserves syntactic completeness. Further splitting is a future consideration after Phase 7 if the class grows further.

**Assembly script specification:**

```bash
#!/usr/bin/env bash
# assemble-sensor-history.sh — Phase Y firmware module assembler
# Concatenates firmware/core/*.h fragments → dashboard/sensor_history_multi.h
#
# Usage:
#   assemble-sensor-history.sh --write     Assemble fragments → OUTPUT
#   assemble-sensor-history.sh --check     Compare assembly to committed file; exit 0/1
#   assemble-sensor-history.sh --list      Print fragment manifest
#   assemble-sensor-history.sh --dry-run   Print what --write would do

OUTPUT="dashboard/sensor_history_multi.h"
MODULES=(
  "firmware/core/config.h"
  "firmware/core/data-model.h"
  "firmware/core/nvs-persistence.h"
  "firmware/core/deferred-management.h"
  "firmware/core/ping-adapter.h"
  "firmware/core/aggregator-runtime.h"
  "firmware/core/web-handler.h"
  "firmware/core/registration.h"
)

case "${1:-}" in
  --write)
    cat "${MODULES[@]}" > "$OUTPUT"
    echo "Assembled ${#MODULES[@]} fragments → $OUTPUT ($(wc -l < "$OUTPUT") lines)"
    ;;
  --check)
    # Generator-aware comparison: strip content between SENSOR_MANIFEST marker
    # pairs before comparing, because render_sensor_config.py writes generated
    # content into the committed file that does not exist in fragment stubs.
    strip_generated() {
      sed '/SENSOR_MANIFEST:HEADER_BEGIN/,/SENSOR_MANIFEST:HEADER_END/{ /SENSOR_MANIFEST:HEADER_BEGIN/!{ /SENSOR_MANIFEST:HEADER_END/!d; }; }' \
        | sed '/SENSOR_MANIFEST:ENTITY_BEGIN/,/SENSOR_MANIFEST:ENTITY_END/{ /SENSOR_MANIFEST:ENTITY_BEGIN/!{ /SENSOR_MANIFEST:ENTITY_END/!d; }; }'
    }
    ASSEMBLED=$(cat "${MODULES[@]}" | strip_generated | sha256sum | cut -d' ' -f1)
    COMMITTED=$(strip_generated < "$OUTPUT" | sha256sum | cut -d' ' -f1)
    if [[ "$ASSEMBLED" == "$COMMITTED" ]]; then
      echo "PASS: Assembly identity verified (non-generated regions match: $ASSEMBLED)"
      exit 0
    else
      echo "FAIL: Assembly SHA-256 mismatch (non-generated regions differ)"
      echo "  Assembled: $ASSEMBLED"
      echo "  Committed: $COMMITTED"
      diff <(cat "${MODULES[@]}" | strip_generated) <(strip_generated < "$OUTPUT") | head -20
      exit 1
    fi
    ;;
  --list)
    for m in "${MODULES[@]}"; do
      echo "  $m ($(wc -l < "$m") lines)"
    done
    echo "Total: $(cat "${MODULES[@]}" | wc -l) lines"
    ;;
  --dry-run)
    echo "Would concatenate:"
    for m in "${MODULES[@]}"; do echo "  $m"; done
    echo "→ $OUTPUT"
    ;;
  *) echo "Usage: $0 [--write|--check|--list|--dry-run]"; exit 1 ;;
esac
```

## 4. Build / Generation / Integration Pipeline Changes

### 4.1 Generator Strategy — Unchanged (Option B)

Under Option B, `render_sensor_config.py` is **not modified**. It continues to:
1. Open `dashboard/sensor_history_multi.h` (the assembled artifact)
2. Find `SENSOR_MANIFEST:HEADER_BEGIN` and `SENSOR_MANIFEST:ENTITY_BEGIN`
3. Replace marker block contents with generated sensor topology
4. Write the updated file

This works because `sensor_history_multi.h` remains the committed assembled artifact and the generator operates on the committed file, not on the fragment sources.

### 4.2 Generator/Assembly Sync — The Reverse-Sync Problem

**Problem:** After `render_sensor_config.py --write`, the assembled file contains generated content in the `data-model.h` region that does not exist in the fragment stub file. If `assemble-sensor-history.sh --check` runs after the generator, it will fail because pure concatenation of fragments produces a different SHA-256 than the generator-modified assembled file.

**Resolution: Assembly-aware `--check` mode.**

The assembly script's `--check` mode operates in two phases:

1. **Before generator runs:** `--check` compares pure concatenation to the committed file (must match).
2. **After generator runs:** `--check` compares only the non-generated regions. The script knows which fragment (`data-model.h`) contains generator markers and compares only the delimiter lines, skipping the generated content between `HEADER_BEGIN`/`HEADER_END` and `ENTITY_BEGIN`/`ENTITY_END`.

Alternatively, the pipeline ordering can enforce: **assemble → generator → (no assembly check after generator)**. The final `render_sensor_config.py --check` at the end of the pipeline serves as the generator consistency gate.

**Canonical pipeline order (after v7.6.6.2):**

```
Step 0: bash scripts/assemble-sensor-history.sh --write   ← produces assembled file from fragments
Step 1: bash scripts/bundle-dashboard.sh --write
Step 2: python3 scripts/render_sensor_config.py --write   ← writes generated content into assembled file
Step 3: node tests/fixtures/generate-fixtures.js
Step 4: python3 scripts/render_sensor_config.py --write
Step 5: bash scripts/build-dashboard.sh --write
Step 6: bash scripts/minify-dashboard.sh
Step 7: bash scripts/generate-header.sh
Step 8: python3 scripts/render_sensor_config.py --check   ← verifies generator content is current
```

The assembly `--check` runs in **preflight** (not in the pipeline) to verify that hand-maintained fragment regions match the committed file. This avoids the ordering conflict.

### 4.3 Where Generated Blocks Live

| Block | Fragment source | Assembled artifact | Written by |
|---|---|---|---|
| `SENSOR_MANIFEST:HEADER` | `firmware/core/data-model.h` (delimiter lines only) | `dashboard/sensor_history_multi.h` (full generated content) | `render_sensor_config.py --write` |
| `SENSOR_MANIFEST:ENTITY` | `firmware/core/data-model.h` (delimiter lines only) | `dashboard/sensor_history_multi.h` (full generated content) | `render_sensor_config.py --write` |

```yaml
  - ../dashboard/sensor_history_multi.h
```

No fragment files are added to the YAML. The ESPHome compiler sees only the assembled artifact.
