# v7.3.4.2 Pre-Phase-1 Expert Opinion

This file is carried forward from v7.3.4 for branch continuity. The assessment remains the same because v7.3.4.2 is a startup hotfix on top of the same architectural position rather than a new architecture phase.

---


## Baseline assessed
- code baseline reviewed: **v7.3.3**
- companion references reviewed: prior documentation/development notes, v7.3 goals, import research notes, PE regression checklist/worksheets, GE testing strategy, and the external architecture analysis

## Executive conclusion

**v7.3.3 was a good stabilization baseline, but it was still a wrapped monolith rather than a truly modular dashboard.**

It already had the right direction:
- App namespace and plugin hooks were in place
- dashboard/history were decoupled in YAML include order
- transport/CORS/date-axis regressions had been addressed

But two structural gaps still kept regression risk too high for Import:
1. **shared dashboard state was still easy to stomp directly**
2. **inline HTML handlers still made UI refactors brittle**

That made the next high-value move very clear:
- centralize the primary shared-state writes behind **`App.State`**
- replace inline handlers with centralized **`bindEvents()`**
- keep Import blocked until that gate is in place and validated

## Where v7.3.3 stood before this build

### What was already good
- backend/history path was coherent and should not be broadly rewritten
- packaging discipline was stronger than earlier branches
- plugin isolation via `App.Features.register/emit` was useful and worth keeping
- the project had already learned the right lesson about not casually touching transport/init behavior

### What was still weak
- dashboard modularity was more naming than enforcement
- sensor/event interactions still depended heavily on inline `onclick` wiring
- the most important shared dashboard values (`SENSORS`, range selection, merged history store, chart-ready state) were still easy to mutate without a real control point

## Recommendation before Import

I agreed with the strongest common recommendation across the uploaded reviews:
- **do Phase 1 first**
- keep it narrow
- do not widen scope into Import, custom range, templates, or a build pipeline yet

## What I recommended to change in plan shape

### Keep
- dashboard HTML as the editable source of truth
- decoupled YAML include model
- preflight/static gating before packaging
- user-first, low-risk refactor approach

### Change
- treat **Phase 1** as the real structural gate, not as optional cleanup
- define success as:
  - primary shared-state writes routed through `App.State`
  - inline handlers removed in favor of `bindEvents()` / delegated listeners
- defer Import until this is verified on the real device and in target browsers

## Why this helps the user

This step is not architecture for architecture’s sake.

It directly helps the user because the next planned features — especially Import and later Custom Range — would otherwise be added on top of the same brittle event/state surfaces that caused repeated regressions in earlier branches.

## Risk view before Phase 1

### Low risk to keep as-is
- retained-history backend logic
- storage partition model
- management auth semantics
- transport strategy chosen in v7.3.3

### Higher risk surfaces
- dashboard click/input wiring
- card-generated controls
- range switching + UI event flow
- shared browser-side history state

## Final pre-Phase 1 conclusion

**v7.3.3 should be used as the baseline, but it should not be treated as modularization completed.**

The correct next step was a focused **v7.3.4 Phase 1** build that improves regression resistance without re-architecting the whole dashboard or starting Import work.
