# v7.5.x — Platform Architecture Evolution: Phase 1 Reference

_Version: v7.5.0.1_  
_Date: 2026-03-14_  
_Status: Phase 1 complete and device-validated_

---

## Overview

v7.5.x is the beginning of a multi-phase architecture evolution that transforms the ESP32-C3 gateway from a ThermoPro-specific sensor appliance into a manifest-driven, metadata-aware platform capable of supporting multiple sensor types and multi-gateway aggregation.

The full plan is in `Docs/v7.5-v7.6-architecture-plan.md`. This document covers what has been implemented in Phase 1, the current API surface, and the scope of Phase 2.

---

## What v7.5.x is changing — and why

The v7.4.x codebase was designed around one sensor type (ThermoPro TP357), one data model (temp + hum), and one rendering assumption (climate card). That was the right trade-off to get the project to a robust, well-tested baseline. But it means everything downstream — dashboard rendering, history fetching, future aggregation — needs to know what kind of sensors it is dealing with before it can do anything useful.

v7.5.x introduces a manifest endpoint that makes the gateway self-describing. Instead of the dashboard assuming "there are N sensors, each has temperature and humidity," the dashboard asks the gateway: "what do you have, and how should I display it?" This is the foundation that makes sensor type extensibility and aggregation architecturally possible.

## Phase 1 — What was delivered (v7.5.0.1)

### New firmware endpoint: `GET /api/manifest`

Returns a schema v2 JSON document describing the gateway's sensor configuration and available metrics.

**Example response (current Phase 1 shape):**
```json
{
  "ok": true,
  "schema_version": 2,
  "source": "firmware",
  "version": "7.5.0.1",
  "sensor_count": 3,
  "metrics": [
    {
      "key": "temp",
      "name": "Temperature",
      "unit": "celsius",
      "unit_symbol": "°C",
      "bounds": {"min": -50, "max": 80},
      "history_suffix": "temp"
    },
    {
      "key": "hum",
      "name": "Humidity",
      "unit": "percent",
      "unit_symbol": "%",
      "bounds": {"min": 0, "max": 100},
      "history_suffix": "hum"
    }
  ],
  "sensors": [
    {
      "id": "office",
      "name": "Office",
      "metrics": [
        {"key": "temp", "history": "/history/office/temp"},
        {"key": "hum", "history": "/history/office/hum"}
      ]
    }
  ]
}
```

**Note on schema completeness:** This is a pragmatic Phase 1 manifest. The full v2 schema specified in `Docs/v7.5-v7.6-architecture-plan.md` section 5.2 includes additional fields (`gateway` identity block, `history` retention policy block, per-measurement `class`/`data_type`/`display` hints) that are required for Phase 2 dashboard consumption. Upgrading the response to the full schema is the first Phase 2 task.

### Dashboard manifest-first boot

Dashboard boot sequence is now:
1. `GET /api/manifest` (preferred)
2. `GET /sensors.json` (backward-compatible fallback)
3. `DEFAULT_SENSOR_META` built-in array (final fallback)

The fallback chain ensures the dashboard works with older firmware (that only serves `/sensors.json`) and in fully offline conditions (only built-in defaults).

### Preserved backward compatibility

All existing endpoints remain unchanged:
- `GET /sensors.json` — v1 sensor list
- `GET /api/status` — gateway health, uptime, heap, sensor validity
- `GET /api/storage-stats` — flash/RAM usage and retention data
- `GET /history/{id}/temp` and `/history/{id}/hum` — history streams
- All `/api/import/*` endpoints — CSV import
- `POST /api/reboot`, `POST /api/delete-data` — management actions

### Dashboard status widget fix

Dashboard Free Heap and Uptime now hydrate from `GET /api/status` directly instead of legacy entity-polling paths. This is more reliable and decoupled from ESPHome entity naming conventions.

### Built-in diagnostics restored

`debug.free`, `debug.loop_time`, and `uptime: type: seconds` blocks restored in `firmware/esp32-c3-multi-sensor.yaml`. The ESPHome built-in web page shows all three diagnostics again.

### Generator fixes

Two generator bugs were found and fixed during Phase 1 implementation:

- **Regex replacement crash:** `render_sensor_config.py` now uses lambda-based replacement for all generated content containing backslash sequences.
- **YAML indentation regression:** All YAML marker replacements now route through `apply_yaml_marker_block()` which preserves indentation column context. Generator is confirmed idempotent — running `--write` twice produces no diff.

## Full API surface at v7.5.0.1

| Endpoint | Method | Auth | Description |
|---|---|---|---|
| `/dashboard.html` | GET | None | Embedded dashboard |
| `/dashboard-download` | GET | None | Dashboard as download attachment |
| `/sensors.json` | GET | None | Legacy v1 sensor array `[{id, name}]` |

| `/history/{id}/hum` | GET | None | CSV history stream — humidity |

| `/api/import/begin/single/{id}` | POST | Basic | Begin single-sensor merge import |
| `/api/import/d/{data}` | POST | Basic | Add data points to current import segment |
| `/api/import/w/{data}` | POST | Basic | Add data points and write segment to NVS |
| `/api/import/finish` | POST | Basic | Finalize import and restore RAM |
| `/api/reboot` | POST | Basic | Reboot the device |
| `/api/delete-data` | POST | Basic | Erase persisted history and clear RAM |

## Phase 2 — Scope

Phase 2 is "Dashboard Consumes v2 Manifest." The goal is to make the dashboard render from manifest metadata rather than hardcoded ThermoPro assumptions. ThermoPro output must remain pixel-identical — Phase 2 is a refactor, not a feature change.

### Phase 2 task sequence

**Step 1 (prerequisite):** Upgrade `/api/manifest` to full v2 schema.

Add to the firmware response:
```json
{
  "gateway": {
    "id": "gw-bothell-01",
    "name": "Bothell Main Gateway",
    "role": "satellite",
    "hardware": "esp32-c3",
    "firmware_version": "7.5.x",
    "api_version": "v2"
  },
  "history": {
    "backend": "local_flash",
    "retention_hours": 1080,
    "ram_window_hours": 24,
    "sample_interval_seconds": 900
  },
  "devices": [
    {
      "id": "office",
      "name": "Office",
      "category": "environmental",
      "adapter": "thermopro_ble",
      "measurements": [
        {"key": "temp_c", "label": "Temperature", "unit": "°C", "class": "analog", "history": true, "display": {"card": true, "chart": true}},
        {"key": "humidity_pct", "label": "Humidity", "unit": "%", "class": "analog", "history": true, "display": {"card": true, "chart": true}},
        {"key": "battery_pct", "label": "Battery", "unit": "%", "class": "metadata", "history": false, "display": {"card": true, "chart": false}},
        {"key": "rssi_dbm", "label": "RSSI", "unit": "dBm", "class": "metadata", "history": false, "display": {"card": true, "chart": false}}
      ]
    }
  ]
}
```

**Steps 2–9:** Dashboard refactor — see `Docs/esp32-gateway-fresh-start-handoff.md` section 7 for the complete Phase 2 task list.

### What Phase 2 changes

| Component | Change |
|---|---|
| `sensor_history_multi.h` | Upgrade `/api/manifest` response to full v2 schema |
| `dashboard.js` | Extend `normalizeManifestSensors()` to capture `category`, `measurements[].class`, `measurements[].display` |
| `dashboard.js` | Introduce `CARD_RENDERERS` registry |
| `dashboard.js` | Refactor `buildSensorCards()` → `buildDeviceCards()` with registry dispatch |
| `dashboard.js` | Add `_default` fallback renderer |
| `dashboard.js` | Add `METRIC_FORMATTERS` registry |
| `dashboard.js` | Refactor `fetchSensorHistoryRows()` to be manifest-driven |
| `tests/fixtures/manifest.json` | Align to full v2 schema |
| `tests/mock-server/server.js` | Serve full v2 manifest fixture |
| `tests/browser/` | New tests: manifest-driven rendering, fallback behavior |

### What Phase 2 does NOT change

- ThermoPro rendering — must be pixel-identical to current behavior (regression gate)
- The C++ data model (`SensorSlot`) — that is Phase 3
- Flash persistence format — unchanged through all of v7.5.x
- All existing API endpoints — no removals, no renames

### Phase 2 risk profile

**Medium.** The card rendering refactor touches many functions in `dashboard.js`. The 28-test Playwright regression suite is the primary safety net. The firmware changes for the full v2 schema are additive (adding fields to an existing response) and lower risk than the dashboard refactor.
