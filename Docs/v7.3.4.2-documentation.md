This build is a **targeted dashboard hotfix** on top of the repaired 7.3.4.x Phase 1 structure.

Primary goals:
- fix `Export All` failing with `HTTP 502`
- keep chart point markers synchronized when a sensor color is changed
- reduce 15-minute chart marker size to match the real-time charts

## Changelog

### Fixed

#### 1. `Export All` now fetches retained history sequentially
- **Symptom:** `Export All` failed with `Export failed: HTTP 502`, while single-sensor export still worked.
- **Cause:** the merged export path fanned out all sensor history requests at once. For three sensors that becomes six history endpoint fetches at the same time, plus gateway metadata fetch, which is materially heavier than individual export.
- **Fix used:** replaced the parallel `Promise.all(SENSORS.map(fetchSensorHistoryRows))` pattern with a sequential helper that fetches each sensor in order.
- **Why this was done this way:** it addresses the failure where it actually happens without touching firmware/history endpoints.
- **User benefit:** `Export All` should stop tripping request-burst failures on the ESP / reverse-proxy / tunnel path.

#### 2. Sensor recolor now updates chart point markers as well as the line
- **Symptom:** changing a sensor color updated the line but the chart dots stayed in the old color.
- **Cause:** recolor logic only updated `borderColor` and fill `backgroundColor`; it did not update point-specific marker colors.
- **Fix used:** recolor now also updates `pointBackgroundColor`, `pointBorderColor`, `pointHoverBackgroundColor`, and `pointHoverBorderColor`.
- **Why this was done this way:** it is the lowest-risk correction because the existing chart structure stays the same.
- **User benefit:** the dashboard no longer shows mismatched sensor identity between lines and markers.

#### 3. 15-minute chart markers now match the real-time charts
- **Symptom:** 15-minute charts showed noticeably larger circles than the real-time charts.
- **Cause:** dataset factory used larger average-chart marker settings.
- **Fix used:** aligned average-chart marker radius and hover radius with the real-time charts.
- **User benefit:** the dashboard looks more consistent and less visually heavy.

#### 4. Theme toggle now forces a chart redraw
- **Symptom:** after switching between dark and light mode, certain chart-rendered elements could become visually wrong or appear missing until the user performed `Ctrl+F5`.
- **Cause:** CSS variables changed immediately, but the chart canvas did not always fully repaint all runtime-rendered elements from the toggle path.
- **Fix used:** after theme change, the dashboard now reapplies chart theme settings and forces resize/render/update passes across all charts.
- **Why this was done this way:** it avoids destroying/recreating chart instances and keeps the fix narrow.
- **User benefit:** users should no longer need manual hard refreshes after toggling theme.

### Not changed
- transport selection strategy
- retained-history data model
- management auth behavior
- partition layout content
- Phase 1 dashboard structure (`bindEvents()`, `App.State`, no inline handlers)
- Import feature scope (still intentionally deferred)

## Lessons learned and prevention

1. **Burstiness matters on embedded/export paths.** A feature can work per sensor and still fail when the multi-sensor path multiplies concurrent requests.
2. **Dataset recolor needs point properties too.** Updating only line/fill colors is incomplete in Chart.js-style datasets.
3. **Visual consistency should be explicit.** If real-time and 15-minute charts should look the same, marker-size settings should be aligned deliberately rather than assumed.
4. **Theme changes need a runtime repaint path.** CSS-variable updates alone are not always enough for canvas-rendered content.
5. **Future dashboard preflight should keep static guards for all four hotfix areas.** This is low-complexity protection that fits the project rules.

## Third-party opinion review

A separate diagnosis file was uploaded with four practical recommendations for the next hotfix:
1. serialize `Export All`
2. update point-marker colors during sensor recolor
3. reduce 15-minute marker size
4. keep the scope narrow and avoid backend churn unless the sequential export still fails

### My view on that opinion
- **I agree with items 1-4.** They correctly identify the lowest-risk repair path for the observed regressions.
- I added one extra fix on top of that analysis: a **theme-toggle redraw pass** to address the user’s additional report that some chart-rendered elements only recover after `Ctrl+F5`.
- I do **not** think this step should widen into transport, backend persistence, or Import work.
