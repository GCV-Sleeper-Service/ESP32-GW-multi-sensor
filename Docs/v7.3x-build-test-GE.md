# Comprehensive Testing Strategy: ESP32-C3 Gateway v7.3.x

## Part 1: Developer Tests (Automated & Pre-Compile Checks)
*These tests ensure the logic is sound, files are synced, and memory is managed safely. These can be automated via scripts or CI/CD pipelines.*

### 1.1 Pre-Flight Configuration & Dependency Checks (Configuration Drift)
- [ ] **Cross-File Version Consistency:** Run a regex script to verify that the version numbers (e.g., `v7.3.1-phase0`) match exactly across:
    - The YAML `includes:` block.
    - The internal C++ `#include "dashboard-v7.x.x.h"` directives.
    - The bash script input/output targets (`generate-header-v7.x.x.sh`).
- [ ] **Artifact Generation Verification:** Assert that the `generate-header-*.sh` script has been executed successfully and that the resulting `.h` file exists *before* triggering the ESPHome build.
- [ ] **Partition Table Alignment:** Verify that the partition CSV file specified in the YAML exists on disk, and that the `HISTORY_PARTITION_LABEL` macro in the C++ code exactly matches the label inside the CSV.
- [ ] **YAML Configuration Validation:** Run `esphome config esp32-c3-multi-v7.3.x.yaml` to validate YAML syntax and ensure all required component dependencies (like `esp32_ble_tracker` for `ble_rssi`) are present before triggering the heavy C++ compiler.

### 1.2 Static Analysis & Linting
- [ ] **C++ Memory & Bounds Checking:** Run `clang-tidy` or `cppcheck` on `sensor_history_multi-v7.3.x.h` to scan for memory leaks (e.g., ensuring `snapshot` is deleted), null pointer dereferences, and `snprintf` buffer overflows.
- [ ] **JavaScript/Frontend Linting:** Run ESLint on `core.js` to prevent global variable leakage and ensure `try/catch` blocks are properly scoped within the `App.Features` plugin manager.
- [ ] **HTML Structure Validation:** Validate the structural integrity of `index.html` to ensure no orphaned tags or duplicate IDs exist before it is converted into a C++ string literal.

### 1.3 C++ Unit Testing (Core Logic Isolated from Hardware)
- [ ] **HistoryBuffer Rollover:** Push 100 mock data points into a buffer with a capacity of 96. Assert that `head_` rolls over correctly, oldest points are overwritten, and `count()` equals exactly 96.
- [ ] **Averaging & Unit Math:** Feed specific dummy temperature values into `add_temp()` and assert that `compute_and_format()` yields the exact correct average and handles Celsius-to-Fahrenheit math perfectly.
- [ ] **Gap Handling:** Advance the mock epoch by 15 minutes without feeding data to ensure `NAN` gaps are automatically inserted.
- [ ] **Auth Lockout Logic:** Feed invalid base64 strings into `authenticate_management_` and assert that the 900ms delay and 30-second lockout trigger exactly on the third failed attempt.

### 1.4 JavaScript/Frontend Unit Testing
- [ ] **CSV Data Parsing:** Pass mock CSV strings into `parseHistoryMetricLines` and assert it handles missing data, malformed lines, and `NaN` values gracefully without crashing the UI.
- [ ] **Meteorological Math:** Unit test `calcDewPoint` and `calcComfortEstimate` against known baseline meteorological values.
- [ ] **Plugin Sandbox Resilience:** Register a mock plugin in `App.Features` that intentionally throws a runtime error. Assert that `App.Features.emit` catches it and the core rendering loop continues uninterrupted.

## Part 2: User Tests (Hardware & Environmental Checks)
*These tests rely entirely on physical realities, network conditions, and actual hardware. They must be conducted manually.*

### 2.1 Hardware Deployment & Connectivity
- [ ] **Firmware Flashing:** Does the firmware flash successfully via USB/OTA to the specific ESP32-C3 SuperMini hardware without entering a boot loop?
- [ ] **BLE Sensor Range & Reliability:** Do the ThermoPro TP357 sensors establish a connection? Verify the RSSI signal bars in the dashboard to ensure advertisements penetrate walls adequately (Office vs. Outside).
- [ ] **WiFi Stability:** Does the gateway maintain a stable connection to the router under real-world interference, or does it drop off the network after a 24-hour period?

### 2.2 Physical NVS & Power-Loss Recovery
- [ ] **The "Plug Pull" Test:** Let the gateway run for >1 hour (ensuring at least one segment is written to flash). Physically unplug the power, plug it back in, and verify the dashboard successfully restores the historical data from the custom NVS partition.
- [ ] **Storage Partition Allocation:** Open the "History Storage" panel on the dashboard and manually confirm the partition sizes match the custom `esp32-c3-multi-v7.3.x-partitions.csv` specifications.
- [ ] **Manual Data Deletion:** Trigger the "Delete Data" management action from the UI and verify that both the RAM buffer is cleared and the NVS partition is successfully erased.

### 2.3 Long-Term Endurance (Soak Testing)
- [ ] **Heap Fragmentation Monitoring:** Run the device for 7 consecutive days. Monitor the "Free Heap" telemetry chart to ensure the memory stays stable and does not slowly leak until a crash occurs.
- [ ] **45-Day NVS Rollover:** (Long Term) Observe the system as it approaches the partition limit. Verify that the circular buffer correctly overwrites segment `000` once the partition is full without corrupting the NVS namespace.

### 2.4 Cross-Device Client Rendering
- [ ] **Mobile Responsive UI:** Open the dashboard on a mobile browser. Verify that the CSS layout adapts correctly and that the charts resize without breaking the layout.
- [ ] **Chart Performance Under Load:** Let the system accumulate 720 points (or load full history). Verify that navigating the dashboard, toggling sensors, and switching light/dark themes does not cause significant browser lag.
