## Critical Rules for Firmware Work

### ESPHome POST Content Type Constraint

ESPHome only consumes POST body bytes for `application/x-www-form-urlencoded` and `multipart/form-data`. JSON bodies are not consumed — socket state is corrupted.

**All curl POST commands in prompts:**
```bash
curl -v -X POST -d 'a=1' -u USER:PASS http://DEVICE/api/endpoint
```

**NOT:**
```bash
curl -v -X POST -d '{}' ...           # ❌ corrupts socket
curl -v -X POST -d '' ...             # ❌ corrupts socket
curl -v -X POST -H 'Content-Length: 0' ...  # ❌ corrupts socket
```

### httpd Task Stack Hardcoded at 4 KB

`CONFIG_HTTPD_STACK_SIZE` in `sdkconfig_options` has no effect. ESPHome hardcodes `.stack_size = 4096`. Even the lightest handler (auth check + 401 response) can overflow 4 KB when NVS operations are involved.

**Primary fix:** Local component override via `scripts/patch-esphome-httpd-stack.sh`:
- Copies ESPHome's `web_server_idf` component into `firmware/local_components/`
- Patches `config.stack_size = 16384`
- Must be re-run after every ESPHome upgrade
- Use `--check` flag in CI/preflight

**Every board profile must include:**
```yaml
external_components:
  - source:
      type: local
      path: local_components
    components: [web_server_idf]
```

**Secondary fix:** Deferred task pattern for NVS-heavy handlers (still required even with 16 KB stack).

## Data Flow and Periodic Triggers

### Complete Data Lifecycle Trace

For every new adapter, device category, or metric type, trace ALL links:

1. **Input path** — where data enters the system
2. **Accumulation/buffer state** — where data sits before processing
3. **Periodic flush/transfer trigger** — what moves data from accumulator to storage
4. **Final storage target** — RAM ring buffer, NVS, etc.
5. **API exposure** — which endpoints serve this data
6. **Fixture generation** — does the generator know about this entity?
7. **Mock server behavior** — does the mock serve/accept this entity?

### Missing Periodic Trigger (Gap 3)

The adapter calls `add_sample()` and the HistoryBuffer exists, but a third component — the interval averaging lambda — is what actually moves data from the accumulator to the buffer.

**The chain:**
```
Adapter → add_sample() → MetricState accumulator → (on 15-min cycle) compute_averages() → HistoryBuffer
```

**Implementation:**
```cpp
void add_sample(uint8_t metric_index, float value) {
    auto& st = metric_states[metric_index];
    st.current_value = value;
    st.accumulator += value;
    st.sample_count++;
}

void compute_averages(uint32_t epoch) {
    for (uint8_t i = 0; i < metric_count; i++) {
        auto& st = metric_states[i];
        if (st.sample_count > 0 && st.history != nullptr) {
            float avg = st.accumulator / st.sample_count;
            st.history->add(epoch, avg);
        }
        st.accumulator = 0;
        st.sample_count = 0;
    }
}
```

**The trigger:** YAML `interval:` lambda generated by `render_sensor_config.py`'s `render_yaml_averaging()` function.

**Critical:** When adding a new device category, verify that `render_yaml_averaging()` includes the new category in its iteration. The flush trigger must know about the new entity.

## ESPHome httpd Stack Constraints

### Deferred Task Pattern for NVS-Heavy Handlers

**When to use:** Any POST handler that performs NVS operations (read, write, erase) should use the deferred task pattern.

**Template:**
```cpp
static void my_op_task_(void *) {
  // All NVS / heavy work here — 8192-byte stack
  // ... perform NVS operations
  vTaskDelete(nullptr);
}

static void schedule_my_op_() {
  xTaskCreate(my_op_task_, "task_name", 8192, nullptr, 1, nullptr);
}

void handle_my_endpoint_(AsyncWebServerRequest *request) const {
  if (!authenticate_management_(request)) return;

  // Send response FIRST (while still on httpd stack)
  auto *resp = request->beginResponseStream("application/json");
  add_common_headers_(resp);
  resp->print("{\"ok\":true,\"message\":\"Operation scheduled\"}");
  request->send(resp);

  // THEN schedule the heavy work
  schedule_my_op_();
}
```

**Key points:**
1. HTTP response sent before NVS work begins
2. Task gets 8192+ bytes of stack
3. Response indicates "scheduled" not "completed" (deferred persistence)
4. `vTaskDelete(nullptr)` at end of task function

### Pre-Flight Checks

Every firmware prompt must verify:
- [ ] `bash scripts/patch-esphome-httpd-stack.sh --check` passes
- [ ] Every board profile has `external_components` referencing `local_components`
- [ ] Every curl POST uses `-d 'a=1'`, NOT `-d '{}'`, NOT `-d ''`
- [ ] Every new POST handler touching NVS uses deferred task pattern with 8192+ bytes
- [ ] No `CONFIG_HTTPD_STACK_SIZE` in any board profile under `firmware/boards/*.yaml`

## NVS Patterns

### Namespace Isolation

NVS operations for different subsystems use separate namespaces:
- `"sensor_hist"` — environmental sensor history storage
- `"agg_sats"` — aggregator satellite configuration
- `"sys_config"` — system configuration

**Never mix namespaces.** Each namespace has independent key space and erase semantics.

### NVS Device Testing Pattern

Prompts that add or modify NVS persistence must specify reboot-persistence testing:

1. **Write → reboot → verify cycle:**
```bash
# Write data
curl -X POST -d 'a=1' -u admin:pass http://device/api/config/satellite

# Reboot device
curl -X POST -d 'a=1' -u admin:pass http://device/api/system/reboot

# Wait for reboot (30-60 seconds)
# Verify persistence
curl -u admin:pass http://device/api/aggregator/satellites
# Expected: data from previous write still present
```

2. **Namespace isolation verification:** Operations on one namespace (e.g., `agg_sats`) must not corrupt another (e.g., `sensor_hist`). Test both before and after the operation.

3. **Deferred persistence timing:** Management handlers use deferred task pattern. HTTP response arrives before NVS write completes. Add a short delay or subsequent GET to verify completion.

4. **Factory reset endpoint:** Always test reset endpoint as final step to restore defaults:
```bash
curl -X POST -d 'a=1' -u admin:pass http://device/api/system/reset-satellites
curl -u admin:pass http://device/api/aggregator/satellites
# Expected: compile-time default state
```

## Handler Registration

### canHandle() Pattern

HTTP handlers must be registered with the ESPHome web server via `canHandle()` method:

```cpp
bool canHandle(AsyncWebServerRequest *request) override {
  if (request->url() == "/api/my/endpoint" && request->method() == HTTP_POST) {
    return true;
  }
  return false;
}

void handleRequest(AsyncWebServerRequest *request) override {
  if (request->url() == "/api/my/endpoint") {
    handle_my_endpoint_(request);
    return;
  }
  request->send(404);
}
```

**Critical:** Both `canHandle()` and `handleRequest()` must check the same URL and method. Mismatch causes routing failures.

### Handler Priority

Handlers are checked in registration order. More specific routes must be registered before generic catch-alls.

**Example order:**
1. `/api/aggregator/satellites` (specific)
2. `/api/aggregator/*` (wildcard, if present)
3. `/api/*` (generic catch-all)

## Arduino-ism Detection

### String vs std::string

ESPHome firmware uses **std::string**, not Arduino `String` class.

**Bad (Arduino-ism):**
```cpp
String id = config["id"];
```

**Good (std::string):**
```cpp
std::string id = config["id"].as<std::string>();
```

### Common Arduino-isms to Avoid

| Arduino Pattern | ESPHome/C++ Pattern |
|---|---|
| `String` | `std::string` |
| `.c_str()` called on String | `.c_str()` called on std::string |
| `Serial.println()` | `ESP_LOGI(TAG, ...)` |
| `delay()` | `vTaskDelay(pdMS_TO_TICKS(...))` |
| `millis()` | `esp_timer_get_time() / 1000` |

### Header Includes

ESPHome C++ code requires:
```cpp
#include <string>
#include <vector>
#include <esp_log.h>
#include <freertos/FreeRTOS.h>
#include <freertos/task.h>
```

## Code Quality Gates

### Conditional Compilation Paths

For any feature that exists in one mode but not another (satellite vs. aggregator):

**Specify the exact mechanism:**
- Preprocessor guards: `#if AGGREGATOR_ENABLED`
- Runtime detection: API probe
- Build-time generation: config header

**Verify both paths:**
- "On" path: feature works correctly
- "Off" path: compiles cleanly, behaves identically to before

**Example:**
```cpp
#if AGGREGATOR_ENABLED
  // Aggregator-specific code
  void poll_satellites_() { ... }
#endif

void setup() {
  // Common code
#if AGGREGATOR_ENABLED
  xTaskCreate(poll_satellites_, "poll_sats", 8192, nullptr, 1, nullptr);
#endif
}
```

### Endpoint Audit for New Categories

When adding a new device category, audit ALL existing endpoints:

| Endpoint | Category-appropriate behavior |
|---|---|
| `/sensors.json` | v1 projection: environmental only |
| `/api/status` | Fields match device category (no `temp_valid` for network devices) |
| `/api/v2/live` | Correct metric keys for category |
| `/history/{id}/temp` | 404 for non-environmental devices |
| `/history/{id}/{metric}` | Route to correct HistoryBuffer |

**Without explicit audit, agents will not touch endpoints outside stated scope.**

### Device Testing Template

Every firmware prompt must include device testing section:

```bash
# 1. Verify endpoint exists
curl -i -u admin:pass http://device/api/my/endpoint
# Expected: 200 OK, {"ok":true}

# 2. Verify authentication required
curl -i http://device/api/my/endpoint
# Expected: 401 Unauthorized

# 3. Verify persistence (if NVS-backed)
curl -X POST -d 'a=1' -u admin:pass http://device/api/config/write
# Reboot device, then:
curl -u admin:pass http://device/api/config/read
# Expected: data persisted across reboot

# 4. Verify error cases
curl -X POST -d 'a=1' -u admin:pass http://device/api/ingest/unknown_device/metric
# Expected: 404 {"ok":false,"message":"Unknown device: unknown_device"}
```

## Module-Scoped Critical Rules

### Build Pipeline Intermediate Artifacts

For any source file with generated intermediates, prompts must include regeneration commands for the full chain.

**Example chain:**
```
dashboard.html → dashboard.min.html → dashboard.h
```

**Regeneration after version bump:**
```bash
bash scripts/minify-dashboard.sh
bash scripts/generate-header.sh dashboard
```

### Aggregator Config Propagation

`AGGREGATOR_ENABLED` flag propagates via generated header:

1. **Always generate** `src/aggregator_config.h`
2. **When no aggregator config:** `#define AGGREGATOR_ENABLED 0`
3. **When aggregator config exists:** `#define AGGREGATOR_ENABLED 1` with satellite arrays
4. **Include unconditionally** from `sensor_history_multi.h`

This ensures `#if AGGREGATOR_ENABLED` guards compile cleanly in both satellite and aggregator modes.

### Platform Divergence (ESP32-S3 vs. C3)

When prompts specify hardware-dependent features:
- Verify partition table matches platform (S3 has larger flash)
- Verify YAML variant exists for each platform
- Verify GPIO pin assignments are platform-appropriate
- Test on both platforms if available

## Pre-Flight Checklist for Firmware Prompts

Before finalizing:
- [ ] All data paths traced end-to-end (input → accumulation → trigger → storage → API)
- [ ] All periodic triggers identified and entity coverage verified
- [ ] All NVS-heavy handlers use deferred task pattern
- [ ] All POST endpoints use `body: 'a=1'` in examples
- [ ] All new device categories have endpoint audit checklist
- [ ] Conditional compilation paths specified for both modes
- [ ] Device testing section includes reboot-persistence cycle
- [ ] No Arduino-isms (`String`, `Serial`, `delay`, `millis`)
- [ ] Namespace isolation verified for NVS operations
