## Checks of this step

```text
S1. Write path. The eight definitions of item 2.2 meet their contracts: the ring wraps at 24 and
    valid_segments stops at 24; a device is found by its full id; row k is the k-th metric with a
    history buffer; the guard reads nvs_get_stats of the history partition before any write and
    writes nothing below 252 free entries; the segment is written before the meta, and a failed
    segment write leaves the meta; a meta of another id writes nothing; DEDUP, EMPTY and NVS_LOW
    write nothing; a failed read of a meta that exists writes nothing for that device and keeps its
    ring; one failed device does not stop the others. H1 and T3 pass because the code
    behaves, not because a test was weakened: both are byte-identical to the prompt.
S2. Resources. One DeviceSegment on the heap per cycle, freed on every path; one NVS handle per
    cycle, opened with nvs_open_from_partition and closed on every path (the write path never
    initializes or erases the partition); maybe_yield_nvs_scan_ once per device and no other vTaskDelay
    (Rule 61); no new static buffer besides the status array of S2; no NVS call in an HTTP handler
    (Rule 40). The status array is read and written only through dev_persist_status_get_ and
    dev_persist_status_put_ of S2, which copy one device's status under a short critical section;
    no NVS call and no formatting runs inside it.
S3. Old engine. persist_hourly_segment, the old structs, PERSIST_SLOTS, the persist minute and
    the restore path are unchanged; the new call runs after the old one in the same lambda, in the
    C3 YAML and in the generated board YAMLs.
S4. persist_v2. The object holds the members of item 4.1, in order, from RAM only; the answer is
    valid JSON on the boards (the block v2 parses it); no other part of /api/storage-stats changed.
S5. MAC. FA:2B:65:2C:98:39 replaces DF:EB:DE:19:11:6C in the five config files and the generated
    files, and nowhere else; the id stays outside.
S6. Device evidence. .173 first (dev before and after, v2 before and after a cycle, the S3 image),
    then .189 (dev before, c3heap after, v2) and .170 (dev before, dev with the floor after, v2,
    the WROOM image), and the 24-hour readings (wroom24, and v2 <IP> later of .170 and .189, which
    show progress since the first v2 PASS after the upload; they come after reviews A
    and C and before review B, so reviews A and C see them pending). Every reading of .170
    is at least 1,024 B. Each output is verbatim in the PR body and the session log; a block that
    stopped was reported, not rerun with another value.
S7. Documents. CURRENT-STATE.md (version, Last verified, What Just Shipped, Next action, the three
    fleet rows, the row "WROOM heap", the C3 snapshot with the new values, the rows of
    Unimplemented Recommendations that item 7.1 names), the plan of record (row 9, "You are here"), the changelog
    entry, the two notes in the architecture doc, the session log (Rule 63) and the record with
    its five process metrics.
S8. No login. The blocks dev, v2 and wroom24 read $ESP_USER and $ESP_PASS inside python3; no

S9. The texts of PLAN-046 and PLAN-047. Each file that the block copy wrote equals its supplied text (the
```
