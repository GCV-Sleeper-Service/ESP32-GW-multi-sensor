## Exact scope

Implement background aggregator polling task that fetches data from satellite gateways.

### Step-by-step:

1. **Add `SatelliteCache` struct** (~7KB per satellite):
   - Cached manifest JSON string (up to 4KB)
   - Cached live values (up to 2KB)
   - Cached status (up to 512 bytes)
   - `reachable` flag, `consecutive_failures` counter
   - `last_manifest_fetch`, `last_live_fetch` timestamps
   - `manifest_stale` flag (refreshed every 5 minutes)

2. **Add `AggregatorTask` as a FreeRTOS task:**
   - Start conditionally: only when `AGGREGATOR_ENABLED == 1` (determined by presence of `config/aggregator.json` at build time)
   - Polls satellites SEQUENTIALLY (not concurrent — memory constraint)
   - Staggered timing: each satellite gets its own poll cycle offset
   - Per satellite per cycle:
     a. If manifest stale (>5 min old or never fetched): `GET /api/manifest` → update cache
     b. `GET /api/status` → update cache
     c. `GET /api/v2/live` → update cache
   - History is NOT fetched proactively — on-demand only (per architecture plan)

3. **Use `esp_http_client.h`** for HTTP requests:
   - Connection timeout: 5 seconds
   - Response buffer: 4KB (sufficient for manifest/live/status)
   - Reuse client handle per satellite when possible
   - Clean up on failure — no leaked handles

4. **Failure handling:**
   - Mark satellite unreachable after 3 consecutive failures
   - Unreachable satellites: poll at reduced frequency (every 5 minutes instead of every 30s)
   - When a satellite recovers: reset failure counter, resume normal polling
   - Log satellite state transitions (reachable → unreachable and vice versa)

5. **Conditionally start task** in YAML on_boot lambda:
   ```cpp
   #if AGGREGATOR_ENABLED
   xTaskCreate(aggregator_poll_task, "agg_poll", 8192, nullptr, tskIDLE_PRIORITY + 2, nullptr);
   #endif
   ```

6. **Memory budget:**
   - Per satellite: ~7KB cache + ~4KB HTTP client buffer during request
   - 2 satellites: ~18KB total (acceptable on ESP32-S3 with 320KB+ SRAM)
   - ESP32-C3: marginal — document that C3 supports max 1–2 satellites

7. **Update changelog, session log, bump to 7.5.5.1**

### ⚠️ CRITICAL: BUG-043 LESSON-OPS-056 Compliance

Any code that handles HTTP responses from satellites that could exceed 10KB must use pre-reserved `std::string` with `reserve()`, not `beginResponseStream` or unbounded `std::string` growth. This applies especially to history proxy responses (v7.5.5.2) but establish the pattern now in the polling task for manifest/live responses.

### Critical constraints:
- Single-core ESP32-C3: aggregator task must yield frequently (`vTaskDelay` between HTTP requests)
- Sequential polling only — never send concurrent requests to multiple satellites
- Stack size: 8192 bytes for the aggregator task (HTTP client + JSON caching)
- Satellite firmware: ZERO changes. The satellite doesn't know it's being polled by an aggregator.

## Device testing (for human, after merge)

**⚠️ Requires TWO ESP32 devices: one satellite (existing C3), one aggregator (ideally ESP32-S3 or a second C3).**

### Prerequisites — pull, compile, flash

```bash
cd /config/ESP32-GW-multi-sensor
git pull origin main

cat VERSION
# Expected: 7.5.5.1

# --- SATELLITE (existing device, no aggregator.json) ---
# Verify satellite still compiles without aggregator:
rm -f config/aggregator.json
python3 scripts/render_sensor_config.py --write
esphome compile firmware/esp32-c3-multi-sensor.yaml
# Expected: Compilation successful. No aggregator code included.
# Flash satellite if needed (should already be running v7.5.4.4 firmware).

# --- AGGREGATOR (second device) ---
# Create aggregator config pointing to satellite:
cp config/aggregator.example.json config/aggregator.json
# Edit config/aggregator.json: set satellite base_url to your satellite's IP
# e.g., "base_url": "http://192.168.120.189"

python3 scripts/render_sensor_config.py --write
esphome compile firmware/esp32-c3-multi-sensor.yaml
# Expected: Compilation successful. Aggregator code included.

# Flash to aggregator device:
esphome run firmware/esp32-c3-multi-sensor.yaml --device <aggregator-ip-or-serial>
```

### Verification

```bash
# 1. Check aggregator device logs for polling activity:
esphome logs firmware/esp32-c3-multi-sensor.yaml --device <aggregator-ip>
# Expected: Log lines showing satellite poll: "Polling satellite gw-main...", "Manifest cached", "Live data updated"

# 2. Wait 2 minutes for several poll cycles, then verify cached data.
# (No API endpoints yet — v7.5.5.2 adds those. For now, verify via logs.)

# 3. Verify satellite is unaffected:
curl -s http://<satellite-ip>/api/status | python3 -m json.tool
curl -s http://<satellite-ip>/api/v2/live | python3 -m json.tool
# Expected: Normal satellite responses, no disruption from aggregator polling

# 4. Check aggregator heap:
curl -s http://<aggregator-ip>/api/status | grep free_heap
# Expected: Stable. Record baseline for comparison.

# 5. Test satellite unreachable scenario:
# Temporarily power off satellite.
# Wait 3 poll cycles (~90 seconds).
# Check aggregator logs for "Satellite gw-main unreachable" message.
# Power satellite back on.
# Wait 1 poll cycle.
# Check logs for "Satellite gw-main recovered" message.

# 6. Clean up — restore satellite-only config:
rm config/aggregator.json
python3 scripts/render_sensor_config.py --write
```

### Report results

Record: aggregator log output (first 2 minutes), satellite heap stability, aggregator heap baseline, unreachable/recovery behavior. ANY satellite instability caused by aggregator polling is a blocker.
