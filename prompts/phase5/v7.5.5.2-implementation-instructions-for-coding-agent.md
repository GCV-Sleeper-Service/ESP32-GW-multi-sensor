## 4. Exact Scope — Aggregator API Endpoints

Expose aggregator-specific API endpoints that serve cached satellite data. All endpoints are conditionally compiled with `#if AGGREGATOR_ENABLED`.

### 4a. `GET /api/aggregator/gateways`

Returns list of configured satellites with cached status:

```json
{
  "gateways": [
    {
      "id": "gw-main",
      "name": "Main Gateway",
      "reachable": true,
      "last_seen": 1710264000,
      "consecutive_failures": 0,
      "manifest_cached": true,
      "live_cached": true
    }
  ]
}
```

Build from `SatelliteCache` array. Extract firmware_version, sensor_count, and free_heap from the cached `status_json` if available (parse with simple `strstr()` string search — no JSON library needed on ESP32).

### 4b. `GET /api/aggregator/live`

Returns unified live values from all satellites:

```json
{
  "timestamp": 1710264000,
  "gateways": {
    "gw-main": {
      "reachable": true,
      "live": "<raw cached JSON from /api/v2/live>"
    }
  }
}
```

**Implementation note:** Rather than parsing and restructuring the cached live JSON, embed it as a raw string. The dashboard will parse the nested structure. This avoids implementing a JSON parser on the ESP32.

### 4c. `GET /api/aggregator/proxy/{gw_id}/history/{device}/{metric}`

On-demand history proxy. The aggregator fetches from the satellite and relays the response.

**⚠️ CRITICAL: Use `fetch_to_buffer()` for the proxy fetch**

The `fetch_to_buffer()` function from v7.5.5.1 uses raw lwIP sockets with HTTP/1.0. It is the ONLY HTTP client available in the ESPHome build environment. Do NOT use `esp_http_client.h` — it will not compile (BUG-057).

**⚠️ CRITICAL: LESSON-OPS-056 Compliance**

Satellite history responses can be 20KB+ (45 days × hourly points). You MUST:

1. Build the satellite URL: `snprintf(url, sizeof(url), "%s/history/%s/%s", sat.base_url, device, metric)`
2. Allocate a static buffer for the proxy response — use a dedicated `s_proxy_tmp[32768]` buffer (separate from `s_fetch_tmp` which the polling task uses). **WHY separate:** The proxy runs in the web handler context while the polling task runs in RTOS context. They must not share the same temp buffer.
3. Call `fetch_to_buffer(url, s_proxy_tmp, sizeof(s_proxy_tmp), &proxy_len)` to fetch from satellite
4. Build the response using `beginResponse(200, "text/plain", reinterpret_cast<const uint8_t*>(s_proxy_tmp), proxy_len)` — zero-copy from the static buffer
5. **NEVER** use `beginResponseStream` for the proxy response
6. If satellite is unreachable or fetch fails, return 502 (Bad Gateway)
7. If gateway ID is unknown, return 404

**URL parsing:** The proxy URL pattern is `/api/aggregator/proxy/{gw_id}/history/{device}/{metric}`. Extract `gw_id`, `device`, and `metric` from the URL path. Follow the existing path-parsing pattern in `handleRequest()`.

**Proxy buffer declaration** (inside `#if AGGREGATOR_ENABLED`, static lifetime):
```cpp
// Separate from s_fetch_tmp — the proxy runs in web handler context
// while the polling task runs in RTOS context. They must not share buffers.
static char s_proxy_tmp[32768];
static uint16_t s_proxy_len = 0;
```

**⚠️ Concurrency note:** `s_proxy_tmp` is only accessed by the web handler (ESPHome main loop, single-threaded). Multiple concurrent proxy requests would conflict, but ESPHome's AsyncWebServer processes requests sequentially on the main loop. The polling task never touches `s_proxy_tmp`. This is safe.

### 4d. Route registration in `canHandle()` / `handleRequest()`

Add URL matching inside `#if AGGREGATOR_ENABLED` blocks:

```cpp
// In canHandle():
#if AGGREGATOR_ENABLED
if (strcmp(p, "/api/aggregator/gateways") == 0) return true;
if (strcmp(p, "/api/aggregator/live") == 0) return true;

```

### ⚠️ URL Collision Check (verify before adding routes)

Before adding new routes, verify that `/api/aggregator/` does NOT conflict with existing routes in `HistoryWebHandler::canHandle()`. The existing handler matches:
- `/api/v2/history/`
- `/history/`
- `/api/manifest`
- `/api/v2/live`
- `/api/status`

None of these overlap with `/api/aggregator/` — but **verify this by reading the current `canHandle()` implementation before making changes.**

### 4e. ⚠️ Mutex usage in web handlers

All aggregator endpoint handlers that read from `SatelliteCache` MUST take the mutex before reading and release after:

```cpp
void handle_aggregator_gateways_(AsyncWebServerRequest *request) const {
  if (xSemaphoreTake(s_cache_mutex, pdMS_TO_TICKS(100)) != pdTRUE) {
    request->send(503);
    return;
  }
  // ... build response from satellite_caches[] ...
  xSemaphoreGive(s_cache_mutex);
  request->send(resp);
}
```

**The proxy endpoint does NOT need the mutex** for the fetch itself (it uses `s_proxy_tmp`, not `SatelliteCache` buffers). But it DOES need the mutex briefly to read `sat.base_url` for URL construction.

### 4f. Status field extraction

The `/api/aggregator/gateways` response should include `firmware_version`, `sensor_count`, and `free_heap` extracted from the cached `status_json`. Extract using `strstr()` on the exact field names `"version":"`, `"sensor_count":`, and `"free_heap":`. Do NOT attempt full JSON parsing.
