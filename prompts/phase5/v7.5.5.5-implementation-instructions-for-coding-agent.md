## 5. Exact Scope — Phase 5 Closure

Documentation, aggregator setup guide, and Phase 5 close.

### 5a. Create `Docs/aggregator-setup.md`

Write a comprehensive deployment guide covering:

**1. Overview**
- What the aggregator does (polls satellites, caches data, serves unified dashboard)
- Satellite vs aggregator role distinction

**2. Hardware Requirements**
- ESP32-C3 SuperMini: supports 1–2 satellites (limited RAM). Same hardware as satellite.
- ESP32-S3: recommended for 3–5 satellites (more RAM, dual-core). Future YAML variant needed.
- Raspberry Pi Zero 2W or similar: recommended for >5 satellites. Separate implementation (not covered by this firmware).

**3. Prerequisites**
- At least one satellite gateway already running and accessible on the network
- ESPHome build environment set up
- Network connectivity between aggregator and all satellite IPs

**4. Configuration**
- Copy `config/aggregator.example.json` to `config/aggregator.json`
- Edit satellite entries: set `id`, `name`, `base_url` for each satellite
- Adjust `poll_interval_seconds` if needed (default 30, range 10–300)
- Keep `config/sensors.json` for the aggregator's own local sensors (or minimal placeholder)

**5. Building and Flashing**
```bash
python3 scripts/render_sensor_config.py --write
# Verify src/aggregator_config.h shows AGGREGATOR_ENABLED 1
esphome compile firmware/esp32-c3-multi-sensor.yaml
esphome run firmware/esp32-c3-multi-sensor.yaml --device <aggregator-ip-or-serial>
```

**6. Accessing the Dashboard**
- Open `http://<aggregator-ip>` in a browser
- Gateway selector bar shows all configured satellites
- "All Gateways" view shows health summary
- Click a gateway to see its devices

**7. Network Requirements**
- Aggregator must be able to reach each satellite's IP on port 80 (or configured port)
- Satellites do NOT need to reach the aggregator — polling is one-directional
- If satellites are on different VLANs: configure routing or place aggregator on a management VLAN with access to all satellite networks
- Firewall: allow HTTP (port 80) from aggregator to each satellite IP

**8. Monitoring**
- `/api/status` on aggregator shows version, heap, uptime
- `/api/aggregator/gateways` shows satellite reachability status
- Monitor heap stability over time — heap drift >5KB over 30 minutes indicates a leak

**9. Troubleshooting**

| Symptom | Likely Cause | Fix |
|---------|-------------|-----|
| Satellite shows "unreachable" | Network issue, satellite powered off, wrong IP | Verify satellite IP, check network connectivity |
| Aggregator dashboard blank | Aggregator not detecting mode | Check `/api/aggregator/gateways` returns data |
| High latency on aggregator dashboard | C3 memory pressure with many satellites | Reduce satellite count or upgrade to S3 |
| Heap declining over time | Memory leak in polling or proxy | Report as bug, check logs for errors |
| History charts empty in aggregator view | Proxy unable to reach satellite | Verify satellite responds to direct `/api/v2/history` requests |

**10. Reverting to Satellite Mode**
```bash
rm config/aggregator.json
python3 scripts/render_sensor_config.py --write
esphome compile firmware/esp32-c3-multi-sensor.yaml
esphome run firmware/esp32-c3-multi-sensor.yaml
```

**11. Security Considerations**
- Satellite APIs are unauthenticated by default (except management endpoints like reboot/delete)
- The aggregator polls unauthenticated read-only endpoints (`/api/manifest`, `/api/status`, `/api/v2/live`)
- For production deployments: place satellites and aggregator on an isolated VLAN
- Future: add authentication to satellite read endpoints (not implemented in v7.5.5.x)
