## 5. Exact Scope

This step has 4 major parts plus housekeeping. Implement in order.

### Part A — Aggregator mode detection and boot flow (dashboard JS)

#### 5a-1. Runtime mode detection

The dashboard detects aggregator mode by probing the API. This is runtime detection, not compile-time — the same `dashboard.html` is embedded in both satellite and aggregator firmware.

```js
var DASHBOARD_MODE = 'satellite'; // default

async function detectAggregatorMode() {
  try {
    var r = await fetch(ESP_HOST + '/api/aggregator/gateways', {cache: 'no-store'});
    if (r.ok) {
      var data = await r.json();
      if (data && Array.isArray(data.gateways) && data.gateways.length > 0) {
        DASHBOARD_MODE = 'aggregator';
        window._aggregatorGateways = data.gateways;
        return true;
      }
    }
  } catch(e) { /* not aggregator — satellite mode */ }
  return false;
}
```

**WHY this approach:** `detectAggregatorMode()` makes a single HTTP request. On satellites, `/api/aggregator/gateways` returns 404 (fast). On aggregators, it returns the gateway list. No compile-time flag needed, no different builds, no conditional compilation in the dashboard.

#### 5a-2. Modified boot flow

Insert aggregator detection at the START of the boot sequence, BEFORE `loadManifestV2()`:

```js
async function initDashboard() {
  // ... existing setup (theme, etc.) ...

  var isAggregator = await detectAggregatorMode();

  if (isAggregator) {
    // Load local manifest too (aggregator may have local sensors like ping)
    await loadManifestV2();
    // Build local sensor cards (if any — may be zero)
    if (App.State.getSensors().length > 0) {
      buildDeviceCards();
    }
    // Initialize aggregator-specific UI
    await initAggregatorDashboard();
  } else {
    // Existing satellite boot flow — COMPLETELY UNCHANGED
    await loadManifestV2();
    buildDeviceCards();
    connectSSE();
    // ... rest of existing satellite init ...
  }
}
```

**⚠️ CRITICAL: The `else` branch must be BYTE-IDENTICAL to the current boot flow.** Do not refactor, reorganize, or "clean up" the satellite path. Any change to the satellite boot sequence risks BUG-043-class regressions.

#### 5a-3. Aggregator dashboard initialization

```js
async function initAggregatorDashboard() {
  renderGatewaySelector(window._aggregatorGateways);
  renderAllGatewaysSummary(window._aggregatorGateways);
  renderSettingsPanel(window._aggregatorGateways);

  // Start periodic aggregator polling — 15s interval, in-flight guarded
  setInterval(pollAggregatorLive, 15000);
  pollAggregatorLive();

  // Signal for Playwright test infrastructure (v7.5.5.4 will use this)
  window._aggregatorReady = true;
}
```

### Part B — Gateway selector and views (dashboard JS + CSS)

#### 5b-1. Gateway selector bar

Horizontal tab bar above the sensor grid. Tabs: "All Gateways" + one per satellite. Each satellite tab shows online/offline indicator.

```js
function renderGatewaySelector(gateways) {
  var container = document.getElementById('sensorGrid');
  var selectorHtml = '<div id="gwSelector" class="gw-selector">' +
    '<button class="gw-tab active" data-gw="all">All Gateways</button>';

  gateways.forEach(function(gw) {
    var statusClass = gw.reachable ? 'gw-online' : 'gw-offline';
    selectorHtml += '<button class="gw-tab ' + statusClass + '" data-gw="' + gw.id + '">' +
      gw.name + '</button>';
  });

  // Settings tab — always last
  selectorHtml += '<button class="gw-tab gw-settings-tab" data-gw="settings">⚙ Settings</button>';
  selectorHtml += '</div>';
  container.insertAdjacentHTML('beforebegin', selectorHtml);

  // Use programmatic event binding (App.State.get/set pattern, not inline onclick)
  document.querySelectorAll('.gw-tab').forEach(function(tab) {
    tab.addEventListener('click', function() {
      document.querySelectorAll('.gw-tab').forEach(function(t) { t.classList.remove('active'); });
      tab.classList.add('active');
      var gwId = tab.getAttribute('data-gw');
      if (gwId === 'all') {
        renderAllGatewaysSummary(window._aggregatorGateways);
      } else if (gwId === 'settings') {
        renderSettingsPanel(window._aggregatorGateways);
      } else {
        renderGatewayDevices(gwId);
      }
    });
  });
}
```

#### 5b-2. "All Gateways" summary view

Shows a card per satellite with status, last seen, firmware version, device count.

#### 5b-3. Per-gateway device view

When a gateway tab is clicked: parse the cached manifest for that gateway, build sensor configs with namespaced IDs (`{gw_id}.{device_id}`), render cards using existing `CARD_RENDERERS`, populate from `/api/aggregator/live`.

**⚠️ The `/api/aggregator/gateways` response from v7.5.5.2 includes a `manifest` field with the cached manifest JSON for each gateway.** Parse this to get device categories and measurements for correct renderer dispatch. If the manifest is unavailable (satellite was unreachable when manifest was last fetched), use `_default` renderer.

#### 5b-4. History charts through proxy

In aggregator mode, when the user opens a chart for a satellite's device, the history URL must route through the aggregator proxy:
`/api/aggregator/proxy/{gw_id}/history/{device}/{metric}` instead of `/history/{device}/{metric}`

Set a per-device `history_base_url` or intercept the URL in `fetchDeviceHistory()`.

#### 5b-5. Stale/unreachable indicators

Unreachable gateways get grayed-out cards with "Unreachable" overlay. Their tabs show a red border.

#### 5b-6. Aggregator live polling

```js
var _aggLiveInFlight = false;
function pollAggregatorLive() {
  if (_aggLiveInFlight) return;
  _aggLiveInFlight = true;
  fetch(ESP_HOST + '/api/aggregator/gateways', {cache: 'no-store'})
    .then(function(r) { return r.json(); })
    .then(function(data) {
      if (data && data.gateways) {
        window._aggregatorGateways = data.gateways;
        var activeTab = document.querySelector('.gw-tab.active');
        if (activeTab) {
          var gwId = activeTab.getAttribute('data-gw');
          if (gwId === 'all') renderAllGatewaysSummary(data.gateways);
          else if (gwId === 'settings') renderSettingsPanel(data.gateways);
          // Per-gateway view auto-refreshes from pollAggregatorLive indirectly
        }
      }
    })
    .catch(function() { /* silent */ })
    .finally(function() { _aggLiveInFlight = false; });
}
```

### Part C — Settings panel (read-only in this version)

#### 5c-1. Settings panel UI

The settings panel shows a "Satellites" section listing configured satellites with their status. In v7.5.5.3, this is **read-only** — no add/remove/edit capability. The UI structure is designed so Phase D (v7.6.x) can add interactive controls without restructuring.

```js
function renderSettingsPanel(gateways) {
  var grid = document.getElementById('sensorGrid');
  grid.innerHTML = '';

  var html = '<div class="settings-panel">';
  html += '<h3 class="settings-title">Satellite Configuration</h3>';
  html += '<p class="settings-subtitle">Configured satellites (read-only — runtime management coming in a future update)</p>';

  gateways.forEach(function(gw) {
    var statusDot = gw.reachable ? '🟢' : '🔴';
    var fwVersion = '—';
    var deviceCount = '—';

    // Extract from cached status if available
    if (gw.firmware_version) fwVersion = gw.firmware_version;
    if (gw.device_count !== undefined) deviceCount = gw.device_count;

    html += '<div class="settings-satellite-card">';
    html += '<div class="settings-sat-header">' + statusDot + ' ' + gw.name + ' <span class="settings-sat-id">(' + gw.id + ')</span></div>';
    html += '<div class="settings-sat-details">';
    html += '<div>URL: <code>' + (gw.base_url || '—') + '</code></div>';
    html += '<div>Firmware: ' + fwVersion + '</div>';
    html += '<div>Devices: ' + deviceCount + '</div>';
    html += '<div>Status: ' + (gw.reachable ? 'Online' : 'Unreachable') + '</div>';
    html += '</div>';
    html += '</div>';
  });

  html += '</div>';
  grid.innerHTML = html;
}
```

**WHY read-only now:** The settings panel structure (card per satellite, status display, detail fields) is the foundation for Phase D's interactive management (add/remove buttons, NVS write-back). Building the layout now means Phase D only adds click handlers and API calls — it doesn't restructure the UI.

### Part D — Board-driven About card

#### 5d-1. Problem

The dashboard About card currently shows "ESP32-C3 SuperMini Gateway" text, C3 pinout SVG, and C3-specific documentation regardless of which board is running. On the S3 aggregator, this is wrong.

#### 5d-2. Solution

The About card content comes from the `about_description` text sensor, which is populated by a lambda that parses the `debug.device` output. This lambda auto-detects the chip model (ESP32-C3, ESP32-S3, etc.) — so the chip name should already be correct on S3.

The C3-specific content that needs board-gating:

1. **Pinout SVG** — in `dashboard.html`, the SVG is inside a `<div id="pinoutDiagram">`. Wrap it with a check: if the manifest's `gateway.hardware` field does NOT contain "C3", hide it. The pinout SVGs for other boards will be added in future steps when the images are available.

2. **Board-specific documentation text** — any hardcoded "ESP32-C3 SuperMini" text in the About section. Replace with the board name from the manifest.

In `dashboard.js` (and mirrored to `dashboard.html`):

```js
// After manifest is loaded, in applySensorMeta() or a new function:
function updateBoardInfo() {
  var manifest = window._manifest;
  if (!manifest || !manifest.gateway) return;

  var hw = manifest.gateway.hardware || '';

  // Hide C3 pinout on non-C3 boards
  var pinout = document.getElementById('pinoutDiagram');
  if (pinout && hw.indexOf('C3') === -1) {
    pinout.style.display = 'none';
  }
}
```

Call `updateBoardInfo()` after the manifest is loaded in both satellite and aggregator boot paths.

**⚠️ Do NOT remove the pinout SVG from the HTML.** Just hide it via CSS/JS when the board doesn't match. C3 satellites still need it.
