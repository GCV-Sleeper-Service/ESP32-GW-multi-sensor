Part 2 - the evolved reality:
Background - previous phases to take into consideration - over the course of the development of this project (already into two months), the following pattern was emerged:

First a proposal for new features and implementations is discussed here with you. 
As a result of the discussion it is either a document for the phased (phases 3/4/5/6, D/X/V, 7...) architectural scope/implementation is created, or, as a preliminary step, a prompt is created based on research that would create such a document. The phased architectural document in its turn is used to produce prompts for each step for each phase. 

How development has evolved: first the code was produce by Claude and run/tested/deployed locally. Then development moved into GitHub, with proper documentation and step planning. Then bugs/issues have been started documented, then usage of multi-LLMs both for agent and review purposes have been introduced. This both made things easier and more complicated at the same time. 

Over the course the another pattern has emerged: for each step in the phase, minimum three prompts need to be produced:

- An very detailed agent prompt that follows strict DO and DO NOTs procedure as well as have checkpoints in it to make sure that prompt assumptions do match the reality at this moment. DO/DO NOTs on its own are based on prompt writing guide from Docs/writing-guide as well as rules that have been learned/discovered and listed in prompts/prompt-index-and-workflow.md
- A handoff document from the previous step that has detailed outlines what this step is doing, risk level, as well as deliverables and also outlines if next step prompts need to be updated and inspected as well
- A two-step prompt that is produced for Claude environment that has checkpoints in them for Agent prompts as well as detailed list what review prompt for this particular step needs to check, confirm and greenlight.

The two-step Claude prompt itself is a base to create review prompts for non-Claude environments, like for Copilot, Perplexity and others that have different tools to access GitHub and need to be rewritten accordingly. So it emerged that it is critical as agent's prompt to be specific, the review prompt to be specific in the review scoping to produce the real consolidated PR audit file, as well as based on these files - the phase conclusion results.

It also emerged that after agent's implementation it is critical to have code reviews by inline reviewers (Copilot, Codex, Gemini) and external reviewers (GPT, Codex) as well. 
It has emerged that number of reviewers matter - some of them can caught things that others do not. 
It also matters how the questions for PR review are phased to external reviewers - what exactly they need to look at.

And after conclusion of phaseY a very detailed phase assessment document was created by Copilot that should be used as a template/guideline how phase conclusion should happen.

PhaseY and phaseV that mostly addressed code refactoring, bug fixing and optimization - they did not introduce any new features or architectural changes. This is the scope for phase 7, 8 and beyond and to adequately prepare for it - that's why I am presenting this text to you for mutual discussion, understanding and finding the best, optimal plan to move forward. I am not saying that the current plan is not working. It is, but I think it CAN be made better.


Part 3: the current development environment and the process

I am now going to detail the current, phaseV development plan - how each step was performed. 

PhaseY:
PhaseY was using web interfaces/portal to run agent prompts - the prompts was pasted to the portal (mostly Copilot, but sometimes - Codex or GPT), agent was running the prompt, updating github repo directly (on github.com), then after finishing working the PR had to be made ready for review and then call inline revivers.  
After PR was opened, the fix-up prompt (when needed) also was posted via web portal for additional commits. Then these commits were synced with the local repo that is running ESPhome on LXC container, and operator (I) run additional actions - flashing, testing, etc. Number of times this process repeated - fix is done on github.com, needs to be synced locally, until PR is ready to be merged.
The reviews were also using web interfaces - Perplexity, Codex and GPT and again, the post merge changes needed to be synced locally as well - for documentation updates/edits, etc.

PhaseV:
PhaseV moved execution of agent's prompts locally on Visual Studio Code (VSC) by installing github, codex, github remote, remote explorer extensions. So now VSC opens remote repo on LXC container that has ESPHome installed. Codex or Copilot extensions that are used for agent's prompts execution locally - they directly work with the content of the repo on the LXC container - they can read all the files locally, no need to use github tools and access the data on github.com. 
Also, the coudflared tunnel allows to access the LSX container with the ESPhome/local repo via internet - regardless if access is via local network or via cloudflared tunnel, codex and copilot on VSC have direct access to the local repo.

As a result, when copy/pasting the agent's prompt section from Claude two-step prompts, it works - I do not need to alter prompt to account agent's tools.

I though about following improvements/suggestions:

1. Automate local testing with boards that rely on curl/non-visual interface commands:

ANY such command can and should be built into the agent's prompt so agent can run compile, flash (wait, if necessary), run curl/test commands and post results. Operator should do manual testing only when only operator can do such action.

Codex agent actually did flashing the boards, but it used esphome run which led that esphome was outputting the logs and had the session hang. Instead it needs to use esphome clean, esphome compile, esphome upload commands as well as have built-in capability to detect if something went wrong and what exactly.

esphome clean   firmware/esp32-c3-multi-sensor.yaml
