## 4. NVS Serialisation Safety (Informational)

Even though the gate was not triggered, the agent correctly reviewed `firmware/core/nvs-persistence.h` before any potential struct change. Finding: persistence uses `HistoryMeta` and `SegmentSnapshot` blobs and shims temperature/humidity history through `devices[i].metric_states[0/1].history` per-field — no `sizeof(SensorEntity)` blob serialisation or layout-coupled restore path exists. This confirms struct changes *would have been* safe had the gate triggered, and documents the finding for Phase 7 planning.

## 6. Lessons Learned

### What went well
- **Conditional gate design worked perfectly.** The heap ≥ 65 KB check cleanly eliminated unnecessary work. The no-change path produced a concise, well-documented PR with zero review findings.
- **Agent compliance was clean.** All 10 Instruction Compliance Output rows passed. The agent read both `data-model.h` and `nvs-persistence.h` before the gate decision, as required.
- **Diff scope was exactly correct.** All 15 files were legitimate version-bump artifacts; no spurious or out-of-scope changes crept in.
- **Issue #165 closed correctly.** The heap measurement was documented in both the issue and the PR description before merge.

### Observations for Phase 7
- `SensorEntity` audit findings (unused metric slots, per-device string buffers) are documented in session log for future reference. If heap pressure increases post-Phase-7 NVS changes, the ~112–176 B per-device gain is a known available optimisation.
- NVS serialisation is confirmed per-field only — no layout coupling. Phase 7 struct work is unblocked from an NVS safety perspective.

### Protocol observations
- The Three-Turn review protocol handled the conditional-step pattern cleanly: Turn 1 extracted both branches of the gate, Turn 2 resolved which branch applied immediately from the PR description + operator-supplied measurement, Turn 3 was decisive with zero ambiguity.
- Operator-supplied live measurement (70,144 bytes) vs. PR-documented measurement (70,952 bytes) — minor variance, both passing. Future steps: consider documenting which boot context the measurement was taken from (cold boot vs. warm restart) for completeness.
