## Internal Audit (Architectural Advisor)

### 1. Did the PR match the scope defined in the step prompt? Any deviations?

Scope was largely respected. One classified deviation:

| File | Deviation Type | Classification |
|------|---------------|----------------|
| `dashboard/components/gateway-panel/index.js` | Addition — auth header wiring to aggregator endpoints | Harmless / necessary |
| `dashboard/core/history.js` | Addition — auth header wiring | Harmless / necessary |
| `dashboard/core/app-shell.js` | Addition — `_setAggregatorAuthFromCreds()` helper | Harmless / necessary |

The dashboard JS changes are a direct consequence of newly-guarded aggregator endpoints. The agent correctly identified that the dashboard could not function without sending auth headers to the three newly-guarded aggregator handlers. These changes are in-scope in effect even though the prompt did not list them explicitly. **Back-port recommendation:** add "auth header wiring to aggregator endpoints in dashboard JS is expected in-scope" to the v7.6.8.0 agent prompt §3 and to the v7.6.8.1 handoff for clarity.

### 2. Did the codebase state match the prompt's assumptions?

Yes, with one material observation: the boot sequence for aggregator mode now probes `/api/status` before `/api/manifest` in `detectAggregatorMode()`. This was a correct autonomous consequence of the status endpoint split but was not specified in the prompt. It caused the BUG-043 Playwright assertion to fire (see CI remediation section). Prompt assumption drift: **low severity, handled correctly.**

### 5. Context that carries forward to next step

- **`/api/status/full` boot-order dependency:** `detectAggregatorMode()` now expects `/api/status` to be answerable before `/api/manifest`. Any v7.6.8.1 change to the aggregator startup sequence must preserve this order.
- **`fetch_to_buffer()` 7th param `basic_auth`:** All future callers must explicitly pass `nullptr` or valid credentials. The default is `nullptr` (unauthenticated) — document in v7.6.8.1 handoff as a carry-forward.
- **External callers of `/api/ingest/` not yet audited:** Push scripts and ESPHome YAML sensors that POST to `/api/ingest/` must be updated with `Authorization` headers before live device deployment of v7.6.8.0. This is an operator task, not agent scope, but must be tracked.
- **No `beginResponseStream` baseline:** PR #177 established a zero-count baseline for `beginResponseStream`. PR #180 maintained it. v7.6.8.1 must also maintain it (Rule 8).

## External Caller Audit — `/api/ingest/` ⚠️

`/api/ingest/` is now auth-gated. All callers must include `Authorization: Basic <base64(user:pass)>`. Failure to update callers before deploying v7.6.8.0 firmware will result in silent data loss (401 responses, no data ingested).

**Callers requiring audit and update before live deployment:**

| Caller Type | Location | Auth Header Added? | Notes |
|-------------|----------|--------------------|-------|
| Push scripts | `scripts/` — any that POST to `/api/ingest/` | ⏳ PENDING operator audit | Must add `-u user:pass` or `Authorization: Basic ...` header |
| ESPHome YAML | ESPHome device configs with `http_request` → `/api/ingest/` | ⏳ PENDING operator audit | Must add `headers: Authorization: Basic <base64>` in `http_request.post` |
| Cron jobs / automations | Any external automation POSTing to `/api/ingest/` | ⏳ PENDING operator audit | Same requirement |

**This is a deployment blocker.** Do not flash v7.6.8.0 firmware to live devices until all callers are confirmed updated.
