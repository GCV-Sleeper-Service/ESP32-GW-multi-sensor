## §0 — Why This Step Exists

Issue #139 ("History loading serialization for C3 boards") was scheduled by the Phase V plan for full fix in Phase 7 (v7.7.x). Two events after plan finalisation changed the risk profile:

1. 2026-04-12 comment on #139: the same heap exhaustion affects 520 KB SRAM WROOM boards, not just the C3 → wider blast radius than the plan assumed.
2. 2026-04-16 v7.6.9.0 device testing: the WROOM satellite crashes on `/history/office/temp` fetch.

The v7.6.8.1 safety-net (a fixed 60 KB `csv.reserve()` cap) was sized for the C3's ~68 KB free-heap budget. On the WROOM with ~30 KB free heap, 60 KB exceeds the running heap and crashes the board.

A plan addendum (`Docs/phase-V-implementation-plan-addendum-v7.6.9.4.md`, already committed alongside this step) authorises a **minimum-viable OTA-safe mitigation**:
- Server-side: replace the fixed cap with a heap-adaptive formula
- Client-side: defer the initial history load until after the first status snapshot succeeds

This is **not** the full #139 fix. Chunked streaming and per-device storage remain Phase 7. This step delivers the ~80% stability win that can ship OTA now.

### Step 1 — Server-side: heap-adaptive reserve cap

**Step 1.1 — Edit `firmware/core/web-handler.h` at the `handle_api_v2_history_` reserve site**

Use `grep -n "csv.reserve" firmware/core/web-handler.h` to confirm the exact line numbers. Expected around lines 568 and 1520.

```cpp

```

Replace with:

```cpp
    // v7.6.9.4 (#139 partial): heap-adaptive cap replaces fixed 60 KB.
    // Fixed cap (v7.6.8.1 V2-E) was sized for C3 ~68 KB free heap budget.
    // On WROOM with ~30–40 KB free, a 60 KB reserve exceeds running heap and
    // crashes the board. Clamp to free_heap/3 with a 12 KB floor and the
    // original 60 KB ceiling preserved for healthy boards. Dashboard tolerates
    // truncated CSV gracefully (parseCompactHistory processes line-by-line).
    size_t free_now = esp_get_free_heap_size();
    size_t adaptive_cap = free_now / 3;
    if (adaptive_cap < 12000) adaptive_cap = 12000;
    if (adaptive_cap > 60000) adaptive_cap = 60000;

    std::string csv;
    csv.reserve(std::min(est_bytes, adaptive_cap));
```

**Step 1.2 — Edit `firmware/core/web-handler.h` at the `handle_history_` reserve site**

Find the second occurrence (inside `handle_history_`). It has the same pattern:


Apply the identical replacement as Step 1.1. The comment block references the same rationale; the code block is byte-for-byte identical.

**Anti-patterns to avoid:**
- Do NOT extract the cap calculation into a helper function. Two call sites with the same inline code is simpler and easier to review. A helper adds an import/forward-declaration burden in a header file for no gain.

### Step 2 — Client-side: gate initial history load on first status snapshot

**Step 2.1 — Edit `dashboard/core/boot.js`**

Use `grep -n "historyBootstrapTimerId" dashboard/core/boot.js` to locate the existing history-trigger block (around lines 111–118 on current main).

Find the block:

```javascript
      // BUG-043-cont (PR2) Fix E: History deferred from 8s to 10s — the sequential initial
      // poll (batch=1, 200ms gap, ~30 paths) takes roughly 7-8s on a loaded device. Adding
      // 2s headroom prevents NVS-heavy history scans from overlapping with poll tail or
      // storage stats (t+5s), keeping the startup window clean.
      historyBootstrapTimerId = setTimeout(function() {
        if (!isImportActive()) loadHistory().catch(function(){});
      }, 10000);
```

Replace with:

```javascript
      // v7.6.9.4 (#139 partial): gate initial history load on first status snapshot.
      // Fixed 10 s timer was a worst-case estimate. Gating on loadStatusSnapshot()
      // gives a live signal the board is (a) responsive, (b) at post-boot heap,
      // (c) past the BLE/WiFi settle window. Preserves a 15 s fallback in case
      // /api/status/full is unreachable (auth mismatch, network drop).
      // loadHistory() is idempotent via _historyInFlight guard, so both triggers
      // firing is safe.
      var _v7_9_4_historyKicked = false;
      function _v7_9_4_kickHistoryOnce() {
        if (_v7_9_4_historyKicked || isImportActive()) return;
        _v7_9_4_historyKicked = true;
        loadHistory().catch(function(){});
      }
      // Primary trigger: fire 1 s after the first status snapshot resolves.
      // loadStatusSnapshot() is already called elsewhere in boot.js — chain off it.
      loadStatusSnapshot().then(function() {
        setTimeout(_v7_9_4_kickHistoryOnce, 1000);
      }).catch(function(){});
      // Safety fallback: always fire by 15 s so the user sees charts even if
      // /api/status/full never returns.
      historyBootstrapTimerId = setTimeout(_v7_9_4_kickHistoryOnce, 15000);
```

**Anti-patterns to avoid:**
- Do NOT remove the existing `loadStatusSnapshot()` calls elsewhere in `boot.js` — they serve other purposes (SSE-mode one-shot at 2 s, polling-mode 30 s interval). Our new call is an **additional** trigger tied specifically to the history-load gate.
- Do NOT pass `credentials: 'same-origin'` here — `loadStatusSnapshot()` already sets it internally (hotfix 2). We just call the existing function.
- Do NOT remove the `historyBootstrapTimerId = setTimeout(...)` binding — other code may cancel that timer via `clearTimeout(historyBootstrapTimerId)`. Preserve the variable assignment.
- Do NOT replace `isImportActive()` check — it still applies inside `_v7_9_4_kickHistoryOnce()`.
- Do NOT add a separate `loadHistory()` retry if `loadStatusSnapshot()` fails — the 15 s fallback already covers that path.

```markdown
## LESSON-OPS-NNN — Heap-adaptive caps on HTTP response allocations

**Context:** v7.6.8.1 shipped a fixed 60 KB cap on `csv.reserve()` in the history handlers as a safety-net for issue #139. The 60 KB constant was sized against the ESP32-C3's ~68 KB free-heap budget — the most constrained supported board at the time.

**Failure mode:** The WROOM-32D (520 KB SRAM total, no PSRAM, ~30–40 KB free heap under sustained dashboard load) hits the fixed cap with a reserve larger than its running free heap. The allocator either throws or forces fragmentation, crashing the board. The board class the cap was meant to protect most (the C3) was fine; a different board class (the WROOM) was broken by the same cap.

**Fix (v7.6.9.4):** Replace the fixed cap with `clamp(esp_get_free_heap_size() / 3, 12000, 60000)`. Division by 3 accounts for three concurrent heap consumers on the same request: the CSV buffer, the HTTP response buffer, and TCP/SSE headroom. Floor of 12 KB prevents starvation where the whole request fails rather than just truncating. Ceiling of 60 KB preserves the existing behaviour for boards with plenty of heap (S3 with 8 MB PSRAM).

**Generalisable rule:** When a bounded allocation must work across SoC variants with different heap budgets, prefer `clamp(current_heap / divisor, floor, ceiling)` over a fixed threshold. The self-calibrating form handles future board additions without plan rework. The divisor captures the "this request has other heap consumers" assumption. The floor prevents pathological paths. The ceiling bounds blast radius for boards where you've already validated the behaviour.

**Anti-pattern:** Per-chip lookup tables for heap caps. Tempting because "esp32c3: 60 KB, esp32: 20 KB" is explicit, but requires plan updates for every new board variant and doesn't respond to per-request heap pressure.

**Not a substitute for:** Chunked responses when the payload genuinely exceeds safe allocation regardless of current heap. Issue #139's full fix (Phase 7) delivers time-windowed chunked streaming for that case. The adaptive cap is the 80% win that ships OTA now.
```
