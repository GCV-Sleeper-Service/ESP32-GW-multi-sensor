## §0 — Why This Step Exists

The ESP32-C3 board has been running with ESPHome's stock **4 KB** httpd task stack since the project began. A local component override at `firmware/local_components/web_server_idf/web_server_idf.cpp` patches the stack to 16,384 bytes — but it was **never compiled into the C3 firmware**.

**Root cause:** The C3 template YAML (`firmware/esp32-c3-multi-sensor.yaml`) is missing the `external_components` block that tells ESPHome to use the local override instead of its built-in `web_server_idf`. The WROOM and S3 board YAMLs have this block (injected by `generate_board_yaml()` in `render_sensor_config.py`), but the C3 template uses a different code path (`render_yaml_file()`) that does in-place marker substitution and never touches `external_components`.

**Evidence:** Post-v7.6.9.4 telemetry shows C3 watermark at 636 bytes — but on a 4 KB stack, not the expected 16 KB. Peak usage is ~3,460 bytes. WROOM peak is ~3,340 bytes on a 16 KB stack. The per-architecture difference is negligible (~3.5%); the 20× watermark gap was entirely caused by different stack sizes.

**PR#195 (first attempt)** implemented an architecture-conditional stack bump (RISC-V 20 KB / Xtensa 16 KB) based on the incorrect assumption that RISC-V uses more stack. The device gate correctly caught that the override wasn't active — watermark stayed at 632 after the "bump." This revised prompt fixes the actual root cause.

**Fix:** Add the `external_components` block to the C3 template. The C3 gets the same 16 KB stack all other boards have. No architecture-conditional sizing needed.
