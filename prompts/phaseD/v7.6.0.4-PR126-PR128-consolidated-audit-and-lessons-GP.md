That makes the correct final judgment:

- **PR #126** delivered the feature,
- **PR #128** made the feature reliable in the real shipped environment,
- the original PR #127 audit was **not sufficient** as the final closure artifact,
- and the true Phase D Step 4 baseline for v7.6.0.5 is **PR #126 + PR #128 together**.

Those were corrected before PR #126 merged.

The Step 4 feature was not fully stable after PR #126 merged. PR #128 fixed a real shipped-state regression class:

- form inputs could be wiped during active interaction,
- auth-confirmed test flows could complete without any visible status update because the stored DOM reference had gone stale,
- periodic re-rendering could still tear down the Settings panel while the user was interacting with it.

So the correct delivery assessment is:

> The coding agent delivered the required feature, but the final accepted implementation is the sum of PR #126 and PR #128. Evaluating PR #126 in isolation understates the real shipped lessons and overstates closure readiness.

## Part II — Did the Codebase State Match the Prompt’s Assumptions?

**Mostly yes, with one important correction and four real prompt-robustness gaps.**

### What matched

1. All three management endpoints already existed and were usable from dashboard JS
2. The step was correctly scoped as dashboard/UI-only work
3. `requestManagementCredentials()`, `safeJsonResponse()`, `escHtml()`, and `escAttr()` already existed for reuse
4. `renderSettingsPanel()` was indeed a read-only placeholder ready to be replaced
5. The required JS ↔ HTML mirror workflow was correctly emphasized as a high-risk area

### What the original PR #127 draft got wrong

The original audit draft incorrectly claimed that the prompt omitted two things:

- the `innerHTML` pairing rule for the relevant returned test-satellite rendering path
- the `safeJsonResponse()` usage in the `_refreshSettingsPanel()` skeleton

PR #127 review comments correctly challenged those claims. Those statements should **not** be carried forward into the final audit. They were part of the reason the original draft was insufficient.

### Real prompt/codebase robustness gaps exposed by the shipped result

#### M1 — Async DOM volatility was not elevated enough

The prompt did not clearly force the agent to treat Settings-panel DOM as unstable across:

- auth modal waits,
- poll-driven re-renders,
- any other `innerHTML` refresh path.

That gap mattered because the code captured a DOM element reference before an async auth flow and later wrote to a stale node.

#### M2 — Live DOM re-query discipline was not made explicit

The prompt did not explicitly require a rule such as:

> if async callbacks update UI status after a possible panel rebuild, re-query the live element by stable `id` before writing.

PR #128 had to add exactly that pattern.

#### M3 — Poll-driven re-render guardrails were under-specified

The prompt did not explicitly require the Settings panel to skip re-render while:

- `_satTestInFlight`, `_satAddInFlight`, or `_satRemoveInFlight` is true,
- the user is actively focused in the URL/name inputs.

PR #128 added that runtime guard in `pollAggregatorLive()`.

#### M4 — The next-step prompt became stale after PR #128

The base v7.6.0.5 prompt was written before the final shipped state settled. It therefore needed a GP addendum to reflect:

- PR #126 + PR #128 together as the baseline,
- real regression coverage needs,
- firmware-over-example contract lock for mock routes.

So the correct codebase/prompt assessment is:

> the prompt was stronger than the original draft gave it credit for, but still not strong enough on async UI lifecycle safety and final shipped-state carry-forward.

## Part IV — Coding Agent Prompt Audit Against the Writing Guide

### Where the v7.6.0.4 prompt aligned well

1. Required reading was concrete and file-specific
2. Auth policy by endpoint was clearly enumerated
3. The prompt strongly emphasized LESSON-OPS-043 (JS ↔ HTML mirror)
4. The prompt explicitly prohibited firmware changes and new endpoints
5. The prompt included concrete quality gates (`escHtml()`, `escAttr()`, `safeJsonResponse()`, in-flight guards, no inline handlers)

### Where the final shipped result shows the prompt still needed strengthening

#### G-Audit-1 — Async UI lifecycle safety needed to be first-class, not implicit

The writing guide’s spirit requires prompts to guard the most likely failure modes for the scoped change. For v7.6.0.4, once an auth modal and poll-driven panel refresh coexisted, async DOM staleness should have been treated as a first-class risk.

#### G-Audit-2 — Re-render suppression rules needed explicit expression

The prompt should have explicitly told the agent:

- do not re-render the Settings panel while satellite operations are in flight,
- do not re-render the Settings panel while the add-form inputs are focused.

#### G-Audit-3 — Prompt audits must distinguish real prompt defects from implementation drift

The original PR #127 draft blurred that line by blaming prompt omissions that the prompt already covered. The writing guide expects audits to be evidence-driven and exact. That means a closure audit must not restate prompt defects unless the prompt text truly supports the claim.

### Carry-forward prompt-writing improvements

1. Add an **Async DOM Safety** block for dashboard prompts:
   - if callbacks run after auth/network waits, re-query stable nodes before updating UI
2. Add a **Re-render Guard** rule for poll-driven dashboards:
   - skip panel rebuild while form inputs are focused or action flags are in flight
3. Add an explicit **Shipped-State Closure Rule**:
   - if a post-merge fix PR changes the real shipped behavior, the consolidated audit must include both PRs
4. Add an **Audit Evidence Rule**:
   - do not identify a prompt defect unless the exact missing/contradictory text has been re-verified in the prompt file being audited
5. Do not mint new `LESSON-OPS-*` IDs in audit-only docs unless the canonical lessons file is updated in lockstep
