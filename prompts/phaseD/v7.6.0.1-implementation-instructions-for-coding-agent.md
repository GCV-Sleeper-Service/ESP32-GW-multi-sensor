## 4) Exact Scope (§3.5)
Implement `POST /api/aggregator/add-satellite` by replacing 501 stub:

### 4.1 Request contract (fixed)
- Method: `POST`
- Query params: `url` (required), `name` (optional), `poll` (optional)
- Example:
  - `POST /api/aggregator/add-satellite?url=http://192.168.1.42&name=Kitchen&poll=30`

### 4.2 Probe flow
- Probe candidate using `fetch_to_buffer(url + "/api/manifest", ...)`.
- Parse `gateway.id` and `gateway.name` from manifest.
- If probe fails or manifest is invalid, reject.

### 4.3 Validation branches
- 405: wrong method
- 400: missing URL
- 400: invalid URL format (must start with `http://`)
- 409: list full (`runtime_satellite_count >= MAX_SATELLITES`)
- 409: duplicate URL
- 400: probe failed/manifest parse failed
- 200: success

### 4.4 Mutation and persistence
Under `AGG_LOCK()`:
1. Write new entry at `satellite_caches[runtime_satellite_count]`.
2. Initialize cache fields safely (`clear_cache()` + identity + poll interval + manifest snapshot fields as used by existing code).
3. Increment `runtime_satellite_count`.
4. Persist via `save_single_satellite_to_nvs_()` or full save path as designed in v7.6.0.0.

On NVS write failure: log and return non-success code without corrupting runtime state.

### 4.5 Data-flow trace (mandatory)
```text
POST add-satellite(url,name,poll)
  → validate query
  → probe manifest at url/api/manifest
  → derive satellite id/name metadata
  → lock cache mutex
  → append at runtime_satellite_count
  → increment runtime_satellite_count
  → persist agg_sats NVS
  → unlock
  → return 200 with added satellite summary
```

- [ ] All satellite iteration loops use `runtime_satellite_count`, not `MAX_SATELLITES`
- [ ] All cache mutations (add/remove/clear) happen under `s_cache_mutex` (AGG_LOCK/AGG_UNLOCK)
