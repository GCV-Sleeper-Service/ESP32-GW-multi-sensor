The base v7.6.0.5 prompt was written before the final v7.6.0.4 shipped state settled.

1. parts of its mock-contract examples,

This addendum corrects those gaps.

## 3. Contract-lock correction

Do **not** treat the example route payloads in the base prompt as authoritative if they conflict with the live firmware contract or the v7.6.0.4 handoff.

### Mandatory rule
Before implementing any mock route, read the live firmware handlers and mirror the **actual** response contract:
- response shape,
- status code,
- message text,
- required parameters,
- error ordering.

If the base prompt’s example JSON differs from the firmware, the **firmware wins**.

### Specific warning
The management-route examples in the base v7.6.0.5 prompt should be treated as scaffolding, not as a canonical schema contract.

## 4. PR126 + PR128 regression coverage is mandatory

The new Playwright group must do more than basic happy-path coverage.

It must also cover the class of regressions exposed by PR #128.

### Add these explicit requirements

#### A. Input-stability regression
At least one browser test must verify that:
- the user can type into the satellite URL / name fields,
- a settings-panel refresh opportunity occurs,
- the typed values are still present when the action continues.

#### B. Auth-flow live-status regression
At least one browser test must verify that:
- Test Satellite enters the auth workflow,
- the flow resumes,
- the status/result is written to the **live** panel, not lost due to stale node references.

#### C. Re-render guard regression
At least one test must verify that the settings panel is not destructively rebuilt while:
- a satellite action is in flight, or
- the add-form inputs have focus.

#### D. Post-action continued usability
At least one test must verify the panel remains usable after a completed action:
- after add,
- after delete,
- after test.

The user must be able to continue interacting with the form/list without needing a manual page reload.

## 5. Mock-server implementation rule additions

### 5.1 Stateful management mock is required
The mock server must preserve management-state mutations across requests within a test process.

### 5.2 Reset endpoint is required
A reset helper endpoint is required so tests can start from a deterministic state.

### 5.3 Do not use detached/static fixture objects after mutation
Once the management list becomes stateful, the aggregator gateways route must return the live managed state, not a stale file object captured at server init.

---

## 6. Test-authoring guardrails to add

### 6.1 Aggregator-only skip guard
All new satellite-management tests must skip unless `FIXTURE_SET=aggregator`.

### 6.2 Self-contained state discipline
Any test that mutates managed satellite state must:
- reset first, or
- fully establish its own expected starting state.

No cross-test state leakage.

### 6.3 No dynamic “whatever the page has” assertions for critical counts
Use deterministic expected counts after setup/reset. Do not weaken tests into shape-only assertions where the exact count is part of the behavior being verified.

### 6.4 Use only the fixtures actually needed
If a test is API-only, use `{ request }` only.  
If a test is UI-only, use `{ page }` only.
