## 4.2 Why PR #128 was required

After PR #126 merged and device/browser testing continued, a real regression was found in the new settings panel workflow.

PR #128 fixed two user-visible problems now recorded in `Docs/bugs-and-lessons-learned.md`:

### BUG-080 — fields cleared during Test/Add interaction
The settings panel could be rebuilt while the user was still typing or clicking a button, causing the URL/name inputs to be destroyed and recreated mid-interaction.

### BUG-081 — auth dialog completed but status update never appeared
The code captured DOM element references before an async auth flow. If the settings panel re-rendered before the callback resumed, the captured node became detached. Writes succeeded against the detached object but were invisible in the live UI.

## 4.3 Final shipped state

The final shipped v7.6.0.4 state is therefore:

- **PR #126** delivered the intended feature.

That means the correct final judgment is:

## 5. Corrected reading of the prompt-quality story

The original PR #127 draft blamed some defects on prompt omissions that the prompt already covered. That needs correction.

## 5.1 What the prompt appears to have already specified correctly

Based on the PR #127 review comments, the v7.6.0.4 prompt already specified:

- `innerHTML` for returned test-satellite value rendering in the relevant path, and
- `safeJsonResponse()` in the `_refreshSettingsPanel()` skeleton.

So those specific claims in the original audit should **not** be carried forward.

## 5.2 What the prompt still did *not* guard strongly enough

Even after correcting those inaccuracies, the prompt still lacked or underemphasized the areas that PR #128 exposed:

### A. Re-render safety across async UI flows
The prompt did not strongly require the implementation to treat settings-panel DOM as unstable across:
- auth-modal round trips,
- periodic aggregator polling,
- explicit panel refreshes.

### B. Fresh DOM re-query discipline
The prompt did not explicitly say:
- do not keep captured status/input element references across async callbacks if the parent panel may re-render,
- re-query live nodes by stable ID at write time.

### C. Interaction guardrails during timer-driven refresh
The prompt did not explicitly require:
- suppressing settings-panel re-render while inputs are focused,
- suppressing settings-panel re-render while satellite actions are in flight.

### D. Browser/device regression coverage for these flows
The prompt for v7.6.0.5 did not yet explicitly force Playwright coverage for:
- typing into the Add form while polling is active,
- auth-confirmed test flow after a panel rebuild opportunity,
- action-button event propagation / rerender interaction,
- stale-node-safe status updates.

Those are the real prompt-strengthening lessons from PR #126 + PR #128.

## 7. Lessons that should carry forward from the final shipped state

These lessons align with the authoritative `Docs/bugs-and-lessons-learned.md` state after PR #128.

### 7.1 Do not cache DOM nodes across async flows if `innerHTML` replacement can occur
If a panel can be rebuilt while an async callback is pending, captured nodes are not reliable write targets.

### 7.2 Re-render loops must respect active user interaction
A timer/poll refresh that blindly rebuilds a form is a UX bug factory. Focused inputs and in-flight actions must block destructive rerenders.

### 7.3 Auth-dialog workflows are re-render hazards
Any handler that pauses for credentials must be treated like a long async boundary. UI updates after auth must re-acquire live DOM.

### 7.4 Audit docs should not mint official LESSON-OPS IDs unless the canonical lessons file is updated in lockstep
Otherwise the audit can drift out of sync with the authoritative project vocabulary.
