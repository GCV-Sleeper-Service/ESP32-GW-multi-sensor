### Critical prompt defects

#### A1 — Wrong YAML in device testing section (Severity: BLOCKING — prevented device testing)

Section 11 referenced `firmware/esp32-c3-multi-sensor.yaml` for the S3 aggregator build. This is the committed C3 satellite template — it produces satellite firmware for the wrong chip. The correct file is the **generated** `firmware/esp32-s3-devkitc1-n16r8-gw.yaml`. All six Phase D prompts had the same defect.

**Root cause:** The prompt author copied the C3 compile command (the only YAML visible in the repo) without accounting for the generated YAML path for non-C3 boards. The generated S3 YAML is gitignored.

**Back-ported as:** LESSON-OPS-090. Critical Rule 36 added. All Phase D prompts corrected.

---

#### A2 — Missing `minify-dashboard.sh` in regeneration pipeline (Severity: MEDIUM — stale dashboard)

All regeneration pipeline references in prompts and docs listed 4 steps instead of 5, omitting `minify-dashboard.sh` before `generate-header.sh`.

**Back-ported as:** LESSON-OPS-091. Critical Rule 37 added. All pipeline references corrected.

---

#### A3 — No explicit authentication requirement for `POST /api/system/reset-satellites` (Severity: HIGH — caused a real security gap, fixed in PR #99)

§5e adds the reset endpoint but does not state it must call `authenticate_management_()`. The agent implemented it without authentication. Every neighbouring management endpoint in the codebase uses `authenticate_management_()`.

**Back-ported as:** LESSON-OPS-093. Applied to v7.6.0.1 prompt §3a.

---

#### A4 — No NVS key buffer sizing specification (Severity: HIGH — caused a real truncation risk, fixed in PR #99)

The prompt specified the key scheme but not buffer sizes. The agent chose `char key_*[8]`, which overflows for indices ≥ 10 (e.g. `s10_name` = 8 chars + NUL = 9 bytes).

**Back-ported as:** LESSON-OPS-092. Applied to v7.6.0.1 prompt §3a.

---

#### A5 — No all-or-nothing NVS load specification (Severity: HIGH — caused silent topology shrink, fixed in PR #99)

§5a says "returns 0 if NVS is empty or corrupt" but does not define what "corrupt" means for partial reads. The agent used `break` on per-entry failure, silently truncating the satellite list.

**Back-ported as:** LESSON-OPS-095. Applied to v7.6.0.1 prompt §3a.

---

#### A6 — No first-boot NVS seeding requirement (Severity: HIGH — caused first-mutation data loss, fixed in PR #99)

§5a says "populate from compile-time arrays" but not "and write them to NVS." The agent loaded defaults but didn't persist them. First runtime mutation would orphan all compile-time defaults on reboot.

**Back-ported as:** LESSON-OPS-094. Applied to v7.6.0.1 prompt §3a.

## Part III — Lessons

### LESSON-OPS-090 — Device testing YAML must reference generated YAML for target board

Prompt device testing sections referenced the committed C3 template for S3 aggregator builds. The operator compiled satellite firmware for the wrong chip. All six Phase D prompts affected.

**Critical Rule 36 added.**

---

### LESSON-OPS-091 — Regeneration pipeline must include dashboard minification

`minify-dashboard.sh` missing from all pipeline references. Stale `.min.html` can silently embed outdated dashboard content.

**Critical Rule 37 added.**

---

### LESSON-OPS-092 — NVS key buffer sizing

**Source:** Agent chose `char key_*[8]` — overflows for index ≥ 10. NVS max key = 15 chars + NUL = 16 bytes. Prompts with indexed NVS key schemes must specify `char key_*[16]` explicitly.

---

### LESSON-OPS-093 — Management endpoints must have explicit auth requirement in prompt

**Source:** Prompt added `POST /api/system/reset-satellites` without specifying `authenticate_management_()`. Security conventions from neighbouring code are not inherited by the agent — they must be stated.

---

### LESSON-OPS-094 — NVS seeding on first boot must be explicit in prompt

**Source:** Prompt said "populate from compile-time arrays" but not "and write to NVS." First-mutation data loss resulted. Prompts must state: "After loading compile-time defaults, call `save_satellites_to_nvs_()` to seed NVS."

---

### LESSON-OPS-095 — All-or-nothing NVS array load must be explicit in prompt

**Source:** Prompt said "returns 0 if corrupt" without defining partial corruption. Agent used `break` (partial load). Prompts must specify: "On any per-entry read failure, close handle and return 0. Partial loads create invisible topology shrink."

---

### LESSON-OPS-096 — Boot-time init vs runtime mutation mutex ordering

**Source:** `init_satellite_caches_()` runs without mutex. Safe at boot (web handlers not active), but technical debt if startup ordering changes. For v7.6.0.1+, any init-time code must run before web server accepts connections.

---

### Failure Prevention Recommendations

1. **Create an "NVS code block checklist" in the writing guide** — every prompt with NVS operations must include: (a) key buffer `[16]`, (b) all-or-nothing load semantics, (c) first-boot seeding, (d) handle-close on all paths.
2. **Prompts for new endpoints must include a security requirements line** — "Endpoint security: `authenticate_management_()` required / not required [reason]."
3. **Error handling behavior must be specified, not implied** — "all-or-nothing," "best-effort," "honest" vs. "silent" are design choices prompts must state.
4. **Device testing sections must reference the generated YAML** — prompt authors must run `get_yaml_output_path()` mentally or check `render_sensor_config.py --write` output.
