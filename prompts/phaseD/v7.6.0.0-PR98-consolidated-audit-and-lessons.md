### Critical prompt defects

#### A1 — No explicit authentication requirement for `POST /api/system/reset-satellites` (Severity: HIGH — caused a real security gap, fixed in PR #99)

**§5e** adds the reset endpoint but does not state that it must call `authenticate_management_()`. The agent implemented the endpoint without authentication. The Copilot inline reviewer caught it during PR review; it was fixed in PR #99.

Every neighbouring management endpoint (`/api/system/reboot`, `/api/system/ota-status`) in the codebase calls `authenticate_management_()`. The prompt should have stated: "This endpoint MUST call `authenticate_management_()` as the first action — same as `/api/system/reboot`."

**Back-ported as:** LESSON-OPS-091. Applied to v7.6.0.1 prompt §3a.

---

#### A2 — No NVS key buffer sizing specification (Severity: HIGH — caused a real truncation risk, fixed in PR #99)

The prompt specified the key scheme (`s{i}_id`, `s{i}_name`, etc.) but did not specify buffer sizes for key construction variables. The agent chose `char key_*[8]`, which overflows for indices ≥ 10 (e.g. `s10_name` = 8 chars + NUL = 9 bytes).

**Prevention:** Prompts must include `char key_*[16]` in all NVS key buffer declarations. The rationale: NVS max key length = 15 chars + NUL = 16 bytes; index can grow beyond single digits.

**Back-ported as:** LESSON-OPS-090. Applied to v7.6.0.1 prompt §3a.

---

#### A3 — No all-or-nothing NVS load specification (Severity: HIGH — caused silent topology shrink, fixed in PR #99)

**§5a** says "returns 0 if NVS is empty or corrupt" but does not define what "corrupt" means for partial reads within a counted array. The agent used `break` on per-entry failure, silently truncating the satellite list at the first bad entry.

The prompt should have stated: "On any NVS read failure mid-array (`nvs_get_str`, `nvs_get_u16` returning non-`ESP_OK`), close the NVS handle and return 0. Partial loads are worse than no load — they create invisible topology shrink."

**Back-ported as:** LESSON-OPS-093. Applied to v7.6.0.1 prompt §3a.

---

#### A4 — No first-boot NVS seeding requirement (Severity: HIGH — caused first-mutation data loss, fixed in PR #99)

**§5a** says "if NVS `count` key is absent, populate from compile-time arrays" but does not say "and write them to NVS." The agent loaded from compile-time arrays on first boot but did not persist them. The first runtime mutation (add/remove) would write only the delta; on reboot, all compile-time defaults were lost.

The prompt should have stated: "After falling back to compile-time defaults, call `save_satellites_to_nvs_()` to seed NVS. This makes the first boot seamless and prevents the first mutation from orphaning all defaults."

**Back-ported as:** LESSON-OPS-092. Applied to v7.6.0.1 prompt §3a.

## Part III — Lessons

### New Lessons

#### LESSON-OPS-090 — NVS key buffer sizing

**Source:** v7.6.0.0 PR #98 — agent chose `char key_*[8]` for NVS key construction buffers. Overflows for index ≥ 10.

NVS max key length is 15 chars + NUL = 16 bytes. When a prompt specifies an indexed key scheme (`s{i}_suffix`), buffer sizing must account for the maximum expected index. The rule: always use `char key_*[16]` for NVS key buffers, and state this explicitly in prompt code blocks.

---

#### LESSON-OPS-091 — Management endpoints must have explicit auth requirement in prompt

**Source:** v7.6.0.0 PR #98 — prompt added `POST /api/system/reset-satellites` without specifying `authenticate_management_()`.

Every prompt that adds a destructive or persistent-state-mutating endpoint must explicitly state: "This endpoint MUST call `authenticate_management_()` as the first action." Security conventions from neighbouring code are not inherited by the agent — they must be stated.

---

#### LESSON-OPS-092 — NVS seeding on first boot must be explicit in prompt

**Source:** v7.6.0.0 PR #98 — prompt said "populate from compile-time arrays" but not "and write to NVS." First-mutation data loss resulted.

When NVS is the single source of truth for runtime data that starts from compile-time defaults, prompts must explicitly state: "After loading compile-time defaults into the cache, call `save_satellites_to_nvs_()` to seed NVS. This prevents the first runtime mutation from orphaning the defaults."

---

#### LESSON-OPS-093 — All-or-nothing NVS array load must be explicit in prompt

**Source:** v7.6.0.0 PR #98 — prompt said "returns 0 if corrupt" without defining partial corruption. Agent used `break` (partial load).

Prompts for NVS array loading must specify: "On any per-entry read failure, close the NVS handle and return 0. Partial loads create invisible topology shrink. All-or-nothing is the correct semantic."

---

#### LESSON-OPS-094 — Boot-time init vs runtime mutation mutex

**Source:** v7.6.0.0 PR #98 — Copilot reviewer noted `init_satellite_caches_()` runs without `s_cache_mutex`. The ESPHome startup sequence guarantees `aggregator_poll_task()` init completes before the web server accepts connections, so the current implementation is safe. However, the absence of a mutex creates technical debt if startup ordering ever changes.

For v7.6.0.1+, any code added during init must be verified to run before the web server accepts connections. Future consideration: wrap init in the same mutex for defense-in-depth once runtime mutators are active.

---

### Failure Prevention Recommendations

1. **Create an "NVS code block checklist" section in the writing guide** — every prompt with NVS operations must include: (a) key buffer `[16]`, (b) all-or-nothing load semantics, (c) first-boot seeding requirement, (d) handle-close on all paths.

2. **Prompts for new endpoints must include a security requirements line** — "Endpoint security: `authenticate_management_()` required / not required [reason]." This forces the author to make an explicit decision rather than omitting auth by default.

3. **Error handling behavior must be specified, not implied** — "all-or-nothing," "best-effort," "honest" vs. "silent" — these are design choices that prompts must state explicitly. The agent cannot infer them from context.

4. **The v7.6.0.0 prompt defect rate (4 high-severity gaps) suggests the writing guide §3.12 needs a "NVS interaction" sub-section** parallel to the existing "Mock Contract Fidelity" sub-section.
