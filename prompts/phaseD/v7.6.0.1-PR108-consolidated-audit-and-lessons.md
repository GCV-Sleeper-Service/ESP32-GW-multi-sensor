## Part I — Prompt Audit

### What the prompt does well

1. **Complete code blocks for `probe_satellite_manifest_()` and `handle_add_satellite_()`** with detailed inline comments explaining pointer lifetime, thread safety, and race condition analysis. Per Guide §3.13 / Rule 29.

2. **Explicit data flow trace (§5b)** — 10-step numbered flow from request parsing through mutex-protected mutation to NVS persistence. Unambiguous execution order.

3. **API contract table (§5a)** with all 7 error conditions, expected HTTP codes, and exact JSON shapes. This became the device test checklist.

4. **§3a back-ported findings from v7.6.0.0** — 5 specific findings (mutex ordering, NVS seeding, key buffers, auth pattern, erase semantics) correctly informed the agent and prevented repeat defects.

5. **Contract-Lock for Mock section (§12)** — documents the mock contract for v7.6.0.5, preventing prompt-vs-implementation drift at test time.

6. **Thread safety annotations** — §5d explicitly warns about `s_proxy_tmp` vs `s_fetch_tmp` ownership, `AGG_LOCK()` scope boundaries, and pointer lifetime for `url_param`.

### Critical prompt defects

#### P1 — `String` (Arduino type) in prompt-provided code block (Severity: BUILD-BREAKING)

**§5d line 224:** `String url_param = request->getParam("url")->value();`

The prompt provides Arduino's `String` type in a code block meant for an ESP-IDF build target. The agent faithfully copied it. ESPHome's IDF variant uses `std::string` — `String` is undefined. This passed CI (Playwright tests don't compile ESP-IDF code) but broke the real build on device.

**Root cause:** The prompt author (Claude) generated code using Arduino conventions. ESPHome's `AsyncWebServerRequest::getParam()->value()` returns `const std::string&` in the IDF variant, so `std::string url_param = ...` is the correct declaration.

**Prevention:** Critical Rule 44 — never use Arduino `String` in ESP-IDF code. All prompt code blocks must be reviewed for this. Add to the writing guide §3.13 code quality gates: "ESP-IDF builds: verify `std::string` not `String`."

#### P2 — No `canHandle()` entry for GET on add-satellite (Severity: LOW — T4 test failure)

The prompt correctly specifies a 405 response in the handler for wrong HTTP method (§5d line 214). But ESPHome's routing architecture requires `canHandle()` to return true for a method/URL combination before the handler is invoked. The prompt does not instruct the agent to add add-satellite to `canHandle()`'s GET section. GET requests therefore never reach the handler — ESPHome's default handler drops the connection (HTTP 000).

**Prevention:** Future prompts for endpoints with method-specific behavior should include `canHandle()` instructions for all methods the endpoint should accept (including methods it rejects with 405).

#### P3 — Missing device testing for custom `poll` parameter (Severity: LOW — coverage gap)

§11 defines 7 device tests but none exercise the `poll` query parameter. The happy path test (Test 1) uses default poll (30s). No test verifies `&poll=60` is accepted and appears in the response.

**Prevention:** Future test sections should include at least one test per optional parameter.

4. **In-lock re-validation pattern from Fix 3** should be applied to delete-satellite as well — re-check that the satellite still exists at the requested index under the mutex before performing the deletion and compaction.

5. **NVS save failure rollback pattern from Fix 4** should be applied to delete-satellite — if NVS update fails after array compaction, consider whether a rollback is feasible (it's harder for delete than add).
