## §5 — Implementation Instructions

### 5a. Prepare firmware

```bash
# Ensure satellite mode (CI-safe)
bash scripts/provision.sh satellite

# Full pipeline
bash scripts/provision.sh satellite
```

### 5b. Flash C3 satellite board

```bash
cd firmware
esphome run esp32-c3-multi-sensor.yaml
# Select serial port when prompted
# Monitor boot output for NVS restore messages
```

**⚠️ LXC USB note:** If flashing from an LXC container, USB permissions may be lost after device reconnect. Run `chmod 0666 /dev/ttyACM0` (or the correct device) on the Proxmox host if the serial port is inaccessible. See Critical Rule 25.

### 5c. Boot log inspection

Watch the serial console after flash for:
- NVS restore messages (slot count, segment count)
- `HistoryMeta` load confirmation
- No stack overflow or watchdog reset during NVS restore
- Successful WiFi connection

**Record the boot log output.** This is required evidence for the PR.

### 5d. Device test protocol

Wait for the device to be reachable on the network (ping `192.168.120.189`).

**Test 1 — Storage stats check:**

```bash
curl -s http://192.168.120.189/api/storage-stats | python3 -m json.tool
```

Expected: JSON response with valid partition sizing and retention estimates. Fields should include NVS-related statistics. Record the full output.

**Test 2 — History endpoint check:**

```bash
# Get manifest first to find available devices/metrics
curl -s http://192.168.120.189/api/manifest | python3 -m json.tool

# Then fetch history for the first available device/metric pair
# Replace {device} and {metric} with actual values from manifest
curl -s "http://192.168.120.189/api/v2/history/{device}/{metric}" | python3 -m json.tool | head -30
```

Expected: JSON response with history data entries. If the device has been running, there should be populated entries.

**Test 3 — Live data check:**

```bash
curl -s http://192.168.120.189/api/v2/live | python3 -m json.tool
```

Expected: JSON response with live sensor readings.

**Test 4 — Status check:**

```bash
curl -s http://192.168.120.189/api/status | python3 -m json.tool
```

Expected: JSON response with `free_heap`, `free_heap_internal`, `free_heap_total`, uptime, version.

**Test 5 — Reboot persistence test:**

```bash
# Record current history count from storage-stats
curl -s http://192.168.120.189/api/storage-stats | python3 -m json.tool > /tmp/pre-reboot-stats.json

# Trigger reboot (authenticated POST with body)
curl -s -u <user>:<pass> -d 'a=1' -X POST http://192.168.120.189/api/reboot
# Expected: 200 OK response, then device reboots

# Wait for device to come back online (30-60 seconds)
sleep 60

# Verify device is back
ping -c 3 192.168.120.189

# Re-check storage stats after reboot
curl -s http://192.168.120.189/api/storage-stats | python3 -m json.tool > /tmp/post-reboot-stats.json

# Compare — segment counts should match or increase (never decrease)
diff /tmp/pre-reboot-stats.json /tmp/post-reboot-stats.json

# Re-check history — should still have data
curl -s "http://192.168.120.189/api/v2/history/{device}/{metric}" | python3 -m json.tool | head -30
```

Expected: History data survives reboot. Segment counts do not decrease.

**Test 6 — Hourly persist observation (if time permits):**

If time allows, wait for the top of the hour and observe whether storage-stats reports a new segment. This test is optional but valuable — if skipped, document the reason.

## §10 — Anti-Patterns and Inline Warnings

| Anti-pattern | Why | Where it applies |
|---|---|---|
| Using `-H "Content-Type: application/json"` in curl | ESPHome does not consume JSON POST bodies — socket corruption | All POST curl commands (§5d Test 5) |
| Using `-d ''` or bare `-X POST` without body | Must use `-d 'a=1'` for all POST commands | All POST curl commands |
| Flashing with generated YAML on C3 | C3 uses committed template `esp32-c3-multi-sensor.yaml` | §5b |
| Skipping boot log capture | Boot log is required evidence — it proves NVS restore works | §5c |
| Attempting to fix device test failures | Escalate — do not attempt workarounds | §8 |
| Skipping the reboot persistence test | This is the critical test — it validates NVS survives power cycles | §5d Test 5 |

### C++ Split Anti-Patterns (apply to all Phase Y steps)

| Anti-pattern | Why |
|---|---|
| `#include` order differs from assembly concatenation order | Assembly concatenation order IS the dependency order |
| `static` function/variable scope confusion | Per-TU under inclusion, file-scoped under assembly — Phase Y uses assembly |
| Mutex redefinition | `s_cache_mutex` defined in exactly one fragment (`aggregator-runtime.h`) |
| Deferred-task visibility violation | Deferred-task functions must be defined before use in assembly order |
| Adding fragments to ESPHome YAML `includes:` | Only the assembled artifact appears in YAML |
| Generated content in fragments | `render_sensor_config.py` marker blocks have delimiter stubs in fragments, content in assembled artifact only |
| `application/json` POST body | All endpoints use `application/x-www-form-urlencoded` with `body: 'a=1'` |
| `maybe_yield_nvs_scan_()` redefinition | Defined once in `nvs-persistence.h`, accessible from all NVS-scanning loop sites |
