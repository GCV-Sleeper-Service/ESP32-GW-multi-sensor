## 1. Rule 61 delay-value drift (the L8 lint rule trigger)

- **What happened:** In a previous Claude Sonnet session I drafted the §A coding-agent prompt and wrote the A10 item with `vTaskDelay(pdMS_TO_TICKS(1))` quoted as Rule 61 behavior. The coding agent faithfully copied that value into `prompts/handoff/phase7/session-handoff-v7.7.1.3.md` and `prompts/phase7/v7.7.1.3-claude-two-step.md`. Neither I, the agent, nor two of three PR-233 reviewers caught it.
- **Live truth:** `firmware/core/nvs-persistence.h:248` defines `maybe_yield_nvs_scan_()` with `vTaskDelay(pdMS_TO_TICKS(5))`. The 5ms value was set in BUG-043 rev2 because 1ms proved insufficient for ESP32-C3 single-core stability under multi-device NVS iteration.
- **Who caught it:** Codex P1 review on commit `594ab88` (PR #233 review id `4258616746`). Round-2 commit `8c13d59` corrected to `pdMS_TO_TICKS(5)` in both files and rewrote the handoff "Critical Rules" table to disambiguate Rule 11 (general yield principle, codebase-wide) from Rule 61 (specific helper, 5ms, this codebase only, BUG-043 rev2).
- **Why §C13 / lint L8 is mandatory:** The defect was caught only by an LLM reviewer with the right code in front of it. A future PR could regress this if a new Sonnet session (or any other producer) re-types the value from memory. Per `Discussion #230 hypothesis 4` ("every drift class ships with a lint rule"), this is now a tracked drift class. **Do not skip §C13 even if the third-party audit forgets to mention it.** The operator has explicitly flagged it.
- **L8 implementation guidance for the producer:** parse `firmware/core/nvs-persistence.h` for the canonical value inside `maybe_yield_nvs_scan_()`, then grep `prompts/**` for any `pdMS_TO_TICKS(<M>)` reference within ±3 lines of "Rule 61" or "NVS scan" or "maybe_yield_nvs_scan_" context, requiring `M` to match the canonical value. Avoid matching unrelated `pdMS_TO_TICKS` calls in non-Rule-61 contexts (e.g., `WiFiClass::reconnect`).

## 3. `preflight-and-compile` required-status-check deadlock (the producer note for branch protection)

- **What happened:** Branch protection on `main` lists `preflight-and-compile` (defined in `.github/workflows/ci.yml`) as a required status check. The workflow uses a `paths:` filter limited to firmware/dashboard/scripts/etc. — none of which match prompt-only or doc-only PRs. Result: on every prompt-only PR, GitHub correctly skips the workflow, no status is reported, and branch protection waits forever ("Expected — Waiting for status to be reported"). Operator has been admin-overriding to merge.
- **Why this matters for §E:** This is a pre-existing footgun the operator has been working around. The Phase 7 batch-production-prompt-update.md producer template currently does NOT mention required-status-check / path-filter interaction. Future prompt-only PRs will keep hitting this deadlock unless the producer guidance flags it.
- **Three options the operator surfaced** (reference: chat session before the §C/§D/§E request):
  1. Add a stub workflow `ci-required.yml` that always runs (no `paths:` filter), detects whether code-relevant paths changed, and either reports success directly (docs-only) or runs the full pipeline inline (code changes). Doctrinally correct, more code to maintain.
  2. Remove the `paths:` filter from `ci.yml` so every PR runs the full pipeline. One-line fix; wastes ~6–10 minutes per docs-only PR.
  3. Status quo: admin-override on merge for docs-only PRs. Operator has been doing this; defeats the gate over time.
- **Operator preference:** Option 1 long-term, Option 2 acceptable as a stop-gap. Operator wants this **tracked but not necessarily fixed in this PR**. Add it to §C as a separate item (call it whatever the producer assigns — likely §C14) so it is on the audit trail. Do NOT have the §C/§D/§E coding agent implement either option in this PR; they require operator decision and a small CI rework that should ship in its own PR. The §C item should describe the deadlock, list the three options with pros/cons, and explicitly defer implementation to a follow-up issue under issue #228.
- **Producer note for §E:** add to the batch-production prompt template's "Constraints" section: "When defining branch protection required-status-checks for a path-filtered workflow, the producer MUST also specify (a) a stub workflow with the same job name that always reports success on excluded paths, OR (b) explicitly document that operator admin override is the merge mechanism for excluded-path PRs." This prevents the deadlock from being re-introduced for future phases.
