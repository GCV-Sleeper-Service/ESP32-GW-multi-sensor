## 5. Exact Scope — POST /api/ingest Endpoint

Add an HTTP endpoint that accepts metric values pushed by external scripts. This is how system metrics (CPU, RAM, disk) from NAS/server hosts reach the gateway.

**In aggregator mode, `/api/ingest` operates on LOCAL devices only** — it does NOT proxy ingest requests to satellites. The ingest endpoint processes data for devices listed in this gateway's own manifest. Satellite devices are managed by the satellites themselves.

### 5a. URL format and validation

`POST /api/ingest/{device_id}/{metric_key}?val={float}`

The endpoint:
1. Parses `device_id` and `metric_key` from the URL path
2. Parses `val` from the query string
3. Validates that the device exists in `devices[]` array
4. Validates that the metric key exists in that device's `metric_defs[]`
5. Calls `devices[d].add_sample(m, value)` and `devices[d].mark_seen(::time(nullptr))`
6. Returns `200 {"ok":true}` on success

Error responses (using existing `send_json_error_()` helper):
- Unknown device_id → `404 {"ok":false,"message":"Unknown device","status":404}`
- Unknown metric_key → `404 {"ok":false,"message":"Unknown metric","status":404}`
- Missing or invalid val → `400 {"ok":false,"message":"Invalid value","status":400}`
- Non-POST method → `405 {"ok":false,"message":"Method not allowed","status":405}`

### 5b. URL path parsing

Follow the EXISTING pattern from the import endpoint path parsing in `handleRequest()`. The URL structure is:

```
/api/ingest/{device_id}/{metric_key}?val=...
          ^-- prefix (12 chars: "/api/ingest/")
                     ^-- slash separates device_id from metric_key
```

Parse using `strchr()` on the path remainder after the prefix, same as `handle_history_()` and `handle_api_v2_history_()`:

```cpp
void handle_api_ingest_(AsyncWebServerRequest *request) const {
  if (request->method() != HTTP_POST) {
    send_json_error_(request, 405, "Method not allowed");
    return;
  }
  
  const char *p = request->url().c_str();
  // Skip "/api/ingest/" — 12 characters
  const char *rest = p + 12;
  const char *slash = strchr(rest, '/');
  if (!slash) {
    send_json_error_(request, 400, "Missing metric key");
    return;
  }
  
  size_t id_len = slash - rest;
  const char *metric_key = slash + 1;
  
  // Find device
  int dev_idx = -1;
  for (int d = 0; d < NUM_DEVICES; d++) {
    if (strlen(devices[d].id) == id_len &&
        strncmp(devices[d].id, rest, id_len) == 0) {
      dev_idx = d;
      break;
    }
  }
  if (dev_idx < 0) {
    send_json_error_(request, 404, "Unknown device");
    return;
  }
  
  // Find metric
  int metric_idx = -1;
  for (int m = 0; m < devices[dev_idx].metric_count; m++) {
    if (strcmp(devices[dev_idx].metric_defs[m].key, metric_key) == 0) {
      metric_idx = m;
      break;
    }
  }
  if (metric_idx < 0) {
    send_json_error_(request, 404, "Unknown metric");
    return;
  }
  
  // Parse value from query string
  if (!request->hasParam("val")) {
    send_json_error_(request, 400, "Missing val parameter");
    return;
  }
  String val_str = request->getParam("val")->value();
  char *endptr = nullptr;
  float value = strtof(val_str.c_str(), &endptr);
  if (endptr == val_str.c_str() || !isfinite(value)) {
    send_json_error_(request, 400, "Invalid value");
    return;
  }
  
  // Ingest the value
  devices[dev_idx].add_sample(metric_idx, value);
  devices[dev_idx].mark_seen(::time(nullptr));
  
  // Use beginResponse (not beginResponseStream) — matches codebase pattern
  auto *resp = request->beginResponse(200, "application/json", "{\"ok\":true}");
  add_common_headers_(resp);
  request->send(resp);
}
```

**Response pattern notes:**
- Use `beginResponse()` not `beginResponseStream()` — the codebase uses `beginResponse` for all small JSON (LESSON-OPS-056 prohibits `beginResponseStream` for responses >10KB, but `beginResponse` is the standard pattern even for small ones).
- Use `add_common_headers_()` for CORS headers on all new endpoints.
- Reuse `send_json_error_()` for error responses — it already handles `beginResponse` + `add_common_headers_` + `Cache-Control: no-store`.

## ADDENDUM: Post-Phase-5 Codebase Context (updated 2026-03-25)

**Multi-board infrastructure is now in the codebase.** The generator supports multiple board targets via `config/gateway.json` and `firmware/boards/*.yaml`. Phase 6 features (ingest endpoint, system devices, system card renderer) are satellite-side functionality that compiles on ALL board variants. No board-specific code is needed.

**Aggregator code exists in `sensor_history_multi.h`.** The `#if AGGREGATOR_ENABLED` block contains `SatelliteCache`, polling task, and API endpoint handlers. Phase 6 code must NOT conflict with these. The ingest endpoint (`POST /api/ingest/...`) is a satellite endpoint — it MUST work when `AGGREGATOR_ENABLED` is either 0 or 1.

**`esp_http_client.h` is NOT available.** If any Phase 6 code needs HTTP client functionality (unlikely — Phase 6 adds server endpoints, not client fetches), use `fetch_to_buffer()` from the aggregator code with `lwip_*()` prefixed socket functions (LESSON-OPS-068).

**Zero-sensor aggregator support exists.** The generator can produce YAML with zero local sensors. Phase 6 features that add new device types to the manifest must handle the case where the new device is the ONLY device (NUM_DEVICES = 1, NUM_ENV_SENSORS = 0). Verify that endpoints work correctly in this scenario.

**CI workaround for deployment configs.** `config/gateway.json` and `config/aggregator.json` are gitignored deployment configs. Their presence changes generator output. CI runs without them. If your dev environment has these files, move them out before running `--write`/`--check`/preflight/tests. See `Docs/aggregator-setup.md` §15.

**Fixture regeneration (Critical Rule 28).** Version bumps require running BOTH `render_sensor_config.py --write` AND `node tests/fixtures/generate-fixtures.js`, then verifying with `--check` and `grep free_heap`. NEVER manually edit fixture JSON files.
