## Defect Registry

### A1 — `set -euo pipefail` conflicts with `|| echo "0"` fallbacks (SEVERITY: HIGH — MERGE BLOCKER)

**Location:** §5a, line 90 of prompt (bash script)

**Problem:** The prompt specifies `set -euo pipefail` at the top of the bash script, but then uses `|| echo "0"` as fallback on every metric collection line. With `set -e`, the `||` construct does prevent the script from exiting on failure — so that part works. However, `set -u` (treat unset variables as errors) combined with `set -o pipefail` (fail on any command in a pipeline) creates a real issue:

```bash
CPU_PCT=$(top -bn1 | grep "Cpu(s)" | awk '{print $2}' || echo "0")
```

If `top -bn1` succeeds but `grep "Cpu(s)"` finds no match (which happens on some Linux distros that output `%Cpu(s)` or use different locale strings), `grep` returns exit code 1. With `pipefail`, the entire pipeline fails. The `|| echo "0"` catches it — but the variable `CPU_PCT` gets set to "0", while the subshell's exit code is 0 (because of `||`). This is correct.

**BUT:** On some minimal Docker/container environments, `top` may not exist at all, and `free` output format varies across distros (busybox `free` vs GNU `free`). The prompt doesn't warn about this, and the agent won't know to test it.

More critically: **`set -u`** will cause the script to fail with an unbound variable error if any of the `${1:-...}` or `${2:-...}` parameter expansions interact unexpectedly with the agent's shell environment. While `${1:-default}` is safe with `set -u`, agents sometimes rewrite this pattern.

**Correction:** Add an explicit warning comment in the script code block, and add a note to the prompt telling the agent to verify `set -euo pipefail` compatibility with all fallback patterns:

**Insert after line 90 of the prompt's bash script** (`set -euo pipefail`):

```bash
# NOTE: pipefail means any command failure in a pipeline propagates.
# Every metric collection line MUST have || echo "0" to prevent script abort.
# Do NOT remove the fallback clauses.
```

**Also add this note after the §5a code block (after line 109):**

> **⚠️ Shell compatibility note:** The `top` output format varies across Linux distributions (Debian/Ubuntu show `%Cpu(s)`, CentOS shows `Cpu(s)`, BusyBox doesn't have `top -bn1`). The `|| echo "0"` fallback handles all these cases — `CPU_PCT` will be "0" on incompatible systems. Do NOT attempt to make the script work on all distros — the fallback to "0" is the correct behavior for a cron-friendly exporter.

### A2 — Python script `get_cpu_pct()` code doesn't match the preamble description (SEVERITY: MEDIUM)

**Location:** §5 preamble (lines 61–67) vs §5b code (lines 130–145)

**Problem:** The preamble at §5 says:

> The Python exporter uses `os.getloadavg()[0] / os.cpu_count() * 100` as the CPU percentage value.

But the actual code in §5b uses:

```python
load = float(open("/proc/loadavg").read().split()[0])
import os
return min(100.0, load / os.cpu_count() * 100)
```

These are semantically equivalent (both read the 1-minute load average), but the code reads `/proc/loadavg` directly instead of calling `os.getloadavg()`. This inconsistency between description and code will confuse the agent — if it reads the preamble first, it might "correct" the code to use `os.getloadavg()`, which would actually be fine but would diverge from the prompt's provided code block.

The macOS path does NOT use `os.getloadavg()` either — it shells out to `sysctl`.

**Correction:** Update the preamble at lines 61–67 to match the actual code:

**Replace lines 61–67 with:**

```markdown
### Note on CPU metric approximation

The Python exporter reads the 1-minute load average from `/proc/loadavg` (Linux) or
`sysctl -n vm.loadavg` (macOS) and normalizes it by CPU count. This is intentionally
a load-average-based approximation, not actual CPU utilization. This is acceptable
for the system health monitoring use case.

**Do NOT** "improve" this by adding `psutil` or other non-stdlib dependencies.
The exporter scripts MUST use stdlib only (no pip install required on the NAS).
**Do NOT** replace the `/proc/loadavg` read with `os.getloadavg()` — both work,
but the explicit file read is more transparent and matches the bash script's approach.
```

**Also update the duplicate warning block at lines 224–232 (the `> ⚠️ Note` block after the Python code) to match.**

**Correction:** Add after line 244:

- `scripts/exporters/system-metrics-exporter.py` (NEW)
- `Docs/data-ingest-setup.md` (NEW)
- `Docs/changelog.md` (modified — v7.5.6.3 entry)

### A7 — §3 Current Status says `<TODAY>` — needs to be an actual instruction (SEVERITY: LOW)

**Location:** §3, line 35

**Problem:** The prompt contains `Current date: <TODAY>` which is a template placeholder. Previous prompts had the same pattern and it worked because the human operator replaces it before pasting. But if the prompt is fed to the coding agent directly from the repo file (which is the documented workflow in `prompt-index-and-workflow.md`), the agent sees the literal string `<TODAY>`.

This is a recurring issue across all Phase 6 prompts. Low severity because the agent can determine the date from the system, but it adds unnecessary ambiguity.

**Correction:** Replace line 35 with:

```markdown
- Current date: 2026-03-26 (or check `date +%Y-%m-%d` at execution time)
```

Or, if you prefer to keep it as a template, add an instruction at §1:

