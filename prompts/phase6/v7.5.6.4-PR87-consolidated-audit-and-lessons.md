### Critical prompt defects

#### A1 — Mock ingest endpoint under-specified: only device validation, no metric/val validation (Severity: HIGH — caused merge-blocking review, 2 fix commits)

**§5b** says: "Add `/api/ingest/:deviceId/:metricKey` mock route for POST requests" and provides a simple `{"ok":true}` for known devices, 404 for unknown. It does NOT require:
- Validating `metricKey` against the device's `measurements[].key`
- Validating `val` query parameter (missing/empty/non-finite → 400)
- Returning JSON error shape `{ok:false,message,status}` matching firmware contract

The agent implemented the literal prompt: device-exists → 200, unknown device → 404. This was caught by Copilot reviewer (r2997261901), the third-party Codex review (issuecomment-4137810485), and the manual review (issuecomment-4137974439). Two fix commits were required (`0d57900` for metric validation, `e3de581` for val validation).

**Root cause:** The prompt simplified the ingest mock to happy-path + unknown-device. It should have enumerated all firmware error branches.

**Prevention:** When a prompt asks the agent to mock an existing firmware endpoint, include a **contract-lock section** that:
1. Names the firmware function to read (`handle_api_ingest_()`)
2. Enumerates all positive + negative branches
3. Specifies exact response shapes for success and failure
4. Requires one test per branch
5. Explicitly prohibits stub-level mocking: "Do NOT reduce this mock to a 'device exists → 200' stub"

---

#### A2 — Skip-reason strings not updated after mixed fixture composition change (Severity: MEDIUM — caused 4 review comments)

**§5b-note** requires adding `nas01` to mixed, making it 4 sensors. But the prompt does not instruct the agent to update existing skip-reason strings that reference "mixed has 3 sensors." The agent faithfully updated the fixture but left stale text in Groups 14, 15, and 18 skip reasons.

**Root cause:** The prompt addressed the fixture change but not the downstream text that references the fixture's composition.

**Prevention:** When a prompt changes a fixture's sensor count, include an explicit instruction: "After updating the mixed fixture, search all `test.skip()` reason strings for references to the old mixed sensor count and update them."

---

#### A3 — No instruction to remove unused Playwright fixtures from test signatures (Severity: LOW — caused 1 review comment)

The prompt-provided test code for `/api/v2/live returns system device data` uses `async ({ page, request })` but only uses `request`. The prompt did not flag this.

**Prevention:** Add "Verify all test signatures only destructure fixtures they actually use" to the test group guardrails.

## Part III — Lessons

### New Lessons for `bugs-and-lessons-learned.md`

#### LESSON-OPS-081 — Mock endpoint prompts must enumerate all firmware validation branches

**Source:** v7.5.6.4 PR #87 — mock ingest required 2 fix commits because the prompt only specified device validation.

When a prompt asks the agent to create a mock endpoint for an existing firmware API, the prompt MUST:
1. Name the firmware function to read (e.g., `handle_api_ingest_()`)
2. Enumerate all positive and negative validation branches
3. Specify exact response shapes for success (`{"ok":true}`) and failure (`{"ok":false,"message":"...","status":N}`)
4. Require one test per branch
5. Explicitly prohibit stub-level mocking: "Do NOT reduce this mock to a 'device exists → 200' stub"

A mock that only validates device existence is a stub, not a contract-faithful implementation. It hides client-side bugs and causes merge-blocking review comments.

---

#### LESSON-OPS-082 — Fixture composition changes require downstream text audit

**Source:** v7.5.6.4 PR #87 — mixed fixture gained `nas01` (3 → 4 sensors) but skip-reason strings referencing "3 sensors" remained in 4 locations.

When a prompt changes a fixture's sensor count or composition:
1. The prompt MUST include an explicit instruction: "After updating the fixture, search all `test.skip()` reason strings in `dashboard.spec.js` for references to the old sensor count and update them."
2. The prompt MUST also flag any group header comments that describe the fixture by composition.

A fixture change is not complete until all downstream text references to that fixture's old composition are updated.

---

#### LESSON-OPS-083 — Playwright test signatures must not include unused fixture arguments

**Source:** v7.5.6.4 PR #87 review comment (Gemini r2997248086) — test `/api/v2/live returns system device data` destructured `{ page, request }` but only used `request`.

When writing a Playwright test that only uses the `request` fixture (e.g., a pure API test), do not include `page` in the destructured argument list. Including `page` forces Playwright to create a browser context even when it is not needed.

**Rule:** Every test function signature must destructure only the fixtures it actually uses. Prompts must include a QA gate: "scan all new tests for unused Playwright fixture arguments before merging."

### Updates Needed for `writing-prompts-for-coding-agents-guide.md`

#### Add §3.12 — Mock Contract Fidelity

> When a prompt asks the agent to mock a firmware endpoint, the prompt must include a **contract-lock section**:
> 1. Name the firmware source function to read
> 2. List all validation branches (device check, metric check, value check, etc.)
> 3. Specify exact response shapes for success and every failure mode
> 4. Require one automated test per branch
> 5. Prohibit stub-level mocking explicitly
>
> A "happy-path + unknown-device" mock is a stub. Stubs hide client-side bugs and always trigger merge-blocking review comments.

#### Addition to §3.11 — Test Group Implementation Guardrails

Add to the existing guardrails list:

> - After any fixture composition change (sensor count or device list), include an explicit search-and-update instruction for all `test.skip()` reason strings that reference the old composition.
> - Verify all test function signatures only destructure the Playwright fixtures (`page`, `request`, etc.) they actually use. Remove unused fixtures from the destructured argument list.
