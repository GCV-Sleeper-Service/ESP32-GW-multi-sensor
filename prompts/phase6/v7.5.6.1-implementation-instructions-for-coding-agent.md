## 5. Exact Scope — System Device Category

Add a `system` device type to the manifest and generator. System devices use the `external_push` adapter — no RTOS task, no BLE scanning. Data arrives via `POST /api/ingest`.

### 5a. Add system device to `config/sensors.json`

Add after the `wan_ping` entry:

```json
{
  "id": "nas01",
  "name": "NAS Health",
  "category": "system",
  "adapter": "external_push",
  "source": { "description": "Pushed via /api/ingest from NAS cron job" }
}
```

### 5b. Extend `sensor_manifest_lib.py` validation

- `category` must accept `"system"` in addition to `"environmental"` and `"network"`
- `adapter` must accept `"external_push"` in addition to `"thermopro_ble"` and `"icmp_ping"`
- For `external_push` adapter: `mac` is NOT required. `source.description` is optional.
- Validation must NOT reject the entry for missing `mac` (same as `icmp_ping` pattern)

### 5c. Extend `render_sensor_config.py` generator

Generate a `SensorEntity` for system devices following the ping device pattern:

- `category_id = 1` (system)
- Metrics: `cpu_pct`, `ram_pct`, `disk_pct` (analog, RAM-only history), `uptime_hrs` (metadata, no history)
- Define `metrics_system[]` MetricDef array (similar to `metrics_ping[]`)
- Generate HistoryBuffers for history-enabled system metrics
- `NUM_ENV_SENSORS` remains unchanged (3) — system device is NOT environmental
- `NUM_DEVICES` increases by 1 (now 5: 3 env + 1 network + 1 system)

### 5d. ⚠️ CRITICAL: `NUM_SENSORS` must NOT change

`NUM_SENSORS` aliases `NUM_ENV_SENSORS` (BUG-045 prevention). Adding a system device changes `NUM_DEVICES` but must NOT change `NUM_SENSORS`. Verify in generated `sensor_history_multi.h`:
```cpp
static constexpr int NUM_DEVICES = 5;       // 3 env + 1 network + 1 system
static constexpr int NUM_ENV_SENSORS = 3;   // environmental only
static constexpr int NUM_SENSORS = NUM_ENV_SENSORS;  // backward compat for persistence
```

### 5e. Manifest update

The generated `gateway_manifest.h` v2 JSON must include the system device with its measurements. The `metrics` array in the manifest must include system metric definitions alongside temp/hum.

### 5f. ⚠️ Endpoint Audit (LESSON-OPS-064)

After adding the system device, verify ALL existing endpoints:

| Endpoint | Expected behavior for system device |
|---|---|
| `/sensors.json` | Must NOT include `nas01` (filters `category_id == 0`) — verify |
| `/api/status` | Must include `nas01` with `"category":"system"`, NO `temp_valid`/`hum_valid` — verify |
| `/api/manifest` | Must include `nas01` with full v2 schema — verify |
| `/api/v2/live` | Must include `nas01` with null values (no data pushed yet) — verify |
| `/history/nas01/temp` | Must return 404 (non-environmental legacy path blocked) — verify |
| `/api/v2/history/nas01/cpu_pct` | Must return empty CSV (no data yet, but route should work) — verify |
| `/api/ingest/nas01/cpu_pct?val=50` | Must return 200 and update the metric — verify |

### 5g. Dashboard impact — verify `chartIdx` filtering holds

The dashboard's `applySensorMeta()` assigns `chartIdx = -1` to non-environmental sensors. The system device (`category: "system"`) will get `chartIdx = -1`. Verify that:
- `mkDS()` excludes the system device from chart datasets (filters `chartIdx >= 0`)
- `loadHistory()` skips the system device (checks `s.category !== 'environmental'`)
- `applyHistoryRange()` skips (checks `s.chartIdx < 0`)

These filters were added in v7.5.4.5 for the network device. They should work for system devices without changes. **Verify — do not assume.**
