## 2. Consolidated Defect Registry

All ten defects identified across the three sources, unified and deduplicated.

### A1 — Missing `compute_averages()` for `external_push` in averaging lambda
- **Severity:** CRITICAL — firmware-breaking, merge-blocking
- **Sources:** All three (unanimous)
- **Prompt gap:** §5c says "Generate HistoryBuffers for history-enabled system metrics" but never mentions `compute_averages(epoch)` calls or the averaging lambda
- **Code evidence:** `render_yaml_averaging()` (lines 212–219) and `generate_board_yaml()` (lines 777–781) both filter on `adapter == "icmp_ping"` only
- **Runtime impact:** `add_sample()` updates accumulator but HistoryBuffer never receives averaged entries. `/api/v2/history/nas01/cpu_pct` returns empty forever.
- **Guide gap violated:** §6 Gap 3 (Missing Periodic Trigger), §10 Anti-Pattern #3 ("follow the X pattern")
- **PR fix status:** ✅ FIXED in commit `979ac36` — `devices[4].compute_averages(epoch)` added to AVERAGING block
- **Lesson:** The prompt described the producer (`add_sample`) and the consumer (HistoryBuffer) but omitted the transfer mechanism (`compute_averages`)

- **Sources:** Third-party audit + independent review (Copilot initial analysis did not call this out as a distinct item)

## 5. Prompt Audit — What Failed

### 5.1 Critical failure: Missing periodic trigger instruction (A1)

**This is the single most important finding across all three sources.**

The prompt says:
- Add history-enabled system metrics (§5c)
- Generate HistoryBuffers (§5c)
- Use ping device pattern (§5c)

The prompt does NOT say:
- Extend the periodic averaging trigger for `external_push`
- `render_yaml_averaging()` currently only handles `icmp_ping`
- `generate_board_yaml()` averaging loop only handles `icmp_ping`
- Without `compute_averages(epoch)`, HistoryBuffers never receive data

**This is a textbook violation of the guide's Gap 3 (§4: Missing Periodic Trigger) and the repo's own Phase 4 case study (§6.1).** The guide explicitly says:

> "For any system with accumulation and periodic flushing, trace the flush trigger. Ask: 'What code calls the function that transfers accumulated data to its final destination? Does that code know about the new entity?'"

The prompt author should have asked this question about `external_push` and answered it in the prompt. The data flow is:

```
ingest POST → add_sample() → accumulator → [???] → HistoryBuffer → /api/v2/history/
```

The `[???]` link is `compute_averages(epoch)`, called every 15 minutes by the AVERAGING lambda. The prompt described the first and last links but not the transfer mechanism.

### 5.2 Critical failure: Missing validation ceiling (A2)

`MAX_SENSORS = 4` is a hard blocker in `canonicalize_sensors()`. The prompt extends validation (§5b) without identifying this constraint. The agent would hit the error immediately when running `--check`, but without understanding the constraint context, it might work around it incorrectly.

### 5.3 High failure: "Follow the X pattern" without enumerating X (A3, A7)

The prompt says "following the ping device pattern" (§5c) and "The generated `gateway_manifest.h` v2 JSON must include the system device with its measurements" (§5e).

It does NOT:
- Name `manifest_v2()` as requiring a new branch
- Name `render_entity_block()` as requiring a new branch
- Warn about the fallback-to-empty-measurements trap in `manifest_v2()`

This is the guide's Anti-Pattern #3: *"Telling the agent to 'follow the pattern of X' without specifying what X actually does across all files."*

### 5.4 Medium failure: No canonical metric schema (A6)

The prompt lists metric names (`cpu_pct`, `ram_pct`, `disk_pct`, `uptime_hrs`) and types (analog/metadata, history/no-history) but doesn't provide a full schema definition. This forces the agent to invent bounds, units, display precision, and history suffixes — details that must be consistent across manifest, entity generation, and fixtures.

## 10. Lessons Learned

### LESSON-PROMPT-001: Data flow tracing must include ALL transfer mechanisms

**Context:** v7.5.6.1 prompt described the data producer (`POST /api/ingest → add_sample()`) and the data consumer (HistoryBuffer → `/api/v2/history/`). It did not describe the transfer mechanism (`compute_averages(epoch)` called by the 15-minute averaging lambda).

**Rule:** When a prompt adds a new entity to an accumulation-and-flush system, the prompt must explicitly trace:
1. Where data enters the system (producer)
2. Where data accumulates (buffer/accumulator)
3. What triggers the transfer from accumulator to final storage (flush mechanism)
4. Whether the trigger knows about the new entity
5. If the trigger has adapter-specific filtering, whether the new adapter is included

**Concrete application:** For any prompt that says "add HistoryBuffers for [new adapter]", the prompt MUST also say:
> "Verify that `render_yaml_averaging()` and `generate_board_yaml()` include the new adapter in their averaging loop filters. Currently these functions filter on `adapter == 'icmp_ping'` — extend them to also match `adapter == '[new_adapter]'`."

### LESSON-PROMPT-002: "Follow the X pattern" must enumerate every site X touches

**Context:** v7.5.6.1 §5c said "Generate a SensorEntity for system devices following the ping device pattern." The ping device pattern touches 7 code sites: `sensors.json`, `sensor_manifest_lib.py` (_PING_METRICS), `render_sensor_config.py` (render_entity_block, render_yaml_averaging, generate_board_yaml), `generate-fixtures.js`, and `gateway_manifest.h`.

**Rule:** When referencing an existing pattern, enumerate every file and function that pattern touches. If the list is long, provide it as a checklist:

```
The "ping device pattern" touches these sites:
□ config/sensors.json — device entry with category, adapter, id
□ sensor_manifest_lib.py — _PING_METRICS constant, manifest_v2() branch
□ render_sensor_config.py:
  □ render_entity_block() — MetricDef array, HistoryBuffers, SensorEntity
  □ render_yaml_averaging() — compute_averages() call in AVERAGING lambda
  □ generate_board_yaml() — compute_averages() in board YAML averaging block
  □ About description builder — device mention in description string
□ generate-fixtures.js — writeFixtureSet() stub CSVs, fixtureManifestV2() entry
□ gateway_manifest.h — regenerated output
```

### LESSON-PROMPT-003: Validation gates must be named in prompts that extend validated data

**Context:** v7.5.6.1 extended `config/sensors.json` from 4 to 5 entries. `sensor_manifest_lib.py` has `MAX_SENSORS = 4`. The prompt didn't mention this constraint.

**Rule:** When a prompt instructs adding items to a validated collection, search the validation code for hard limits and name them:
> "NOTE: `sensor_manifest_lib.py` line 21 has `MAX_SENSORS = 4`. This must be raised to 5 to accommodate the new system device."

### LESSON-PROMPT-004: Generated comments and documentation strings are code

**Context:** The SENSOR COUNT CONFIGURATION GUIDE comment block in `sensor_history_multi.h` was not identified as needing an update. It said "max 4" when `NUM_DEVICES=5`.

**Rule:** If a generated file contains human-readable guides, changelogs, or documentation embedded in comments, the prompt must include instructions to update them when semantics change. These are not "just comments" — they are developer-facing documentation that will mislead future readers.

### LESSON-PROMPT-005: Generator branch points must be explicitly named

**Context:** `manifest_v2()` falls through to empty measurements for unknown adapters. `render_entity_block()` only handles `thermopro_ble` and `icmp_ping`. The prompt didn't name these functions as requiring new branches.

**Rule:** When extending a generator to handle a new adapter or category, the prompt must name every function that dispatches on adapter/category and describe what happens for unrecognized values:
> "`manifest_v2()` (sensor_manifest_lib.py line 235) has explicit branches for `thermopro_ble` and `icmp_ping`. Unrecognized adapters fall through to `'measurements': []`. You MUST add an `external_push` branch that emits system metric measurements with correct `history_url` values."

### LESSON-PROMPT-006: Review-fix cycles cost 3x — catch issues in the prompt

**Context:** PR #82 required 4 fix commits after 2 implementation commits. ~60% of wall-clock time was spent on review-driven fixes.

**Quantitative rule:** Each review→fix cycle costs approximately 30 minutes of agent time (read comments, understand context, make fix, push, wait for re-review). Three cycles = 90 minutes. If the prompt had explicitly called out `compute_averages()`, `MAX_SENSORS`, and `manifest_v2()` fallthrough, the agent would likely have gotten it right in one pass — saving ~90 minutes.

### LESSON-PROMPT-007: Prompt pre-flight must include data lifecycle trace for new entities

**Context:** The guide's §9 pre-flight checklist asks prompt authors to check for periodic triggers and flush mechanisms. This check was not applied to v7.5.6.1.

**Enhancement to pre-flight:** Add this question to the mandatory prompt pre-flight:
> "For each new entity or data path: trace input → accumulation → flush → storage → API → test fixture → mock server → Playwright assertion. Is every link explicitly addressed? Is the flush trigger named?"

### 11.3 New anti-pattern for §10

```markdown
### Anti-Pattern 14: Referencing an existing pattern without enumerating its touch points

**Example:** "Generate a SensorEntity for system devices following the ping device pattern"

**Problem:** The "ping device pattern" touches 7 code sites across 4 files. The agent may
identify 5 of them through code reading but miss the averaging lambda and the fixture
generator. The prompt author knows what "the ping pattern" means because they wrote it.
The agent does not.

**Fix:** Enumerate every file and function the pattern touches:

```
The "ping device pattern" requires changes in these files/functions:
□ config/sensors.json — device entry
□ sensor_manifest_lib.py — _PING_METRICS constant, manifest_v2() branch, canonicalize_sensors() validation
□ render_sensor_config.py — render_entity_block(), render_yaml_averaging(), generate_board_yaml()
□ generate-fixtures.js — fixtureManifestV2(), writeFixtureSet()
```

If the list seems too long to enumerate, that is a signal the prompt should be split
into smaller steps, not that the enumeration should be skipped.
```

### 11.4 New anti-pattern for §10

```markdown
### Anti-Pattern 15: Extending validated data without naming validation constraints

**Example:** Prompt adds a 5th device to sensors.json without mentioning MAX_SENSORS = 4.

**Problem:** The generator will reject the manifest with a cryptic error. The agent may
either waste cycles debugging or apply a workaround that breaks other things.

**Fix:** Before writing a prompt that adds items to any validated collection, search the
validation code for hard limits:

```bash
grep -n "MAX_\|max_\|limit\|ceiling" scripts/sensor_manifest_lib.py
```

Name every relevant limit in the prompt:
"NOTE: sensor_manifest_lib.py line 21 has MAX_SENSORS = 4. Raise to 5."
```

### Source characteristics

| Source | Strength | Blind Spot |

| **Copilot initial analysis** | PR execution timeline, review comment tracking, fix prompt generation | Did not independently identify A2 (MAX_SENSORS) as distinct defect |

### Value of multi-source analysis

The three-source approach revealed that:
1. **Single-source analysis is insufficient for generator-heavy codebases** — each source caught details the others missed
2. **Prompt audit and PR audit are complementary** — the prompt audit identifies what *should have been caught before execution*; the PR audit identifies what *was actually caught during/after execution*
3. **The attribution question matters** — "Is this a prompt failure or an agent failure?" determines whether to fix the prompt template or the agent's pre-commit validation
