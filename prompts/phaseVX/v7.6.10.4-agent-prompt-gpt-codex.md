## §6 — Implementation Steps

### Task 1: Create `dashboard/core/auth.js`

Create a new core module at `dashboard/core/auth.js` with the following structure:

```javascript
// auth.js — Application-level credential management
// Eliminates browser native auth dialogs by injecting Authorization header
// in every fetch call to auth-gated endpoints.

var _authHeader = null;  // 'Basic <base64>' or null

function authFetch(url, opts) {
  if (!opts) opts = {};
  if (_authHeader) {
    if (!opts.headers) opts.headers = {};
    opts.headers['Authorization'] = _authHeader;
  }
  // Never use credentials: 'same-origin' — we manage auth ourselves
  delete opts.credentials;
  return fetch(url, opts).then(function(resp) {
    if (resp.status === 401 && _authHeader) {
      // Credentials expired or changed — clear and re-prompt
      _authHeader = null;
      // Don't auto-prompt here — let the caller handle the 401
    }
    return resp;
  });
}

function setAuthCredentials(username, password) {
  _authHeader = 'Basic ' + btoa(username + ':' + password);
}

function clearAuth() {
  _authHeader = null;
}

function isAuthenticated() {
  return _authHeader !== null;
}

function getAuthHeader() {
  return _authHeader;
}

// Probe whether auth is required by trying /api/status/full without credentials
function probeAuth() {
  return fetch(ESP_HOST + '/api/status/full', {cache: 'no-store'})
    .then(function(resp) {
      if (resp.status === 401) {
        return 'required';
      }
      return 'not-required';
    })
    .catch(function() {
      // Network error — can't determine, assume required
      return 'required';
    });
}
```

**Important:** This is a core module. It must use `var` and `function` declarations (not `const`/`let`/arrow functions) for compatibility with the project's ES5-compatible dashboard code style. Check existing core modules for the coding convention.

### Task 2: Integrate auth probe into boot sequence

In `dashboard/core/boot.js`, add an auth probe step early in the initialization:

1. Call `probeAuth()` before loading status snapshot
2. If auth is required: call `requestManagementCredentials('Dashboard access')` (from auth-modal)
3. On successful auth: call `setAuthCredentials(username, password)` with the entered credentials
4. On cancel: proceed in degraded mode (public endpoints only)
5. Then continue with normal boot sequence

**Read `boot.js` carefully before modifying.** The boot sequence has a specific order (manifest → status → history → SSE/polling). Auth must happen before the first auth-gated fetch.

### Task 3: Extend `auth-modal/index.js` integration

The `requestManagementCredentials()` function already works. Extend it:

1. After successful credential verification (the function already does a test fetch), call `setAuthCredentials(username, password)` with the verified credentials
2. The existing verify fetch in the auth modal uses its own `Authorization` header construction — align this with `_authHeader` so the credential is stored centrally

**Do NOT rewrite requestManagementCredentials().** Extend it minimally. The existing function handles dialog lifecycle, error display, rate limiting, and cleanup correctly.

### Task 4: Convert fetch → authFetch in all dashboard modules

For each file, replace `fetch()` calls that hit auth-gated endpoints with `authFetch()`. Leave `fetch()` calls for public endpoints unchanged.

**Public endpoints** (no auth — leave as plain `fetch()`):

### Task 5: Handle 401 re-authentication during operation

In modules that handle fetch responses (status-snapshot, gateway-panel), add a pattern:

```javascript
authFetch(url, opts).then(function(resp) {
  if (resp.status === 401) {
    clearAuth();
    return requestManagementCredentials('Session expired')
      .then(function(creds) {
        setAuthCredentials(creds.username, creds.password);
        // Retry the fetch
        return authFetch(url, opts);
      });
  }
  return resp;
});
```

Apply this pattern to the **primary polling loops** (status-snapshot, gateway-panel). Do NOT apply it to every single fetch — only the ones that run on timers and would cause repeated 401 failures.
